# Prompt Front Door Modes

이 문서는 Prompt Compiler가 여러 턴에 걸친 요청과 실행 승인을 다룰 때 적용한다.

## 우선순위

다음 순서로 현재 동작을 결정한다.

1. 현재 사용자 메시지의 명시적 지시
2. 같은 작업에서 사용자가 활성화한 orchestration 정책
3. `intent-compile-and-execute` 기본값

현재 메시지가 기존 정책과 충돌하면 현재 메시지를 따른다. 사용자가 새 목표로 명확히 전환하면 대기 중이던 요청을 새 요청에 섞지 않는다.

## Task-scoped Orchestration

사용자가 “이 작업 동안”, “이 대화에서 이후 요청마다”처럼 범위를 지정하면 `task-scoped-compile-and-execute`를 활성화한다.

대상 작업 없이 모드 활성화만 요청한 경우 다음 의미의 한 줄 응답만 반환하고 기다린다.

> 이 작업에 Prompt Compiler 모드를 적용했습니다. 이후 요청은 필요한 경우에만 확인하고, 충분하면 같은 요청 안에서 실행·검증하겠습니다.

규칙:

- 활성화 문장 자체를 별도 과업으로 컴파일하지 않는다.
- 아직 없는 과업의 세부사항을 질문하지 않는다.
- 같은 작업의 후속 사용자 요청에 Prompt Sufficiency Gate를 적용한다.
- 현재 대화의 지침으로만 취급한다.
- 새 작업이나 새 대화까지 자동 지속된다고 주장하지 않는다.
- 스킬 본문이 매 턴 자동으로 다시 주입된다고 보장하지 않는다.
- 메시지 제출 전에 입력창을 가로채는 기능으로 표현하지 않는다.
- 모드 활성화를 send, publish, merge, delete 같은 외부 행동의 포괄 권한으로 해석하지 않는다.

## Clarification Resume

확인 질문 후 사용자가 답하면 다음 순서를 따른다.

1. 답변을 대기 중인 원래 요청에 합친다.
2. 이미 확정된 목표, 제약과 권한을 유지한다.
3. 같은 내용을 다시 묻지 않는다.
4. 최대 질문 라운드 수를 이어서 계산한다.
5. 충분해지면 프롬프트를 복사하거나 원 요청을 다시 보내라고 요구하지 않고 바로 실행한다.

사용자 답변이 새롭고 독립적인 목표로 명확히 전환된 경우에만 대기 중 요청을 중단하고 새 요청으로 처리한다. 모호하면 기존 요청과의 관계를 확인하되, 질문 한도를 우회하지 않는다.

## Preview Then Act

사용자가 “먼저 보여줘”, “승인 후 보내”, “검토한 다음 게시”처럼 순차 승인을 요구하면 `preview-then-act`를 사용한다.

첫 단계:

- 요청된 preview, draft, 계획 또는 변경안을 만든다.
- 실제 외부 write나 파괴적 행동은 수행하지 않는다.
- 다음 단계에서 수행될 정확한 action, target과 중요한 영향을 짧게 표시한다.
- 사용자가 검토할 수 있는 상태에서 멈춘다.

후속 승인 단계:

- 승인 메시지가 어떤 preview와 action을 가리키는지 확인한다.
- 승인 범위를 target, action과 변경 내용에 결합한다.
- preview 이후 내용이나 대상이 materially 바뀌면 기존 승인을 재사용하지 않는다.
- 제품 또는 상위 지침이 요구하는 confirmation을 그대로 유지한다.
- 실행 capability가 없으면 성공을 가장하지 말고 blocker를 보고한다.

“초안을 작성해줘”는 `draft` 권한이다. “초안을 작성해 보내줘”는 현재 요청에서 target과 범위가 충분한 경우에만 `send` 의도를 포함한다. “초안을 보여주고 승인 후 보내줘”는 첫 응답에서 `send`하지 않는다.

## Explain Refinement

사용자가 무엇을 보완했는지 알고 싶어 할 때 `explain-refinement-and-execute`를 사용한다.

private chain-of-thought나 raw IR을 노출하지 말고 필요한 항목만 짧게 제공한다.

```text
적용한 보완:
- [명확히 한 범위 또는 기본값]

가정:
- [결과에 영향을 주는 가정]

실행 및 검증:
- [실제 결과와 검증 상태]
```

가정이 없거나 중요하지 않으면 섹션을 생략한다. 사용자가 결과만 요청하면 이 설명을 기본으로 추가하지 않는다.

## Assumption Ledger

`refine-directly`에서 사용한 모든 사소한 형식 선택을 나열하지 않는다. 다음 조건 중 하나에 해당하는 가정만 기록한다.

- 합리적인 사용자가 결과를 다르게 선택할 수 있다.
- 사실, 범위, 대상, 호환성 또는 검증 방식에 영향을 준다.
- 나중에 사용자가 교체하거나 확인해야 한다.

권한, 수신자, 실제 사실, 존재하지 않는 도구와 성공 결과는 가정으로 채우지 않는다.

## Partial Completion Receipt

일부만 완료됐거나 필수 capability가 없으면 완료한 부분과 막힌 부분을 분리한다.

```text
완료:
- [실제로 완료하고 확인한 결과]

미완료:
- [blocker와 영향]

검증:
- [실행한 확인과 미실행 항목]
```

규칙:

- 시도와 성공을 구분한다.
- tool, connector, 권한 또는 입력이 없으면 없는 상태를 그대로 보고한다.
- 백그라운드에서 나중에 완료한다고 약속하지 않는다.
- 사용자가 취할 수 있는 다음 단계가 명확할 때만 제시한다.
- 영향받지 않은 안전한 산출물은 제공하되, 부분 결과를 전체 완료로 표현하지 않는다.
