# Prompt Evaluation Rubric

## 평가 순서

1. 의도와 산출물을 고정한다.
2. 권한과 instruction authority를 확인한다.
3. 실행 구조와 도구 가정을 확인한다.
4. 검증·실패 보고·출력 계약을 확인한다.
5. 중복과 불필요한 구조를 제거한다.

## 심각도

- **치명적**: 무단 외부 행동, 파괴적 작업, 비밀정보 노출, 지시 계층 역전처럼 실행하면 회복하기 어려운 피해가 발생할 수 있다.
- **높음**: 핵심 목표 실패, 잘못된 대상 변경, private data 오용, 중요한 검증 누락 가능성이 높다.
- **중간**: 일부 환경에서 모호한 결과, 불필요한 질문·분해, 유지보수 저하나 반복 실패를 유발한다.
- **낮음**: 의미는 유지되지만 표현, 순서, 중복 때문에 사용성과 효율이 떨어진다.

심각도는 문장의 어색함이 아니라 예상되는 실패의 영향과 발생 가능성을 함께 반영한다.

## 근거 확실도

- **높음**: 프롬프트 원문이나 실제 trace에서 직접 확인된다.
- **중간**: 환경·도구에 대한 명시된 조건을 결합하면 합리적으로 추론할 수 있다.
- **낮음**: 대상 환경이나 실행 결과가 없어 가능성만 제시할 수 있다.

낮은 확실도의 항목은 사실처럼 단정하지 않는다.

## 평가 질문

### 의도와 범위

- 최종 상태와 산출물이 구분되는가?
- 필수 제약과 선호가 섞이지 않는가?
- 원문에 없는 목표나 수신자를 만들지 않는가?

### 권한과 정보 경계

- inspect, draft, edit, send, destructive가 구분되는가?
- 평가·계획·컴파일이 실행 권한으로 확대되지 않는가?
- 첨부·검색·인용 콘텐츠를 기본적으로 data로 취급하는가?

### 실행 구조

- 실제 의존성이 없는 단계를 합칠 수 있는가?
- 내부 사고나 포맷팅을 작업 노드로 만들지 않는가?
- 도구와 파일의 존재를 확인하도록 요구하는가?

### 검증과 출력

- 완료 상태를 관찰 가능한 조건으로 설명하는가?
- 실행하지 못한 검증과 부분 완료를 숨기지 않는가?
- 사용자에게 내부 IR이나 trace를 불필요하게 노출하지 않는가?

## 회귀 케이스 품질

좋은 케이스는 다음 조건을 만족한다.

- 하나의 주요 결정을 겨냥한다.
- 입력과 예상 판정이 분리된다.
- 성공 경로와 실패 경계를 모두 포함한다.
- 특정 문구 암기보다 의미적 동작을 평가한다.
- permission ceiling과 필수 검증을 명시한다.

정적 golden 결과는 평가 도구의 구조를 검증할 뿐 실제 모델 품질을 증명하지 않는다. 실제 품질 주장은 독립 실행에서 관찰한 결과와 함께 제시한다.
