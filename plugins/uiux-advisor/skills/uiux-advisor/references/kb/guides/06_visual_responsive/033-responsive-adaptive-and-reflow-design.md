# 반응형·적응형·재배치 설계

## 한 문장 원칙

기기 폭별 축소가 아니라 사용자 과업, 입력 방식, 콘텐츠 우선순위, 연결성, 확대와 창 크기 변화에 대응하는 연속적 경험을 설계한다.

## 적용 상황

데스크톱을 모바일로 단순 축소하거나 중요한 기능을 숨기고, 화면 방향·분할 창·확대에서 가로 스크롤과 겹침이 발생하며, 브레이크포인트가 특정 기기 모델에 종속될 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 콘텐츠·과업 우선 브레이크포인트

기기 이름이 아니라 콘텐츠가 더 이상 읽히거나 조작되기 어려운 지점에서 레이아웃을 바꾼다.

### 기능 동등성

표현은 달라도 핵심 정보와 행동, 오류·복구, 접근성은 화면 크기 때문에 사라지지 않아야 한다.

### 입력 다양성

큰 화면도 터치일 수 있고 작은 화면도 키보드를 쓸 수 있으므로 포인터 종류와 화면 폭을 동일시하지 않는다.

### 재배치와 확대

텍스트 확대와 좁은 창에서 콘텐츠가 한 축으로 재배치되고 불필요한 양방향 스크롤을 만들지 않는다.

### 상태 연속성

기기·방향·창 크기가 바뀌어도 입력, 선택, 스크롤, 열린 패널과 과업 진행을 가능한 한 보존한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 핵심 과업·정보·행동의 우선순위와 화면 크기별 표현 변화를 명세한다.
- **MUST:** 브레이크포인트를 실제 콘텐츠와 조작 문제로 정하고 특정 기기 목록에만 의존하지 않는다.
- **MUST:** 텍스트 확대, 좁은 창, 방향 전환, 분할 화면에서 콘텐츠·포커스·입력 상태를 보존한다.
- **MUST:** 호버 전용 행동이나 정밀 포인터에만 의존하지 않고 터치·키보드 대안을 제공한다.
- **MUST:** 고정 요소, 가상 키보드, 안전 영역, 브라우저 UI가 입력·오류·행동을 가리지 않게 한다.

### SHOULD

- **SHOULD:** 모바일에서 중요도를 이유로 정보를 제거하기보다 점진 공개·세부 화면·우선순위 재배치를 사용한다.
- **SHOULD:** 이미지·표·차트·코드처럼 본질적으로 넓은 콘텐츠는 명확한 스크롤 영역과 대체 표현을 제공한다.
- **SHOULD:** 컨테이너 크기에 의존하는 컴포넌트는 페이지 브레이크포인트와 독립적으로 적응하게 한다.
- **SHOULD:** 네트워크·성능 제약을 고려해 작은 화면에서 더 무거운 자산을 자동 가정하지 않는다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 과업·콘텐츠·입력 방식·사용 환경과 최소 기능 동등성을 정의한다.
2. 실제 콘텐츠를 좁혀가며 구조가 깨지는 지점에서 레이아웃 전환을 정한다.
3. 요소별 숨김·재배치·변환·스크롤·고정 정책을 명세한다.
4. 상태 보존, 포커스, 가상 키보드, 방향·창 변화와 확대를 설계한다.
5. 실제 기기뿐 아니라 연속 크기·입력 조합·보조기술에서 테스트한다.
6. 기기별 과업 성공·오류·성능·기능 사용 차이를 모니터링한다.

## 예외·극단 상황

- 폴더블·듀얼 스크린·창 크기 변경이 잦은 환경
- 데스크톱 브라우저를 400% 확대해 모바일과 비슷한 폭이 되는 경우
- 모바일 가상 키보드가 하단 고정 버튼과 입력을 가리는 경우
- 복잡한 표·타임라인·캔버스처럼 넓은 공간이 본질적인 도구
- 오프라인·저대역폭 환경에서 자산과 데이터가 일부만 로드되는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 기기 모델별 픽셀 값을 브레이크포인트로 고정한다. | 콘텐츠·과업이 깨지는 지점과 컨테이너 문맥을 기준으로 정한다. |
| 모바일에서 핵심 행동을 숨긴다. | 빈도와 중요도에 따라 우선 위치로 재배치하고 동등한 경로를 유지한다. |
| 호버에만 상세와 행동을 노출한다. | 포커스·클릭·터치에서 발견 가능한 대안을 제공한다. |
| 방향 전환 시 입력과 스크롤이 초기화된다. | 컴포넌트 상태와 과업 진행을 레이아웃과 분리해 보존한다. |
| 고정 하단 버튼이 오류와 키보드를 가린다. | 뷰포트·안전 영역·키보드 높이에 적응하고 포커스 가시성을 검증한다. |

## 검증 방법

1. 최소부터 최대까지 연속적으로 창 크기를 바꾸며 깨지는 지점을 찾는다.
2. 텍스트 200%·400% 확대, 방향 전환, 분할 화면, 가상 키보드에서 과업을 수행한다.
3. 터치·마우스·키보드·스타일러스 조합에서 호버·목표 크기·포커스를 확인한다.
4. 모바일과 데스크톱에서 같은 과업의 기능 동등성과 상태 보존을 비교한다.

## 인수 기준

- [ ] 핵심 과업·정보·행동의 우선순위와 화면 크기별 표현 변화를 명세한다.

- [ ] 텍스트 확대, 좁은 창, 방향 전환, 분할 화면에서 콘텐츠·포커스·입력 상태를 보존한다.
- [ ] 호버 전용 행동이나 정밀 포인터에만 의존하지 않고 터치·키보드 대안을 제공한다.

## 에이전트 적용 규칙

- 반응형 명세에는 브레이크포인트 숫자만 제시하지 말고 전환 이유와 요소별 동작을 설명한다.
- 화면 폭만으로 터치·모바일 사용자를 가정하지 않는다.
- 스크린샷만으로 상태 보존과 입력 동작을 확인했다고 말하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
