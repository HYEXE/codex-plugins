# 색상·대비·비색상 단서

## 한 문장 원칙

색상은 위계와 상태를 보조하되 텍스트·형태·아이콘·패턴·위치 같은 비색상 단서와 충분한 대비로 의미를 중복 전달한다.

## 적용 상황

오류·성공·선택을 빨강·초록이나 색상만으로 구분하고, 브랜드 팔레트가 대비 기준을 충족하지 않거나 다크 모드·고대비 모드에서 상태가 사라질 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 의미 중복

색각 차이, 흑백, 저품질 화면, 강한 조명에서도 상태·링크·선택을 이해할 수 있게 한다.

### 실제 조합 검증

색상 토큰 자체가 아니라 글자 크기, 굵기, 배경, 상태, 투명도와 합성된 실제 조합을 검증한다.

### 상태 간 구별

기본·호버·포커스·누름·비활성·선택·오류가 서로 충분히 구분되며 포커스가 가려지지 않아야 한다.

### 테마의 의미 보존

라이트·다크·고대비·브랜드 테마에서 같은 의미 토큰이 일관된 역할을 수행한다.

### 데이터 색상

차트는 범주·순서·긍정·부정을 색상뿐 아니라 레이블·패턴·형태·직접 표기로 전달한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 텍스트, 아이콘, 컨트롤 경계, 포커스 표시의 실제 색상 조합을 해당 접근성 기준으로 검증한다.
- **MUST:** 오류·성공·경고·선택·필수·링크를 색상만으로 전달하지 않는다.
- **MUST:** 비활성 상태를 단순 저대비로 만들어 읽을 수 없게 하지 않고 사용 불가 의미를 구조적으로 표현한다.
- **MUST:** 테마 전환과 시스템 고대비·강제 색상 모드에서 콘텐츠와 상태가 유지되게 한다.
- **MUST:** 동적 배경·이미지 위 텍스트는 모든 가능한 콘텐츠에서 대비를 보장하거나 안정된 배경을 제공한다.

### SHOULD

- **SHOULD:** 의미 색상과 장식 색상을 분리하고 의미 토큰의 사용 범위를 제한한다.
- **SHOULD:** 색각 시뮬레이션을 보조 도구로 사용하되 실제 대비·사용자 테스트를 대체하지 않는다.
- **SHOULD:** 차트 범주 수를 제한하고 직접 레이블·정렬·패턴으로 해석 부담을 줄인다.
- **SHOULD:** 브랜드 색이 기준을 충족하지 않으면 텍스트·배경·경계 역할을 조정하고 예외를 문서화한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 색상의 정보 역할과 장식 역할, 테마, 상태, 데이터 시각화 범위를 인벤토리한다.
2. 의미 토큰과 실제 전경·배경 조합, 비색상 단서를 정의한다.
3. 컴포넌트 모든 상태와 포커스·비활성·오류를 테마별로 검증한다.
4. 차트·이미지·동적 배경·고대비 모드의 예외를 테스트한다.
5. 저시력·색각 차이·야외·저품질 화면에서 과업을 검증한다.
6. 새 색상과 예외가 시스템에 들어오는 승인·자동 검사 절차를 운영한다.

## 예외·극단 상황

- 사용자가 브랜드·조직별 테마를 직접 구성하는 화이트라벨 제품
- 영상·사진·지도처럼 배경 색을 예측할 수 없는 콘텐츠
- 많은 범주와 연속값을 동시에 표현하는 분석 차트
- 다크 모드에서 그림자·경계·고도 표현이 사라지는 경우
- 브라우저 강제 색상·운영체제 고대비 모드

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 필수 필드를 빨간 테두리만으로 표시한다. | 텍스트 레이블·오류 설명·의미 속성을 함께 제공한다. |
| 비활성 텍스트를 읽을 수 없을 정도로 흐리게 한다. | 상태 의미를 별도로 표현하고 필요한 정보는 충분히 읽히게 한다. |
| 브랜드 색 하나를 모든 배경에 사용한다. | 역할별 조합과 대체 토큰을 정의하고 실제 대비를 검증한다. |
| 차트 범주를 비슷한 색만으로 구분한다. | 직접 레이블, 패턴, 형태, 순서와 상호작용 설명을 추가한다. |
| 다크 모드를 색상 반전으로만 만든다. | 고도, 이미지, 상태, 대비, 눈부심과 시스템 설정을 별도 설계한다. |

## 검증 방법

1. 자동 대비 검사와 수동 실제 상태 검사를 함께 수행한다.
2. 흑백·색각 차이·고대비·다크·라이트 테마에서 상태와 차트를 해석하게 한다.
3. 포커스 표시가 모든 배경과 인접 상태에서 분명하고 가려지지 않는지 확인한다.
4. 동적 이미지와 사용자 테마에서 최악 조합을 생성해 회귀 테스트한다.

## 인수 기준

- [ ] 텍스트, 아이콘, 컨트롤 경계, 포커스 표시의 실제 색상 조합을 해당 접근성 기준으로 검증한다.
- [ ] 오류·성공·경고·선택·필수·링크를 색상만으로 전달하지 않는다.
- [ ] 비활성 상태를 단순 저대비로 만들어 읽을 수 없게 하지 않고 사용 불가 의미를 구조적으로 표현한다.
- [ ] 테마 전환과 시스템 고대비·강제 색상 모드에서 콘텐츠와 상태가 유지되게 한다.
- [ ] 동적 배경·이미지 위 텍스트는 모든 가능한 콘텐츠에서 대비를 보장하거나 안정된 배경을 제공한다.
- [ ] 자동 대비 검사와 수동 실제 상태 검사를 함께 수행한다.
- [ ] 흑백·색각 차이·고대비·다크·라이트 테마에서 상태와 차트를 해석하게 한다.

## 에이전트 적용 규칙

- 색상 값을 제안할 때 실제 배경·크기·굵기 없이 대비 충족을 단정하지 않는다.
- 색상 의미에는 반드시 비색상 단서를 함께 제안한다.
- 브랜드 팔레트보다 과업과 접근성 역할을 우선한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

### [spectrum-inclusive] Inclusive Design

- 발행·관리 주체: Spectrum Design System
- 유형: product-design-system
- 적용 범위: 다양한 능력, 상황, 문화권을 고려한 포용적 설계
- 이 가이드에서의 사용: 평균 사용자 가정을 깨고 배제 위험을 발견할 때 사용한다.
- 원문: https://spectrum.adobe.com/page/inclusive-design/

### [material-tokens] Design Tokens

- 발행·관리 주체: Material Design

- 이 가이드에서의 사용: 디자인과 코드의 공통 계약 및 테마 확장 구조를 설계할 때 사용한다.
- 원문: https://m3.material.io/foundations/design-tokens

- 발행·관리 주체: Carbon Design System
- 유형: product-design-system
- 적용 범위: 접근성을 설계·개발·테스트 전 과정에 포함하는 방법
- 이 가이드에서의 사용: 팀 역할과 접근성 품질 게이트를 설계할 때 참고한다.
- 원문: https://v10.carbondesignsystem.com/guidelines/accessibility/overview/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
