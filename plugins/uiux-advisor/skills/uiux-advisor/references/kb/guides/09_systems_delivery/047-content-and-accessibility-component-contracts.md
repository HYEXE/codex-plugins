# 콘텐츠·접근성 컴포넌트 계약

## 한 문장 원칙

컴포넌트는 시각적 껍데기가 아니라 허용 콘텐츠, 의미 구조, 키보드 동작, 접근 가능한 이름·상태, 오류·현지화 규칙을 포함한 계약으로 제공한다.

## 적용 상황

컴포넌트 자체는 접근 가능하다고 주장하지만 제품 팀이 잘못된 레이블·제목·순서·상태 조합으로 결함을 만들거나, 콘텐츠 길이와 번역이 레이아웃을 깨뜨릴 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 공유 책임

기반 컴포넌트가 기술적 의미를 제공해도 호출자가 적절한 레이블·지침·상태·순서를 넣지 않으면 최종 경험은 접근 가능하지 않다.

### 콘텐츠 제약

슬롯마다 목적, 필수 여부, 길이·형식, 금지 표현, 번역·복수형·동적 변경 규칙을 정의한다.

### 네이티브 우선

표준 HTML·플랫폼 컨트롤의 의미와 동작으로 해결하고 불가피한 복합 위젯에만 ARIA 패턴을 적용한다.

### 상태 전달

시각적 변화와 함께 이름·설명·역할·상태·라이브 알림이 보조기술에 올바른 시점과 범위로 전달되어야 한다.

### 조합 접근성

개별 컴포넌트가 통과해도 대화상자 안 폼, 테이블 안 메뉴처럼 조합하면 포커스·읽기 순서·오류 문제가 생길 수 있다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 각 컴포넌트 슬롯에 의미, 필수·선택, 콘텐츠 예시·금지 예시, 길이·번역·동적 갱신 규칙을 제공한다.
- **MUST:** 접근 가능한 이름·설명·역할·상태의 생성 책임이 컴포넌트와 호출자 중 누구에게 있는지 명시한다.
- **MUST:** 키보드 입력, 포커스 진입·이동·복귀, 오류·상태 알림, 확대·재배치 동작을 계약에 포함한다.
- **MUST:** ARIA를 추가할 때 해당 패턴의 키보드 모델과 상태 갱신을 함께 구현하고 네이티브 대안을 먼저 검토한다.
- **MUST:** 잘못된 콘텐츠·속성·조합을 개발 중 탐지할 수 있는 검증, 경고, 예제, 테스트를 제공한다.

### SHOULD

- **SHOULD:** 문서 예시는 행복 경로뿐 아니라 긴 번역, 누락 값, 오류, 비동기 상태, 보조기술 사용을 포함한다.
- **SHOULD:** 콘텐츠 디자이너와 접근성 전문가가 컴포넌트 API와 문서 변경을 공동 검토한다.
- **SHOULD:** 컴포넌트가 스스로 만들 수 없는 페이지 제목·랜드마크·읽기 순서 같은 상위 맥락 책임을 명시한다.
- **SHOULD:** 제품 팀의 오용 사례를 문서·린트·타입·테스트 개선으로 환류한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 컴포넌트가 해결하는 사용자 과업과 필요한 의미 구조를 정의한다.
2. 콘텐츠 슬롯, 허용 값, 상태, 이벤트, 키보드·보조기술 계약을 설계한다.
3. 네이티브 요소와 공개 접근성 패턴을 기준으로 구현 책임을 나눈다.
4. 대표·극단 콘텐츠와 조합 맥락으로 문서 예제와 테스트를 만든다.
5. 자동 검사와 수동 키보드·스크린 리더·확대 테스트를 실행한다.
6. 제품 오용과 사용자 문제를 수집해 API, 가드레일, 문서를 개선한다.

## 예외·극단 상황

- 레이블이 화면에 보이지 않고 주변 문맥으로만 의미를 얻는 아이콘 행동
- 여러 언어의 문법·어순·복수형 때문에 단순 문자열 결합이 불가능한 문구
- 비동기 갱신이 잦아 라이브 알림이 과도하거나 중요한 변화가 묻힐 수 있는 화면
- 복합 위젯을 다른 복합 위젯 안에 넣어 키보드 모드와 포커스 규칙이 충돌하는 경우
- 서드파티 콘텐츠나 사용자 생성 콘텐츠가 제목·대체 텍스트·링크 품질을 좌우하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 컴포넌트에 ARIA 속성이 있으니 접근 가능하다고 본다. | 키보드 동작, 상태 갱신, 콘텐츠 책임, 조합 맥락을 함께 검증한다. |
| 모든 콘텐츠 슬롯을 자유 문자열로 둔다. | 목적·형식·길이·금지 규칙과 구조화된 속성을 정의한다. |
| 아이콘 이름을 시각 모양으로만 제공한다. | 사용자에게 수행되는 행동·결과를 나타내는 접근 가능한 이름을 요구한다. |
| 오류 메시지는 제품 팀이 알아서 작성하게 둔다. | 문제·위치·수정 방법과 오류 연결 규칙을 계약과 예제로 제공한다. |
| 개별 컴포넌트 테스트만 하고 조합을 검증하지 않는다. | 대표 화면 조합과 포커스·읽기 순서·랜드마크를 소비자 테스트한다. |

## 검증 방법

1. 문서만 받은 제품 팀이 올바른 레이블·상태·키보드 동작으로 구현하는지 사용성 테스트한다.
2. 접근성 트리에서 이름·역할·상태·관계가 의도대로 노출되고 동적 변경이 적절히 알림되는지 확인한다.
3. 긴 번역, RTL, 200% 이상 확대, 오류 다수, 비동기 변경에서 콘텐츠와 포커스가 유지되는지 점검한다.
4. 금지 조합과 필수 속성이 정적 분석·런타임 경고·테스트 중 적절한 위치에서 발견되는지 검증한다.

## 에이전트 적용 규칙

- 컴포넌트 설명에는 콘텐츠 책임과 접근성 책임의 경계를 명시한다.
- ARIA 속성만 나열하지 말고 사용자 상호작용과 상태 전이 전체를 설명한다.
- 구체적인 준수 판정은 실제 구현과 보조기술 테스트 없이 확정하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
