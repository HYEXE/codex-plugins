# 핸드오프와 인수 기준

## 한 문장 원칙

핸드오프는 정적 화면 전달이 아니라 사용자 과업, 상태 전이, 콘텐츠, 반응형·접근성 동작, 데이터·오류, 측정과 검증 기준을 제품 팀이 공동으로 이해하는 계약 과정이다.

## 적용 상황

개발자가 화면을 보고 숨은 동작을 추측하거나, 구현 후에야 빈 상태·오류·키보드·모바일 요구가 발견되거나, 픽셀 일치만 완료 기준으로 삼을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 의도 전달

치수와 색상보다 어떤 사용자 문제와 결과를 위해 결정했는지 알아야 구현 트레이드오프를 올바르게 판단할 수 있다.

### 상태 완전성

기본 화면 외에 입력, 로딩, 빈 데이터, 부분 데이터, 성공, 오류, 권한, 오프라인, 취소, 복구를 명세한다.

### 행동 가능한 기준

‘반응형이어야 함’, ‘접근 가능해야 함’이 아니라 조건·행동·기대 결과가 재현 가능한 인수 기준을 쓴다.

### 공동 작성

디자인 후 개발에 던지는 단계가 아니라 기술·콘텐츠·분석·QA와 제약을 조기에 검토하며 계약을 함께 만든다.

### 변경 추적

설계와 구현 중 결정이 바뀌면 근거, 영향, 버전, 승인 상태를 기록해 산출물 간 불일치를 줄인다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 기능마다 사용자·과업·성공 상태·비즈니스 규칙·데이터 전제·범위와 비범위를 명시한다.
- **MUST:** 모든 주요 상태의 진입 조건, 사용자 행동, 시스템 응답, 전이, 오류·취소·재시도·복구를 기술한다.
- **MUST:** 키보드, 포커스, 접근 가능한 이름·상태, 확대·재배치, 터치, 감소된 모션, 콘텐츠 극단의 인수 기준을 포함한다.
- **MUST:** 컴포넌트·토큰·콘텐츠의 출처와 버전을 연결하고 새 예외는 이유와 시스템 환류 계획을 기록한다.
- **MUST:** 각 인수 기준에 검증 방법, 테스트 환경, 책임 역할을 연결하고 구현 전 모호성을 공동 검토한다.

### SHOULD

- **SHOULD:** 대표 API·데이터 예와 실패 응답을 제공하되 특정 구현을 불필요하게 고정하지 않는다.
- **SHOULD:** 분석 이벤트와 개인정보 요구를 사용자 과업·상태 전이에 연결해 누락·과잉 수집을 줄인다.
- **SHOULD:** 프로토타입은 설명 보조로 사용하고 텍스트 기반 상태표·인수 기준을 기준 기록으로 둔다.
- **SHOULD:** 구현 중 발견된 제약과 개선을 설계·시스템 문서로 되돌리는 정기 검토를 운영한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 사용자 결과, 핵심 흐름, 제약, 위험, 시스템 의존성을 팀과 함께 정리한다.
2. 상태 모델과 콘텐츠·데이터·권한·오류 조건을 표로 만든다.
3. 반응형·접근성·성능·개인정보·측정 요구를 각 상태에 연결한다.
4. 조건-행동-기대 결과 형태의 인수 기준과 테스트 방법을 작성한다.
5. 개발·QA·콘텐츠·분석과 사전 검토해 불확실성과 구현 선택을 결정 로그에 남긴다.
6. 구현 리뷰와 사용자 검증 후 문서·컴포넌트·회귀 테스트를 갱신한다.

## 예외·극단 상황

- 백엔드 계약이 확정되지 않아 상태와 오류가 계속 바뀌는 초기 제품
- 서드파티 SDK·브라우저·운영체제가 UI와 권한 흐름을 일부 통제하는 기능
- 실시간 협업·낙관적 업데이트로 로컬과 서버 상태가 일시적으로 다른 화면
- 여러 팀이 동일 흐름의 앞뒤 단계를 소유해 단일 산출물로 전체 과업을 설명하기 어려운 경우
- 규제 문구·번역·고객별 설정이 릴리스 직전 변경될 수 있는 서비스

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 정상 상태 화면과 간격 값만 전달한다. | 상태 전이·데이터·오류·콘텐츠·접근성·반응형 계약을 함께 전달한다. |
| ‘디자인대로 구현’만 인수 기준으로 쓴다. | 사용자 행동과 관찰 가능한 결과로 기준을 작성한다. |
| 프로토타입이 모든 동작을 설명한다고 가정한다. | 텍스트 상태표와 예외·미구현 범위를 별도로 기록한다. |
| 개발 제약을 구현 단계에서 처음 논의한다. | 문제 정의와 프로토타입 단계에서 기술·데이터·성능 위험을 공동 검토한다. |
| 구현 변경이 원본 명세에 반영되지 않는다. | 결정 로그와 기준 문서를 단일 출처로 갱신하고 버전을 연결한다. |

## 검증 방법

1. 개발·QA 담당자가 명세만 보고 주요 상태와 완료 조건을 동일하게 설명하는지 확인한다.
2. 인수 기준을 자동·수동 테스트로 실행해 모호하거나 관찰 불가능한 문장을 찾아 수정한다.
3. 구현을 상태표와 비교하고 누락·추가·변경된 전이를 결정 로그와 연결한다.
4. 대표 사용자와 보조기술로 핵심 과업을 수행해 픽셀 일치 밖의 결과를 검증한다.

## 인수 기준

- [ ] 기능마다 사용자·과업·성공 상태·비즈니스 규칙·데이터 전제·범위와 비범위를 명시한다.
- [ ] 모든 주요 상태의 진입 조건, 사용자 행동, 시스템 응답, 전이, 오류·취소·재시도·복구를 기술한다.
- [ ] 키보드, 포커스, 접근 가능한 이름·상태, 확대·재배치, 터치, 감소된 모션, 콘텐츠 극단의 인수 기준을 포함한다.
- [ ] 컴포넌트·토큰·콘텐츠의 출처와 버전을 연결하고 새 예외는 이유와 시스템 환류 계획을 기록한다.
- [ ] 각 인수 기준에 검증 방법, 테스트 환경, 책임 역할을 연결하고 구현 전 모호성을 공동 검토한다.
- [ ] 개발·QA 담당자가 명세만 보고 주요 상태와 완료 조건을 동일하게 설명하는지 확인한다.
- [ ] 인수 기준을 자동·수동 테스트로 실행해 모호하거나 관찰 불가능한 문장을 찾아 수정한다.
- [ ] 구현을 상태표와 비교하고 누락·추가·변경된 전이를 결정 로그와 연결한다.

## 에이전트 적용 규칙

- 명세 요청에는 상태표와 조건-행동-결과 인수 기준을 기본 산출물로 포함한다.
- 보이지 않는 데이터·권한·오류 전제를 임의로 만들지 말고 가정으로 표시한다.
- 특정 구현 코드보다 사용자 계약과 검증 기준을 우선한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [govuk-design-system] GOV.UK Design System

- 발행·관리 주체: UK Government Digital Service
- 유형: public-design-system
- 적용 범위: 접근 가능한 스타일, 컴포넌트, 공통 서비스 패턴과 운영 경험
- 이 가이드에서의 사용: 검증된 패턴을 재사용하고 서비스 전체의 일관성을 판단할 때 사용한다.
- 원문: https://design-system.service.gov.uk/

### [uswds-accessibility] USWDS Accessibility

- 발행·관리 주체: U.S. Web Design System
- 유형: implementation-guidance
- 적용 범위: 컴포넌트 접근성, 팀 책임, 테스트와 준수 범위
- 이 가이드에서의 사용: 디자인 시스템이 접근성을 보장하는 범위와 제품 팀의 책임을 구분할 때 사용한다.
- 원문: https://designsystem.digital.gov/documentation/accessibility/

### [nng-usability-testing] Usability Testing 101

- 발행·관리 주체: Nielsen Norman Group
- 유형: research-guidance
- 적용 범위: 대표 과업, 관찰, 진행, 참가자, 결과 해석을 포함한 사용성 테스트
- 이 가이드에서의 사용: 설계안을 실제 행동으로 검증하는 연구 계획을 수립할 때 사용한다.
- 원문: https://www.nngroup.com/articles/usability-testing-101/

### [material-states] Interaction States

- 발행·관리 주체: Material Design
- 유형: product-design-system
- 적용 범위: 호버, 포커스, 누름, 드래그, 선택, 비활성 등 상호작용 상태
- 이 가이드에서의 사용: 컴포넌트 상태 모델과 시각적 피드백을 설계할 때 비교 근거로 사용한다.
- 원문: https://m3.material.io/foundations/interaction/states

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
