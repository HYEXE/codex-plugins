# 성능과 지각된 성능

## 한 문장 원칙

성능은 기술 지표와 사용자가 기다림·반응·안정성을 인식하는 경험을 함께 설계하며, 빠르게 보이게 하는 장치가 실제 지연·오류·접근성 문제를 숨겨서는 안 된다.

## 적용 상황

페이지가 측정상 빠르지만 입력 반응이 늦거나 레이아웃이 움직이거나, 긴 작업에 피드백이 없거나, 스켈레톤·낙관적 업데이트가 실제 상태를 오인하게 할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 사용자 중심 시간

로드 시간만이 아니라 첫 의미 있는 정보, 입력 반응, 시각 안정성, 과업 전체 완료와 재시도 비용을 본다.

### 즉시 피드백

행동이 접수되었음을 빠르게 알려 중복 입력과 불확실성을 줄이되 완료되지 않은 작업을 성공처럼 표시하지 않는다.

### 진실한 진행

정확한 진행률을 알 수 있으면 표시하고, 알 수 없으면 비결정적 상태를 정직하게 표현하며 멈춤과 실패를 구분한다.

### 콘텐츠 우선순위

핵심 과업에 필요한 정보와 상호작용을 먼저 제공하고 비핵심 자산과 기능은 지연·점진 로드한다.

### 포용적 성능

고성능 기기·빠른 네트워크 평균이 아니라 저사양·불안정 연결·확대·보조기술 환경의 체감과 오류 복구를 포함한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 핵심 과업의 로드, 반응, 안정성, 완료 시간을 실제 사용자·기기·네트워크 조건에서 측정한다.
- **MUST:** 사용자 행동을 즉시 확인하고 진행·완료·오류·취소·재시도 상태를 시각과 보조기술에 명확히 전달한다.
- **MUST:** 낙관적 업데이트는 실패 시 원래 상태 복구, 오류 설명, 재시도·대안 경로를 제공한다.
- **MUST:** 로딩 표시가 콘텐츠 이동, 포커스 손실, 과도한 모션, 반복 알림을 만들지 않게 한다.
- **MUST:** 현재 성능 지표와 권고 기준은 공식 문서에서 재확인하고 측정 버전·환경·필드 또는 실험실 출처를 기록한다.

### SHOULD

- **SHOULD:** 예상 시간이 의미 있게 길면 진행률·남은 단계·취소 가능성을 제공한다.
- **SHOULD:** 스켈레톤은 최종 구조를 과도하게 오인시키지 않고 감소된 모션과 스크린 리더 경험을 고려한다.
- **SHOULD:** 캐시·프리페치·점진 로딩은 개인정보, 데이터 비용, 오래된 정보, 불필요한 네트워크 사용과 균형을 맞춘다.
- **SHOULD:** 성능 예산과 회귀 경보를 공통 컴포넌트와 주요 사용자 경로의 인수 기준에 포함한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 핵심 사용자 경로와 시간 민감 단계, 실패 비용, 대표 환경을 정의한다.
2. 기술 지표와 사용자가 인식하는 반응·안정·완료 상태를 함께 계측한다.
3. 콘텐츠·기능 우선순위와 로딩·진행·낙관적 업데이트 전략을 설계한다.
4. 느린 네트워크, 저사양 기기, 오류, 오프라인, 취소, 보조기술로 상태를 검증한다.
5. 실제 사용자 필드 데이터와 사용성 관찰을 결합해 병목과 인식 차이를 찾는다.
6. 성능 예산·회귀 테스트·운영 경보를 릴리스 과정에 연결한다.

## 예외·극단 상황

- 실제 처리 시간의 변동 폭이 커 정확한 진행률을 계산하기 어려운 작업
- 백그라운드 처리 후 나중에 완료되는 내보내기·분석·생성 작업
- 오프라인 편집과 동기화 충돌로 로컬 성공과 서버 성공 시점이 다른 제품
- 사용자 행동을 미리 예측하는 프리페치가 개인정보·데이터 비용을 증가시킬 수 있는 경우
- 보조기술 사용 시 동적 콘텐츠 알림과 포커스 관리가 체감 성능을 좌우하는 화면

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 스피너만 보여주고 무엇이 진행되는지 알리지 않는다. | 작업 이름, 상태, 예상 범위, 취소·대안·오류 복구를 제공한다. |
| 클릭 즉시 성공 상태를 보여 실제 실패를 숨긴다. | 낙관적 상태임을 관리하고 실패 시 되돌림·설명·재시도를 제공한다. |
| 평균 로드 시간만 최적화한다. | 실제 사용자 분포와 느린 구간, 입력 반응, 레이아웃 안정, 과업 완료를 본다. |
| 스켈레톤 애니메이션이 계속 움직여 인지 부담을 만든다. | 필요한 범위만 사용하고 감소된 모션과 정적 대안을 제공한다. |
| 성능 개선으로 핵심 콘텐츠나 접근성 정보를 늦춘다. | 과업·의미·접근성 우선순위를 기준으로 로드 순서를 다시 설계한다. |

## 검증 방법

1. 대표 및 열악한 기기·네트워크에서 필드·실험실 지표와 과업 완료 행동을 함께 측정한다.
2. 사용자가 작업 접수, 진행, 완료, 실패, 취소 가능성을 정확히 설명하는지 사용성 테스트한다.
3. 키보드·스크린 리더·확대·감소된 모션에서 로딩 중 포커스와 알림이 안정적인지 확인한다.
4. 릴리스 전후 성능 예산과 실제 사용자 분포를 비교하고 회귀 원인과 책임 경로를 추적한다.

## 인수 기준

- [ ] 사용자 행동을 즉시 확인하고 진행·완료·오류·취소·재시도 상태를 시각과 보조기술에 명확히 전달한다.
- [ ] 낙관적 업데이트는 실패 시 원래 상태 복구, 오류 설명, 재시도·대안 경로를 제공한다.
- [ ] 로딩 표시가 콘텐츠 이동, 포커스 손실, 과도한 모션, 반복 알림을 만들지 않게 한다.

## 에이전트 적용 규칙

- 성능 제안은 현재 지표 명칭·기준을 공식 자료로 재확인하도록 표시한다.
- 스켈레톤이나 낙관적 업데이트를 만능 해법처럼 권하지 말고 오류·접근성·정직성 조건을 함께 제시한다.
- 실험실 수치만으로 실제 사용자 체감이 개선됐다고 단정하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.

> **최신성 주의:** 이 가이드는 시간에 따라 정의·도구·권고가 바뀔 수 있는 내용을 포함한다. 현재 공식 문서와 운영 데이터를 확인하지 않은 수치·기능·임계값은 미검증으로 표시한다.
