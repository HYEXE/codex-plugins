# 토큰·컴포넌트·변형·상태

## 한 문장 원칙

토큰은 의미 있는 설계 결정을, 컴포넌트는 사용자 문제와 동작 계약을, 변형은 제한된 사용 맥락을, 상태는 시간에 따른 조건을 표현하도록 계층을 분리한다.

## 적용 상황

색상·간격 값이 하드코딩되고, 컴포넌트 변형이 조합 폭발을 일으키거나, 상태와 크기·스타일 옵션이 뒤섞여 디자인과 코드가 일치하지 않을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 의미 기반 토큰

원시 값 이름보다 역할과 맥락을 표현하는 의미 토큰을 사용해야 테마·모드·브랜드 변경에서도 의도가 유지된다.

### 책임 계층

토큰은 값과 의미, 컴포넌트는 구조와 행동, 변형은 허용된 구성, 상태는 사용자·시스템 조건을 담당한다.

### 유효 조합 제한

모든 속성을 독립 옵션으로 노출하면 접근성·콘텐츠·상태 계약을 깨는 조합이 생긴다. 지원 조합을 명시한다.

### 상태 전이

기본·호버·포커스·활성·선택·비활성뿐 아니라 로딩·성공·오류와 전이 조건을 모델링한다.

### 디자인-코드 대응

이름만 같고 의미가 다른 매핑을 피하고 토큰·속성·상태·이벤트의 대응을 기계적으로 검증할 수 있게 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 토큰을 원시 값, 의미 역할, 컴포넌트 적용 계층으로 구분하고 의도와 허용 범위를 문서화한다.
- **MUST:** 컴포넌트 API에 구조, 콘텐츠 슬롯, 상태, 이벤트, 키보드 동작, 접근성 속성, 반응형 동작을 정의한다.
- **MUST:** 변형과 상태를 구분하고 지원하지 않는 조합을 설계·코드·문서에서 동일하게 제한한다.
- **MUST:** 색상·모션·크기 토큰 변경이 대비, 포커스, 터치 목표, 감소된 모션 요구를 깨지 않는지 검증한다.
- **MUST:** 파괴적 토큰·API 변경에는 버전, 영향 범위, 대체 경로, 마이그레이션 기간을 제공한다.

### SHOULD

- **SHOULD:** 의미 토큰은 시각 속성보다 사용자 역할과 상태를 반영하고 테마별 값은 별도 매핑한다.
- **SHOULD:** 컴포넌트 상태 모델을 다이어그램이나 상태표로 제공해 진입·종료·우선순위를 명확히 한다.
- **SHOULD:** 코드 생성·검사 도구보다 먼저 사람이 이해할 수 있는 명명 원칙과 소유권을 합의한다.
- **SHOULD:** 예외적 제품 요구가 반복되면 임시 속성을 늘리기보다 컴포넌트 경계와 패턴을 재검토한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 제품 전반의 반복 값·역할·컴포넌트·상태를 목록화하고 중복 의미를 찾는다.
2. 원시 값과 의미 토큰을 분리하고 명명·범위·테마 규칙을 정한다.
3. 컴포넌트의 사용자 문제, 구조, 콘텐츠, 동작, 상태 전이와 접근성 계약을 설계한다.
4. 지원 변형과 유효 조합을 제한하고 디자인·코드 표현을 매핑한다.
5. 극단 콘텐츠·테마·확대·키보드·보조기술·오류 상태로 계약을 검증한다.
6. 버전·사용 데이터·예외 요청을 바탕으로 API와 토큰을 진화시킨다.

## 예외·극단 상황

- 사용자 생성 테마나 고객별 화이트라벨로 값 조합을 사전에 모두 알 수 없는 경우
- 웹·네이티브 플랫폼의 단위·상태·접근성 API가 서로 다른 경우
- 데이터 시각화처럼 의미 색상 수가 많고 대비·색각 요구가 복잡한 영역
- 고밀도 업무 도구와 터치 중심 소비자 화면이 같은 기반을 공유하는 경우
- 서버 상태와 낙관적 업데이트가 컴포넌트 상태를 비동기적으로 바꾸는 인터페이스

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 색상 값을 ‘blue-500’처럼만 노출한다. | 원시 값은 내부에 두고 텍스트·표면·행동·위험 같은 의미 역할로 매핑한다. |
| 모든 스타일 차이를 변형으로 추가한다. | 사용자 맥락과 행동 차이가 없는 시각 옵션은 토큰이나 조합 규칙으로 정리한다. |
| 비활성, 로딩, 오류가 동시에 가능한데 우선순위가 없다. | 상태 전이와 상호 배타·중첩 규칙을 명시한다. |
| 디자인과 코드의 이름만 같고 지원 상태가 다르다. | 공통 스키마와 소비자 테스트로 API 대응을 검증한다. |
| 토큰 변경을 전역 검색·치환으로 배포한다. | 의미 영향과 접근성 회귀를 검토하고 버전·마이그레이션을 제공한다. |

## 검증 방법

1. 토큰 이름만 보고 설계자가 값이 아니라 역할과 사용 금지 조건을 설명하는지 확인한다.
2. 지원 변형·상태 조합을 자동 렌더링해 시각·동작·접근성 회귀를 검사한다.
3. 디자인 속성과 코드 API를 기계적으로 비교해 누락·이름 불일치·잘못된 기본값을 찾는다.
4. 테마, 고대비, 확대, 긴 콘텐츠, RTL, 키보드, 보조기술에서 컴포넌트 계약을 검증한다.

## 인수 기준

## 에이전트 적용 규칙

- 컴포넌트 명세를 만들 때 토큰·변형·상태를 섞지 말고 계층별 책임을 나눈다.
- 가능한 모든 조합을 제안하지 말고 유효 조합과 금지 조합을 근거와 함께 제한한다.
- 기술 프레임워크의 구체 API는 저장소와 현재 버전을 확인한 뒤 작성한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [material-tokens] Design Tokens

- 발행·관리 주체: Material Design
- 유형: product-design-system
- 적용 범위: 색상·타이포그래피·형태 등 디자인 결정을 토큰으로 표현하는 방법
- 이 가이드에서의 사용: 디자인과 코드의 공통 계약 및 테마 확장 구조를 설계할 때 사용한다.
- 원문: https://m3.material.io/foundations/design-tokens

### [material-states] Interaction States

- 발행·관리 주체: Material Design
- 유형: product-design-system
- 적용 범위: 호버, 포커스, 누름, 드래그, 선택, 비활성 등 상호작용 상태
- 이 가이드에서의 사용: 컴포넌트 상태 모델과 시각적 피드백을 설계할 때 비교 근거로 사용한다.
- 원문: https://m3.material.io/foundations/interaction/states

### [fluent-layout] Layout

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 공간, 그리드, 정렬, 밀도와 반응형 레이아웃
- 이 가이드에서의 사용: 화면 위계와 다양한 뷰포트의 구조를 설계할 때 비교 근거로 사용한다.
- 원문: https://fluent2.microsoft.design/layout

### [fluent-typography] Typography

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 타입 램프, 위계, 가독성, 플랫폼 간 타이포그래피
- 이 가이드에서의 사용: 텍스트 위계와 읽기 품질을 시스템화할 때 비교 근거로 사용한다.
- 원문: https://fluent2.microsoft.design/typography

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
