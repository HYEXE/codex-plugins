# 디자인 시스템과 거버넌스

## 한 문장 원칙

디자인 시스템은 컴포넌트 모음이 아니라 반복되는 사용자 문제를 일관되고 접근 가능하게 해결하기 위한 결정, 구현, 콘텐츠, 검증, 변경 관리의 공동 제품이다.

## 적용 상황

팀마다 비슷한 컴포넌트를 다시 만들거나, 라이브러리는 있지만 사용 지침·코드·접근성·버전이 어긋나거나, 중앙 팀이 병목이 되어 제품 요구를 따라가지 못할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 공유 문제 중심

시스템화의 단위는 시각적 유사성이 아니라 여러 제품에서 반복되는 사용자 문제와 상태 모델이다.

### 단일 계약

디자인 자산, 코드, 콘텐츠, 접근성 동작, 분석 이벤트, 테스트가 같은 컴포넌트 계약을 가리켜야 한다.

### 기여와 책임

중앙 팀만 만드는 폐쇄형 모델이나 누구나 무검토로 추가하는 모델 모두 지속되기 어렵다. 기여·리뷰·소유권을 명시한다.

### 변경의 안전성

버전, 마이그레이션, 폐기, 회귀 검증 없이 시스템 변경을 배포하면 일관성이 오히려 대규모 결함을 확산한다.

### 성과와 채택

컴포넌트 수보다 중복 감소, 수정 전파 속도, 접근성 결함 감소, 채택 이유와 이탈 이유로 시스템 가치를 본다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 시스템의 목적, 지원 제품·플랫폼, 비지원 범위, 의사결정 원칙, 책임 구조를 문서화한다.
- **MUST:** 각 패턴에 사용 조건, 금지 조건, 상태·변형, 콘텐츠 규칙, 접근성 계약, 구현 예, 테스트를 제공한다.
- **MUST:** 제안·검토·승인·버전·폐기·마이그레이션 절차와 최종 결정 책임자를 정의한다.
- **MUST:** 공통 컴포넌트 변경은 영향 범위와 접근성·시각·동작·콘텐츠 회귀를 검증한 뒤 배포한다.
- **MUST:** 제품 팀이 시스템을 벗어날 수 있는 예외 조건, 기록 방법, 만료·재검토 시점을 둔다.

### SHOULD

- **SHOULD:** 디자인·개발·콘텐츠·접근성·리서치·제품 담당자가 거버넌스에 참여한다.
- **SHOULD:** 채택률만 보지 말고 미채택 이유, 우회 구현, 지원 요청, 마이그레이션 비용을 분석한다.
- **SHOULD:** 제품 팀의 실제 사례와 실패를 문서와 테스트에 반영하는 피드백 루프를 운영한다.
- **SHOULD:** 플랫폼별 네이티브 관습을 존중하면서 핵심 의미·콘텐츠·상태·접근성 계약을 공유한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 제품 전반의 반복 패턴, 중복 비용, 접근성·일관성 결함을 조사한다.
2. 시스템화할 문제와 제품별로 남길 영역을 가치·빈도·위험으로 선택한다.
3. 컴포넌트 계약, 코드·자산, 문서, 테스트, 소유자를 함께 만든다.
4. 실제 제품에서 파일럿하고 다양한 상태·콘텐츠·기기·보조기술로 검증한다.
5. 버전과 마이그레이션 계획으로 배포하고 채택·결함·지원 데이터를 모은다.
6. 기여와 피드백을 통해 패턴을 개선하거나 폐기하고 결정 기록을 보존한다.

## 예외·극단 상황

- 웹·모바일·데스크톱이 서로 다른 네이티브 패턴과 릴리스 주기를 가진 조직
- 브랜드가 여러 개이지만 계정·접근성·콘텐츠 기반은 공유하는 포트폴리오
- 레거시 제품이 시스템을 전면 도입할 수 없어 점진 마이그레이션이 필요한 경우
- 규제·고객 계약 때문에 같은 컴포넌트도 지역·고객별 변형이 필요한 경우
- 중앙 시스템 팀의 인력보다 제품 팀 수와 기여 속도가 훨씬 큰 조직

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 색상과 버튼 라이브러리만 만들고 시스템이라 부른다. | 사용 조건, 상태, 콘텐츠, 접근성, 코드, 테스트와 거버넌스를 한 계약으로 만든다. |
| 모든 제품 예외를 금지한다. | 원칙 기반 예외 절차와 피드백을 통해 시스템의 누락을 학습한다. |
| 컴포넌트를 많이 추가할수록 성공이라고 본다. | 중복 감소, 결함 감소, 수정 전파, 제품 결과와 유지 비용을 측정한다. |
| 파괴적 변경을 공지 없이 배포한다. | 버전, 변경 로그, 마이그레이션 도구, 폐기 기간과 회귀 테스트를 제공한다. |
| 디자인 자산과 코드 구현이 따로 진화한다. | 공동 소유자와 릴리스 게이트를 두고 동일한 상태·변형 계약을 검증한다. |

## 검증 방법

1. 대표 제품이 문서만으로 올바른 패턴을 선택·구현하고 예외를 설명할 수 있는지 확인한다.
2. 디자인·코드·문서의 상태·속성·접근성 동작이 같은 계약과 버전을 가리키는지 자동·수동 검사한다.
3. 변경이 여러 제품과 보조기술에서 회귀를 만들지 소비자 테스트를 실행한다.
4. 채택·미채택·지원·결함·마이그레이션 데이터를 분기별로 검토해 투자 우선순위를 조정한다.

## 에이전트 적용 규칙

- 디자인 시스템 제안에는 목적, 범위, 거버넌스, 기여, 버전, 예외, 측정까지 포함한다.
- 특정 제품 디자인 시스템의 패턴을 보편 표준처럼 복제하지 않고 비교 근거로 사용한다.
- 새 컴포넌트보다 기존 패턴 조합·개선·문서 보완 가능성을 먼저 검토한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
