# 디자인 QA와 회귀 검증

## 한 문장 원칙

디자인 QA는 출시 직전 외관 검사에 그치지 않고 사용자 과업, 상태, 콘텐츠, 접근성, 반응형, 성능을 요구사항과 실제 구현 사이에서 반복 검증하고 회귀를 자동·수동으로 방지하는 활동이다.

## 적용 상황

구현이 정적 화면과는 비슷하지만 오류·키보드·긴 콘텐츠·모바일에서 무너지거나, 같은 결함이 릴리스마다 재발하거나, 디자이너만 마지막에 수동으로 확인할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 위험 기반 범위

모든 픽셀을 동일하게 검사하지 않고 핵심 과업, 고위험 행동, 공통 컴포넌트, 접근성·성능 회귀를 우선한다.

### 상태와 환경 매트릭스

화면 한 장이 아니라 데이터·권한·오류·기기·뷰포트·입력·보조기술 조합을 관리한다.

### 자동과 수동의 조합

시각 회귀와 정적 검사는 반복 가능한 차이를 찾고, 의미·이해·키보드·보조기술·사용자 결과는 수동 검증이 필요하다.

### 재현 가능한 결함

스크린샷만 남기지 않고 환경, 경로, 현재 결과, 기대 결과, 근거, 심각도, 검증 조건을 기록한다.

### 시스템 환류

반복 결함은 개별 화면 수정에 그치지 않고 컴포넌트, 토큰, 문서, 인수 기준, 테스트와 프로세스를 고친다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 릴리스 범위에 맞는 대표 과업과 상태·환경·사용자 조건의 QA 매트릭스를 만든다.
- **MUST:** 접근성은 자동 검사 외에 키보드, 포커스, 이름·역할·상태, 스크린 리더, 확대·재배치를 수동 검증한다.
- **MUST:** 오류, 로딩, 빈·부분 데이터, 느린 네트워크, 권한 거부, 중복 제출, 취소·복구 상태를 검사한다.
- **MUST:** 결함마다 재현 단계, 환경, 증거, 기대 결과, 적용 기준, 사용자 영향, 심각도, 수정·재검증 상태를 기록한다.
- **MUST:** 공통 컴포넌트와 토큰 수정은 소비 제품의 시각·동작·접근성 회귀 테스트를 통과해야 한다.

### SHOULD

- **SHOULD:** 시각 회귀 기준 이미지는 승인된 상태·콘텐츠·뷰포트별로 관리하고 의도적 변경을 리뷰한다.
- **SHOULD:** 실제 또는 현실적인 데이터 길이·누락·특수문자·RTL·번역으로 콘텐츠 견고성을 검사한다.
- **SHOULD:** 성능과 사용자 체감은 개발 환경만이 아니라 대표 기기·네트워크와 실제 사용자 필드 데이터로 확인한다.
- **SHOULD:** 발견된 결함의 원인을 명세 누락, 컴포넌트 결함, 구현 편차, 콘텐츠, 데이터, 테스트 공백으로 분류한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 변경 영향, 사용자 위해, 공통성으로 QA 우선순위와 매트릭스를 정의한다.
2. 인수 기준과 디자인 시스템 계약을 자동·수동 테스트 케이스로 변환한다.
3. 대표 환경에서 핵심 경로와 예외 상태를 수행하고 증거를 수집한다.
4. 결함을 심각도와 시스템 원인으로 분류해 수정 책임과 출시 게이트를 정한다.
5. 수정 후 직접 경로와 인접 회귀 경로를 재검증한다.
6. 반복 결함을 컴포넌트·문서·테스트·프로세스에 반영하고 품질 추세를 검토한다.

## 예외·극단 상황

- 동일 UI가 브라우저·운영체제·글꼴 렌더링에 따라 미세하게 달라 시각 비교 노이즈가 큰 경우
- 개인화·권한·실험으로 상태 조합이 너무 많아 전수 검사가 불가능한 제품
- 실시간·비동기 데이터로 기준 이미지가 결정적이지 않은 화면
- 외부 위젯·결제·인증 제공자가 핵심 흐름 일부를 소유하는 경우
- 접근성 트리와 보조기술 동작이 플랫폼·버전별로 달라 호환성 범위를 명시해야 하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 출시 직전에 외관만 비교한다. | 개발 중 상태·접근성·반응형·콘텐츠·성능 검증을 지속하고 출시 게이트와 연결한다. |
| 자동 검사 통과를 완전한 품질로 본다. | 수동 상호작용, 보조기술, 사용자 이해와 실제 과업을 검증한다. |
| 모든 시각 차이를 결함으로 막는다. | 사용자 영향과 의도된 플랫폼 차이를 구분하고 기준을 갱신한다. |
| 결함을 채팅 메시지로만 전달한다. | 재현 조건·근거·심각도·재검증 상태가 있는 추적 가능한 기록을 만든다. |
| 반복 결함을 화면마다 고친다. | 공통 컴포넌트·토큰·명세·테스트의 시스템 원인을 수정한다. |

## 검증 방법

1. QA 매트릭스가 실제 사용자·기기·상태·보조기술 위험을 포괄하는지 제품·개발·QA가 공동 검토한다.
2. 자동 테스트가 의도적으로 삽입한 대표 결함을 탐지하는지 테스트 자체를 검증한다.
3. 수정된 이슈를 원래 재현 환경과 인접 경로에서 다시 수행해 회귀를 확인한다.
4. 출시 후 지원·분석·성능·접근성 데이터에서 QA가 놓친 패턴을 찾아 매트릭스와 테스트를 갱신한다.

## 인수 기준

- [ ] 릴리스 범위에 맞는 대표 과업과 상태·환경·사용자 조건의 QA 매트릭스를 만든다.
- [ ] 접근성은 자동 검사 외에 키보드, 포커스, 이름·역할·상태, 스크린 리더, 확대·재배치를 수동 검증한다.
- [ ] 오류, 로딩, 빈·부분 데이터, 느린 네트워크, 권한 거부, 중복 제출, 취소·복구 상태를 검사한다.
- [ ] 결함마다 재현 단계, 환경, 증거, 기대 결과, 적용 기준, 사용자 영향, 심각도, 수정·재검증 상태를 기록한다.
- [ ] 공통 컴포넌트와 토큰 수정은 소비 제품의 시각·동작·접근성 회귀 테스트를 통과해야 한다.
- [ ] QA 매트릭스가 실제 사용자·기기·상태·보조기술 위험을 포괄하는지 제품·개발·QA가 공동 검토한다.
- [ ] 자동 테스트가 의도적으로 삽입한 대표 결함을 탐지하는지 테스트 자체를 검증한다.
- [ ] 수정된 이슈를 원래 재현 환경과 인접 경로에서 다시 수행해 회귀를 확인한다.

## 에이전트 적용 규칙

- QA 계획은 화면 목록이 아니라 과업·상태·환경·위험 매트릭스로 작성한다.
- 정적 이미지 비교만으로 키보드·스크린 리더·성능·동적 상태가 통과했다고 판단하지 않는다.
- 결함 보고에는 수정 제안과 재검증 절차까지 포함한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [webdev-vitals] Web Vitals

- 발행·관리 주체: web.dev
- 유형: performance-guidance
- 적용 범위: 로딩, 상호작용 응답성, 시각적 안정성 등 사용자 중심 웹 성능 지표
- 이 가이드에서의 사용: 현재 지표명·임계값은 최신 원문을 확인하고, 현장 데이터와 실제 과업 지표를 함께 사용한다.
- 원문: https://web.dev/articles/vitals

### [govuk-design-system] GOV.UK Design System

- 발행·관리 주체: UK Government Digital Service
- 유형: public-design-system
- 적용 범위: 접근 가능한 스타일, 컴포넌트, 공통 서비스 패턴과 운영 경험
- 이 가이드에서의 사용: 검증된 패턴을 재사용하고 서비스 전체의 일관성을 판단할 때 사용한다.
- 원문: https://design-system.service.gov.uk/

### [uswds-accessibility] USWDS Accessibility

- 발행·관리 주체: U.S. Web Design System
- 유형: implementation-guidance
- 적용 범위: 컴포넌트 접근성, 팀 책임, 테스트와 준수 범위
- 이 가이드에서의 사용: 디자인 시스템이 접근성을 보장하는 범위와 제품 팀의 책임을 구분할 때 사용한다.
- 원문: https://designsystem.digital.gov/documentation/accessibility/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
