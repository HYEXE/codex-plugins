# 버튼과 행동 위계

## 한 문장 원칙

버튼은 결과가 있는 행동에 사용하고, 한 맥락에서 사용자의 주요 목표·보조 행동·위험 행동을 의미와 상태로 명확히 구분한다.

## 적용 상황

모든 행동이 같은 강조를 받거나 링크와 버튼이 의미 없이 섞이고, 비활성·로딩·성공·오류 상태가 빠지며, 버튼 문구가 실제 결과를 설명하지 못할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 행동과 이동 구분

상태를 변경하거나 작업을 실행하면 버튼, 다른 위치나 문서로 이동하면 링크를 기본으로 사용한다.

### 맥락적 우선순위

주요 버튼은 페이지마다 하나라는 기계적 규칙보다 현재 결정에서 가장 중요한 행동이 무엇인지로 판단한다.

### 상태의 완전성

기본, 호버, 포커스, 누름, 비활성뿐 아니라 처리 중, 성공, 오류, 선택, 권한 제한을 과업에 맞게 설계한다.

### 결과 중심 문구

‘확인’, ‘계속’보다 저장·전송·결제·삭제처럼 실행 결과를 구체적으로 말한다.

### 입력 방식 독립

포인터 호버에만 정보를 두지 않고 키보드·터치·음성·보조기술에서 동일한 행동과 상태를 사용할 수 있게 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 버튼별 행동 결과, 데이터 변경, 가역성, 권한, 중복 실행 규칙을 정의한다.
- **MUST:** 키보드 포커스와 누름 상태를 명확히 구분하고 포커스 표시를 제거하지 않는다.
- **MUST:** 처리 중에는 접수 여부와 중복 실행 가능성을 표시하고 작업이 끝나면 성공·오류 상태를 닫는다.
- **MUST:** 비활성 버튼만 보여주지 말고 사용 불가 이유와 활성화 조건을 가까이 제공하거나 가능한 행동을 유지한다.
- **MUST:** 아이콘 전용 버튼은 접근 가능한 이름, 충분한 목표 크기, 상태 설명을 제공한다.

### SHOULD

- **SHOULD:** 주요·보조·저강조·위험 행동의 시각 스타일 수를 제한하고 의미를 시스템 전체에서 일관되게 사용한다.
- **SHOULD:** 한 영역의 여러 주요 행동이 경쟁하면 과업 흐름, 기본값, 순차 공개를 재검토한다.
- **SHOULD:** 버튼 문구와 접근 가능한 이름이 시각 레이블과 크게 달라 음성 사용자를 혼란시키지 않게 한다.
- **SHOULD:** 긴 번역, 확대, 동적 카운트, 아이콘 유무에도 레이아웃과 클릭 영역을 유지한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 화면의 모든 행동을 이동·상태 변경·선택·위험 행동으로 분류한다.
2. 사용자 목표와 결과를 기준으로 행동 위계와 문구를 정한다.
3. 상태, 이벤트, 중복 실행, 권한, 로딩·성공·오류 전환을 표로 작성한다.
4. 키보드·터치·음성·스크린 리더의 이름과 목표 영역을 명세한다.
5. 대표·극단 콘텐츠와 느린 응답에서 실제 과업을 테스트한다.
6. 오클릭, 반복 클릭, 비활성 체류, 취소·복구 데이터를 모니터링한다.

## 예외·극단 상황

- 저장과 다음 단계 이동을 동시에 수행하는 복합 행동
- 여러 행에 반복되는 데이터 테이블의 행별 행동
- 버튼 클릭 후 외부 앱이나 시스템으로 전환되는 행동
- 접근 권한을 요청하거나 관리자의 승인이 필요한 행동
- 파괴적 행동과 안전한 대안이 같은 영역에 있는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 링크처럼 보이는 버튼과 버튼처럼 보이는 링크를 혼용한다. | 행동과 이동의 의미에 맞는 요소와 일관된 표현을 사용한다. |
| 처리 중 버튼을 비활성화만 해 상태를 알 수 없다. | 접수·처리 중 문구와 진행 피드백, 중복 실행 규칙을 제공한다. |
| 비활성 버튼에 이유가 없다. | 가능하면 활성 상태에서 검증하고, 비활성이라면 조건과 해결 방법을 설명한다. |
| 아이콘만으로 파괴적 행동을 표시한다. | 명확한 이름, 필요 시 텍스트 레이블과 위험 확인을 제공한다. |
| 주요 버튼을 색상만으로 구분한다. | 위치, 형태, 레이블, 문맥과 의미 구조를 함께 사용한다. |

## 검증 방법

1. 레이블만 보고 각 버튼의 결과와 위험을 사용자가 예측하는지 확인한다.
2. Tab·Enter·Space·터치·음성으로 모든 상태와 행동을 검증한다.
3. 느린 응답과 중복 클릭에서 작업이 한 번만 처리되고 상태가 닫히는지 테스트한다.
4. 200% 이상 확대와 긴 번역에서 레이블·포커스·목표 영역이 유지되는지 확인한다.

## 인수 기준

- [ ] 버튼별 행동 결과, 데이터 변경, 가역성, 권한, 중복 실행 규칙을 정의한다.
- [ ] 키보드 포커스와 누름 상태를 명확히 구분하고 포커스 표시를 제거하지 않는다.
- [ ] 처리 중에는 접수 여부와 중복 실행 가능성을 표시하고 작업이 끝나면 성공·오류 상태를 닫는다.
- [ ] 비활성 버튼만 보여주지 말고 사용 불가 이유와 활성화 조건을 가까이 제공하거나 가능한 행동을 유지한다.
- [ ] 아이콘 전용 버튼은 접근 가능한 이름, 충분한 목표 크기, 상태 설명을 제공한다.
- [ ] 레이블만 보고 각 버튼의 결과와 위험을 사용자가 예측하는지 확인한다.
- [ ] Tab·Enter·Space·터치·음성으로 모든 상태와 행동을 검증한다.
- [ ] 느린 응답과 중복 클릭에서 작업이 한 번만 처리되고 상태가 닫히는지 테스트한다.

## 에이전트 적용 규칙

- 버튼 명세에는 스타일 이름보다 의미, 결과, 상태, 이벤트, 접근 가능한 이름을 포함한다.
- 기본·호버만 제안하지 말고 포커스·누름·처리·성공·오류·비활성 조건을 포함한다.
- 비활성화를 유일한 오류 예방 수단으로 사용하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [material-states] Interaction States

- 발행·관리 주체: Material Design
- 유형: product-design-system
- 적용 범위: 호버, 포커스, 누름, 드래그, 선택, 비활성 등 상호작용 상태
- 이 가이드에서의 사용: 컴포넌트 상태 모델과 시각적 피드백을 설계할 때 비교 근거로 사용한다.
- 원문: https://m3.material.io/foundations/interaction/states

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [govuk-content-design] Understand Content Design

- 발행·관리 주체: UK Government Digital Service
- 유형: content-guidance
- 적용 범위: 사용자 필요에서 시작하는 명확하고 과업 중심적인 콘텐츠 설계
- 이 가이드에서의 사용: 콘텐츠의 양·형식·위치와 유지관리 기준을 설계할 때 사용한다.
- 원문: https://www.gov.uk/guidance/content-design/what-is-content-design

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
