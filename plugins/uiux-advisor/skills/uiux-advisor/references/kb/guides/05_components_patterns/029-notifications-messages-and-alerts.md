# 알림·메시지·경고

## 한 문장 원칙

메시지의 긴급성, 지속성, 행동 필요성, 범위에 따라 인라인·배너·토스트·알림함·외부 알림을 선택하고 사용자의 주의를 과도하게 빼앗지 않는다.

## 적용 상황

모든 성공·오류를 토스트로 표시해 놓치거나, 배너가 항상 긴급해 보이고, 이메일·푸시가 중복되며, 스크린 리더에 상태 변화가 지나치게 많이 발표될 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 범위와 위치

필드·컴포넌트·페이지·계정·서비스 수준 메시지는 관련 범위 가까이에 표시해야 한다.

### 지속성과 복구

읽고 행동해야 하거나 법적·재정적 결과가 있는 메시지는 자동으로 사라지지 않아야 한다.

### 긴급성 절제

경고 색·아이콘·라이브 알림은 실제 위험과 즉시 행동 필요에 비례해야 한다.

### 채널 일관성

인앱, 이메일, 푸시, SMS의 목적과 중복·빈도·설정·기록을 조정한다.

### 접근 가능한 발표

상태 변화는 적절한 라이브 영역과 포커스 정책으로 알리되 반복·사소한 업데이트로 사용을 방해하지 않는다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 메시지별 범위, 심각도, 지속 시간, 필요한 행동, 재발 조건, 기록·채널을 정의한다.
- **MUST:** 중요 오류·경고·완료 결과를 자동 소멸 토스트에만 의존하지 않는다.
- **MUST:** 메시지는 발생 원인, 영향, 필요한 행동과 기한을 구체적으로 설명한다.
- **MUST:** 색상·아이콘뿐 아니라 텍스트와 의미 구조로 심각도와 상태를 전달한다.
- **MUST:** 스크린 리더 발표 우선순위와 빈도를 통제하고 포커스를 임의로 빼앗지 않는다.

### SHOULD

- **SHOULD:** 성공 메시지는 필요한 경우 결과 위치와 연결하고 사소한 성공을 과도하게 알리지 않는다.
- **SHOULD:** 서비스 수준 배너에는 시작·종료 시점, 영향 범위, 대안, 최신 업데이트를 제공한다.
- **SHOULD:** 외부 알림에는 민감 정보를 최소화하고 앱에서 안전하게 상세를 확인하게 한다.
- **SHOULD:** 알림 설정은 주제·채널·빈도·필수 운영 알림을 이해 가능하게 구분한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 메시지 이벤트를 범위·심각도·행동 필요·지속성·채널로 분류한다.
2. 인라인·페이지 알림·배너·토스트·알림함·외부 채널을 매핑한다.
3. 문구, 행동, 닫기, 재발, 기록, 접근성 발표를 상태별로 명세한다.
4. 중복·연속·오프라인·다중 기기·알림 설정 시나리오를 설계한다.
5. 실제 과업에서 발견·이해·행동·방해 정도를 테스트한다.
6. 닫기, 무시, 행동, 알림 해제, 지원 문의 데이터를 통해 우선순위를 조정한다.

## 예외·극단 상황

- 사용자가 즉시 행동해야 하는 보안·결제·안전 경고
- 서비스 장애가 일부 지역·기능·사용자에게만 영향을 주는 경우
- 여러 백그라운드 작업이 동시에 완료되는 경우
- 푸시 권한이 없거나 외부 알림 채널이 실패하는 경우
- 관리자가 조직 전체 알림을 강제하지만 개인 채널 선호도 있는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 오류를 3초 토스트로만 보여준다. | 오류 위치와 지속 메시지, 복구 행동, 기록을 제공한다. |
| 모든 메시지를 빨간 배너로 표시한다. | 심각도와 행동 필요성에 맞춰 표현과 위치를 구분한다. |
| 성공할 때마다 화면 읽기에 라이브 발표한다. | 과업에 중요한 상태만 적절한 우선순위로 알린다. |
| 같은 사건을 이메일·푸시·인앱으로 반복 전송한다. | 채널 목적, 우선순위, 설정과 중복 억제를 설계한다. |
| 닫은 배너가 매 페이지 다시 나타난다. | 재발 조건, 사용자 확인, 중요 변경 시점과 만료를 정의한다. |

## 검증 방법

1. 메시지 유형별로 사용자가 원인·영향·행동을 정확히 설명하는지 확인한다.
2. 키보드·스크린 리더에서 메시지 발견, 링크 이동, 닫기, 포커스 유지가 가능한지 검증한다.
3. 여러 메시지가 동시에 발생했을 때 우선순위와 중복 억제가 작동하는지 테스트한다.
4. 외부 알림을 놓치거나 차단한 사용자도 앱에서 결과와 기록을 찾을 수 있는지 확인한다.

## 인수 기준

- [ ] 메시지별 범위, 심각도, 지속 시간, 필요한 행동, 재발 조건, 기록·채널을 정의한다.
- [ ] 중요 오류·경고·완료 결과를 자동 소멸 토스트에만 의존하지 않는다.
- [ ] 메시지는 발생 원인, 영향, 필요한 행동과 기한을 구체적으로 설명한다.
- [ ] 색상·아이콘뿐 아니라 텍스트와 의미 구조로 심각도와 상태를 전달한다.
- [ ] 스크린 리더 발표 우선순위와 빈도를 통제하고 포커스를 임의로 빼앗지 않는다.
- [ ] 메시지 유형별로 사용자가 원인·영향·행동을 정확히 설명하는지 확인한다.
- [ ] 키보드·스크린 리더에서 메시지 발견, 링크 이동, 닫기, 포커스 유지가 가능한지 검증한다.
- [ ] 여러 메시지가 동시에 발생했을 때 우선순위와 중복 억제가 작동하는지 테스트한다.

## 에이전트 적용 규칙

- 메시지 패턴을 추천할 때 범위·긴급성·지속성·행동 필요성을 먼저 분류한다.
- 토스트를 모든 피드백의 기본값으로 제안하지 않는다.
- 라이브 영역 사용은 구현 검증 없이 접근 가능하다고 단정하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [govuk-error-message] Error Message Component

- 발행·관리 주체: GOV.UK Design System
- 유형: component-guidance
- 적용 범위: 필드 오류의 위치, 문구, 시각적 표현과 복구 안내
- 이 가이드에서의 사용: 사용자 입력 오류를 구체적이고 복구 가능하게 전달할 때 사용한다.
- 원문: https://design-system.service.gov.uk/components/error-message/

### [nng-heuristics] 10 Usability Heuristics for User Interface Design

- 발행·관리 주체: Nielsen Norman Group
- 유형: evaluation-framework
- 적용 범위: 시스템 상태, 현실 세계 대응, 통제, 일관성, 오류 방지, 인식, 유연성, 최소성, 복구, 도움말
- 이 가이드에서의 사용: 휴리스틱 리뷰의 관찰 틀로 사용하되 실제 사용자 연구를 대체하지 않는다.
- 원문: https://www.nngroup.com/articles/ten-usability-heuristics/

### [carbon-loading] Loading Pattern

- 발행·관리 주체: Carbon Design System
- 유형: interaction-pattern
- 적용 범위: 로딩 상태의 종류, 범위, 진행 표시와 콘텐츠 안정성
- 이 가이드에서의 사용: 대기 경험의 상태 모델을 비교할 때 사용하며 제품별 성능 목표는 별도 측정한다.
- 원문: https://v10.carbondesignsystem.com/patterns/loading-pattern/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
