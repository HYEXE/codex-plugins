# 내비게이션 패턴

## 한 문장 원칙

내비게이션 형태는 화면 크기가 아니라 목적지 수, 계층, 이동 빈도, 현재 위치, 사용자 역할과 과업 연속성에 맞춰 선택한다.

## 적용 상황

탭·사이드바·상단 메뉴·하단 내비게이션·브레드크럼이 중복되거나 모바일에서 메뉴가 숨겨져 위치를 잃고, 키보드와 뒤로 가기 동작이 일관되지 않을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 목적지와 보기 전환 구분

사이트·앱의 다른 위치로 이동하는 내비게이션과 같은 데이터의 보기·상태를 바꾸는 탭을 구분한다.

### 현재 위치

선택 항목, 제목, URL, 브레드크럼, 페이지 내용이 같은 위치 모델을 전달해야 한다.

### 빈도와 우선순위

빈번하고 핵심적인 목적지는 지속적으로 보이고, 드문 관리·보조 목적지는 낮은 위계로 둔다.

### 반응형 연속성

표현이 사이드바에서 메뉴로 바뀌어도 정보 구조, 레이블, 선택 상태, 순서는 가능한 한 유지한다.

### 표준 상호작용

키보드, 포커스, 펼침, 닫기, 뒤로 가기, 깊은 링크가 패턴에 맞게 예측 가능해야 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 각 내비게이션 요소의 범위, 계층, 목적지, 현재 위치 표현, URL·히스토리 동작을 정의한다.
- **MUST:** 동일 목적지를 여러 레이블로 중복 제공하거나 서로 다른 목적지를 같은 레이블로 표현하지 않는다.
- **MUST:** 펼침 메뉴와 내비게이션 영역을 키보드로 열고 이동하고 닫을 수 있게 하며 포커스를 관리한다.
- **MUST:** 모바일 전환 후에도 핵심 목적지와 현재 위치를 발견 가능하게 유지한다.
- **MUST:** 권한으로 숨겨진 목적지와 접근 시 거부되는 목적지의 정책을 일관되게 한다.

### SHOULD

- **SHOULD:** 브레드크럼은 계층형 위치를 나타낼 때 사용하고 단순 방문 기록처럼 만들지 않는다.
- **SHOULD:** 하단 내비게이션은 소수의 동등한 최상위 목적지에 사용하고 임시 행동을 섞지 않는다.
- **SHOULD:** 탭은 같은 맥락의 병렬 보기에 사용하고 각 탭의 상태·URL·로딩을 명확히 한다.
- **SHOULD:** 새 목적지 추가는 기존 분류와 우선순위를 재검토하는 거버넌스 절차를 거친다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 목적지 목록을 사용자 과업·빈도·계층·역할별로 정리한다.
2. 내비게이션과 보기 전환, 행동, 필터를 분리한다.
3. 상단·사이드·탭·하단·브레드크럼 후보를 구조와 기기 맥락에 맞게 비교한다.
4. 현재·호버·포커스·펼침·비활성·권한·긴 레이블 상태를 명세한다.
5. 트리 테스트와 실제 프로토타입에서 찾기·이동·복귀를 검증한다.
6. 내비게이션 반복, 뒤로 가기, 검색 전환, 이탈 데이터를 통해 구조를 개선한다.

## 예외·극단 상황

- 여러 조직·프로젝트·워크스페이스를 전환하는 다중 컨텍스트 제품
- 관리자와 일반 사용자의 목적지 구조가 크게 다른 경우
- 깊은 계층과 자주 쓰는 교차 링크가 동시에 필요한 정보 제품
- 웹과 네이티브 앱에서 플랫폼 관습과 공통 정보구조가 충돌하는 경우
- 오프라인·로그아웃 상태에서 일부 목적지만 사용 가능한 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 모바일에서 모든 목적지를 햄버거 메뉴에 숨긴다. | 핵심 과업의 지속 노출과 우선순위를 유지하고 나머지를 계층화한다. |
| 탭 클릭이 완전히 다른 페이지로 이동한다. | 동일 맥락의 보기인지 목적지 이동인지 구분해 적절한 패턴을 사용한다. |
| 현재 위치를 색상만으로 표시한다. | 선택 상태, 의미 속성, 제목·URL·문맥을 함께 맞춘다. |
| 드롭다운 메뉴가 포인터 호버로만 열린다. | 클릭·키보드 조작과 닫기·포커스 규칙을 제공한다. |
| 새 기능마다 최상위 메뉴를 추가한다. | 사용자 과업과 구조 원칙에 따라 통합·재분류하고 거버넌스를 적용한다. |

## 검증 방법

1. 대표 목적지를 레이블과 구조만으로 찾는 트리 테스트를 수행한다.
2. 키보드와 스크린 리더로 내비게이션 랜드마크, 현재 항목, 펼침 상태, 포커스 순서를 검증한다.
3. 브라우저 뒤로·앞으로, 깊은 링크, 새로고침, 새 탭에서 상태가 일관되는지 확인한다.
4. 모바일·확대·긴 번역에서 핵심 목적지와 현재 위치가 유지되는지 테스트한다.

## 인수 기준

- [ ] 각 내비게이션 요소의 범위, 계층, 목적지, 현재 위치 표현, URL·히스토리 동작을 정의한다.
- [ ] 동일 목적지를 여러 레이블로 중복 제공하거나 서로 다른 목적지를 같은 레이블로 표현하지 않는다.
- [ ] 펼침 메뉴와 내비게이션 영역을 키보드로 열고 이동하고 닫을 수 있게 하며 포커스를 관리한다.
- [ ] 모바일 전환 후에도 핵심 목적지와 현재 위치를 발견 가능하게 유지한다.
- [ ] 권한으로 숨겨진 목적지와 접근 시 거부되는 목적지의 정책을 일관되게 한다.
- [ ] 대표 목적지를 레이블과 구조만으로 찾는 트리 테스트를 수행한다.
- [ ] 키보드와 스크린 리더로 내비게이션 랜드마크, 현재 항목, 펼침 상태, 포커스 순서를 검증한다.
- [ ] 브라우저 뒤로·앞으로, 깊은 링크, 새로고침, 새 탭에서 상태가 일관되는지 확인한다.

## 에이전트 적용 규칙

- 내비게이션 패턴을 추천할 때 목적지 수만이 아니라 계층, 빈도, 현재 위치, 히스토리, 역할을 설명한다.
- 플랫폼 관습을 최신 공식 지침 없이 절대 규칙으로 단정하지 않는다.
- 탭, 필터, 버튼, 링크의 의미를 혼용하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
