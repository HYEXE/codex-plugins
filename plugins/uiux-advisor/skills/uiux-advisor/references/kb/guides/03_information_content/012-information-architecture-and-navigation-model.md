# 정보구조와 내비게이션 모델

## 한 문장 원칙

조직의 부서·기능 구조가 아니라 사용자의 목표, 언어, 예상 경로와 정보 관계를 기준으로 콘텐츠와 기능을 구조화한다.

## 적용 상황

메뉴가 내부 조직도처럼 구성되거나 사용자가 어디에 있는지, 어디서 과업을 시작해야 하는지, 유사 항목의 차이를 이해하지 못할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 사용자 목표 중심

항목 이름과 그룹은 내부 소유자가 아니라 사용자가 하려는 일과 찾는 정보에 맞춘다.

### 위치와 범위의 가시성

현재 위치, 상위 구조, 가능한 다음 경로, 뒤로 갔을 때의 상태가 예측 가능해야 한다.

### 분류의 상호배타성과 중첩

현실의 정보는 완전히 상호배타적이지 않을 수 있으므로 중복 경로, 관련 링크, 검색을 의도적으로 설계한다.

### 깊이보다 인지 부담

무조건 얕은 구조보다 각 단계의 선택 수, 레이블 명확성, 맥락 유지가 더 중요하다.

### 변화 가능한 구조

콘텐츠·제품이 늘어날 때 분류 규칙과 거버넌스가 확장되는지 확인한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 핵심 사용자 과업과 사용자가 사용하는 용어를 기반으로 상위 범주와 레이블을 정의한다.
- **MUST:** 각 항목의 포함·제외 기준과 다른 항목과의 차이를 문서화한다.
- **MUST:** 현재 위치, 선택 상태, 상위·하위 관계가 시각과 의미 구조 모두에서 드러나게 한다.
- **MUST:** 브라우저 뒤로 가기, 깊은 링크, 새로고침, 권한 차이에서 위치와 상태를 보존한다.
- **MUST:** 검색·관련 링크·교차 진입을 포함해 한 경로 실패가 과업 실패로 이어지지 않게 한다.

### SHOULD

- **SHOULD:** 카드 분류, 트리 테스트, 검색어, 지원 문의로 구조와 레이블을 검증한다.
- **SHOULD:** 메뉴 항목 수를 임의 숫자로 제한하기보다 의미 있는 그룹과 우선순위를 만든다.
- **SHOULD:** 모바일·데스크톱에서 구조 의미는 유지하되 표현 방식은 기기 제약에 맞춘다.
- **SHOULD:** 중복·고아·낡은 콘텐츠를 찾는 콘텐츠 인벤토리와 소유자 체계를 운영한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 핵심 과업, 콘텐츠 유형, 사용자 용어, 현재 탐색 문제를 수집한다.
2. 콘텐츠 인벤토리에서 중복·누락·관계·권한·수명주기를 표시한다.
3. 분류 원칙과 여러 구조 후보를 만들고 대표 과업 경로를 연결한다.
4. 레이블과 트리 구조를 실제 사용자에게 독립적으로 테스트한다.
5. 내비게이션 상태, 깊은 링크, 검색, 권한, 오류·빈 상태를 명세한다.
6. 분석과 지원 데이터를 통해 실패 경로를 모니터링하고 구조를 갱신한다.

## 예외·극단 상황

- 동일 콘텐츠가 역할·산업·지역·수명주기 등 여러 축에 속하는 경우
- 로그인 전후 또는 권한별로 보이는 구조가 크게 다른 경우
- 긴급 상황에서 일반 정보구조를 건너뛰어야 하는 경우
- 사용자가 제품 용어를 모르고 문제 증상으로만 검색하는 경우
- 다국어에서 범주 경계와 레이블 길이가 달라지는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 조직 부서명을 상위 메뉴로 사용한다. | 사용자의 과업과 기대 결과를 기준으로 재분류하고 내부 소유자는 메타데이터로 둔다. |
| 메뉴를 줄이기 위해 서로 다른 항목을 모호한 ‘더보기’에 넣는다. | 의미 있는 그룹과 우선순위를 만들고 낮은 빈도 항목도 검색·관련 경로로 찾게 한다. |
| 모바일에서 데스크톱 구조를 단순히 숨긴다. | 핵심 과업 우선순위를 유지하면서 메뉴 상태와 위치 인지를 재설계한다. |
| 현재 위치가 색상만으로 표시된다. | 텍스트·상태 속성·문맥으로 선택과 위치를 중복 전달한다. |
| 구조 출시 후 검증하지 않는다. | 검색 실패, 뒤로 가기, 메뉴 반복, 지원 문의와 과업 성공을 추적한다. |

## 검증 방법

1. 트리 테스트에서 대표 과업의 첫 선택, 최종 위치, 되돌림 이유를 관찰한다.
2. 레이블만 보여주고 포함될 내용을 사용자가 예측할 수 있는지 확인한다.
3. 키보드·스크린 리더로 내비게이션의 계층, 현재 위치, 펼침 상태를 검증한다.
4. 깊은 링크·권한 없음·삭제된 콘텐츠·다국어 URL에서 회복 경로를 테스트한다.

## 에이전트 적용 규칙

- 사이트맵을 만들 때 내부 팀 구조를 그대로 복제하지 말고 과업과 사용자 언어를 우선한다.
- 항목 수만으로 좋은 정보구조를 판단하지 않는다.
- 제안에는 레이블 검증과 실패 경로 측정 방법을 포함한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
