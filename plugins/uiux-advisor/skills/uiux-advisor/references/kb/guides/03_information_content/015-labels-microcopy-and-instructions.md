# 레이블·마이크로카피·지침

## 한 문장 원칙

짧은 문구일수록 행동, 대상, 결과, 조건을 정확히 표현하고 위치와 상태에 맞게 필요한 순간에 제공한다.

## 적용 상황

버튼이 ‘확인’, ‘계속’처럼 결과를 숨기거나 필드 레이블이 예시·플레이스홀더에 의존하고, 도움말이 너무 늦거나 너무 많아 과업을 방해할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 결과를 말하는 동사

버튼과 링크는 사용자가 누른 뒤 일어날 결과를 구체적 동사와 대상으로 설명한다.

### 영구 레이블

플레이스홀더는 입력 후 사라지므로 레이블과 필수 조건을 대체하지 않는다.

### 필요 시점

사전 지침은 입력 전에, 오류는 문제 발생 후 해당 위치에서, 결과 피드백은 행동 직후 제공한다.

### 일관된 용어

같은 개념과 행동에는 같은 이름을 쓰고 사용자에게 내부 상태명이나 구현 용어를 노출하지 않는다.

### 정서적 정확성

친근함을 위해 실패를 축소하거나 사용자를 탓하지 않고 상황과 해결 방법을 차분하게 설명한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 주요 행동 문구에 대상과 실제 결과를 포함하고 취소·삭제·결제·전송을 모호하게 표현하지 않는다.
- **MUST:** 모든 입력에 지속적으로 보이는 레이블과 필요한 형식·단위·조건을 제공한다.
- **MUST:** 오류 문구는 무엇이 잘못됐는지와 어떻게 고칠지 구체적으로 설명한다.
- **MUST:** 필수·선택 여부, 개인정보 사용, 비용, 되돌리기 가능성을 결정 전에 명확히 한다.
- **MUST:** 상태·긴급성·중요도를 색상이나 아이콘만이 아니라 텍스트로도 전달한다.

### SHOULD

- **SHOULD:** 부정문과 이중 부정을 피하고 사용자가 선택하는 의미를 긍정적이고 직접적인 문장으로 쓴다.
- **SHOULD:** 도움말은 기본 과업에 필수인지 판단해 인라인, 예시, 상세 도움으로 계층화한다.
- **SHOULD:** 숫자·날짜·단위·통화는 사용자의 지역과 과업 맥락에 맞게 예시를 제공한다.
- **SHOULD:** 짧은 문구도 번역 길이, 스크린 리더 발음, 음성 명령 이름을 검토한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 사용자가 각 요소에서 알아야 할 행동·대상·조건·결과를 적는다.
2. 사용자 언어와 제품 용어집에서 일관된 명사를 선택한다.
3. 레이블, 도움말, 예시, 오류, 성공 문구를 상태 흐름으로 작성한다.
4. 모호한 ‘확인·계속·처리’와 사용자 탓 표현을 구체적 문구로 바꾼다.
5. 실제 화면 공간, 확대, 번역, 보조기술에서 문구를 검증한다.
6. 지원 문의와 오류 로그에서 오해가 반복되는 용어를 갱신한다.

## 예외·극단 상황

- 한 버튼이 저장과 다음 단계 이동을 동시에 수행하는 경우
- 작업이 즉시 실행되지 않고 검토·승인·예약 상태로 넘어가는 경우
- 공간이 매우 제한된 모바일·웨어러블·음성 인터페이스
- 사용자 이름·파일명·금액 같은 동적 값이 매우 길거나 민감한 경우
- 법적·안전상 정확한 용어와 일상 언어를 함께 제공해야 하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 버튼을 모두 ‘확인’으로 쓴다. | ‘결제하기’, ‘초대 보내기’, ‘변경사항 저장’처럼 결과를 명시한다. |
| 플레이스홀더로 레이블을 대체한다. | 입력 후에도 남는 레이블과 별도 예시를 제공한다. |
| 오류를 ‘유효하지 않습니다’로 끝낸다. | 문제 필드와 필요한 형식·범위·해결 행동을 설명한다. |
| ‘이런!’ 같은 감정 표현이 정보보다 앞선다. | 상황과 해결 방법을 먼저 전달하고 톤은 서비스 맥락에 맞춘다. |
| 툴팁에 핵심 조건을 숨긴다. | 과업 완료에 필수인 내용은 기본 화면에 노출한다. |

## 검증 방법

1. 레이블과 버튼 문구만 보고 입력·행동 결과를 예측하게 한다.
2. 오류 상태에서 사용자가 추가 도움 없이 문제를 고칠 수 있는지 관찰한다.
3. 200% 이상 확대와 긴 번역에서 잘림, 중첩, 의미 손실을 확인한다.
4. 스크린 리더의 폼 목록과 음성 명령으로 컨트롤을 식별할 수 있는지 검증한다.

## 인수 기준

- [ ] 주요 행동 문구에 대상과 실제 결과를 포함하고 취소·삭제·결제·전송을 모호하게 표현하지 않는다.
- [ ] 모든 입력에 지속적으로 보이는 레이블과 필요한 형식·단위·조건을 제공한다.
- [ ] 오류 문구는 무엇이 잘못됐는지와 어떻게 고칠지 구체적으로 설명한다.
- [ ] 필수·선택 여부, 개인정보 사용, 비용, 되돌리기 가능성을 결정 전에 명확히 한다.
- [ ] 상태·긴급성·중요도를 색상이나 아이콘만이 아니라 텍스트로도 전달한다.
- [ ] 레이블과 버튼 문구만 보고 입력·행동 결과를 예측하게 한다.
- [ ] 오류 상태에서 사용자가 추가 도움 없이 문제를 고칠 수 있는지 관찰한다.
- [ ] 200% 이상 확대와 긴 번역에서 잘림, 중첩, 의미 손실을 확인한다.

## 에이전트 적용 규칙

- 마이크로카피를 생성할 때 정상·오류·성공·비활성·대기 상태를 세트로 작성한다.
- 동적 값이나 법적 조건을 임의로 만들지 않고 자리표시자와 확인 필요 항목을 구분한다.
- 친근한 톤보다 정확성과 복구 가능성을 우선한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
