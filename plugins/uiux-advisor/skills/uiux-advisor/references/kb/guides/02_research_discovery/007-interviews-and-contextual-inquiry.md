# 인터뷰와 맥락 조사

## 한 문장 원칙

의견을 수집하기보다 최근의 실제 사례, 행동, 환경, 제약, 도구와 의사결정 과정을 구체적으로 탐색한다.

## 적용 상황

사용자의 목표·업무·문제·언어를 이해해야 하지만 직접 행동 로그만으로 이유를 알 수 없거나, 현장 도구와 사회적 맥락이 경험에 큰 영향을 줄 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 최근 사례 우선

일반적 선호보다 최근 실제 사건을 시간 순서로 재구성하면 기억 왜곡과 이상적 답변을 줄일 수 있다.

### 행동의 증거

화면 공유, 문서, 메모, 도구, 주변 사람, 우회 절차 같은 물리·디지털 증거를 함께 본다.

### 중립적 질문

해결책을 암시하거나 동의를 유도하지 않고 무엇을 했고 왜 그렇게 판단했는지 후속 질문한다.

### 맥락과 권력

조직 규칙, 역할, 승인, 성과 압박, 감정, 프라이버시가 답변과 행동을 바꿀 수 있다.

### 해석의 절제

한 사람의 발언을 보편적 필요로 만들지 않고 반복 패턴과 반례를 찾는다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 연구 목적과 다룰 수 없는 주제, 녹음·기록·데이터 사용, 중단 권리를 사전에 설명하고 동의를 받는다.
- **MUST:** ‘보통 어떻게 하세요’보다 최근 실제 사례를 시작·중간·결과 순서로 탐색한다.
- **MUST:** 제품 아이디어에 대한 칭찬이나 미래 사용 의향을 실제 수요의 증거로 사용하지 않는다.
- **MUST:** 질문자의 가정과 해석을 메모에서 참가자의 관찰·발언과 분리한다.
- **MUST:** 민감 정보가 화면·문서에 노출될 때 캡처 범위와 보관 정책을 통제한다.

### SHOULD

- **SHOULD:** 참가자가 사용하는 실제 용어와 분류 방식을 기록해 콘텐츠·정보구조에 활용한다.
- **SHOULD:** 말한 내용과 실제 행동이 다를 때 판단하지 말고 상황 차이를 탐색한다.
- **SHOULD:** 현장 조사에서는 방해하지 않는 관찰과 질문 시점을 합의한다.
- **SHOULD:** 세션 직후 관찰, 인용 요약, 가설, 반례, 후속 질문을 정리한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 결정과 학습 목표를 3~5개의 핵심 질문으로 줄인다.
2. 행동·맥락 기준으로 참가자를 모집하고 필요한 접근 지원을 준비한다.
3. 도입에서 안전·동의·역할을 설명하고 최근 실제 사례로 시작한다.
4. 시간 순서, 도구, 사람, 정보, 판단, 실패, 우회, 감정을 구체적으로 추적한다.
5. 세션별 사실·해석·질문을 분리한 뒤 참가자 간 패턴과 반례를 합성한다.
6. 결과를 문제 가설과 설계 기회로 연결하되 우선순위는 추가 근거로 검증한다.

## 예외·극단 상황

- 상사나 구매자가 동석해 참가자가 자유롭게 말하기 어려운 조직 연구
- 실패·부채·건강·차별처럼 수치심과 위험이 있는 주제
- 통역사·보호자·지원 인력이 필요한 인터뷰
- 기억하기 어려운 장기·반복 과업 또는 매우 드문 사건
- 현장 관찰이 보안·개인정보·안전 규정으로 제한되는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| ‘이 기능 쓰실 것 같나요?’를 핵심 질문으로 삼는다. | 현재 문제를 해결하기 위해 실제로 한 행동과 비용을 탐색한다. |
| 인터뷰어가 아이디어를 설명하고 설득한다. | 설명 시간을 줄이고 참가자의 경험과 언어를 수집한다. |
| 강한 인용 한 개로 결론을 만든다. | 반복 행동, 맥락, 반례, 다른 데이터와 함께 판단한다. |
| 참가자의 우회를 비효율로만 본다. | 우회가 제공하는 통제·기록·협업·안전 가치를 파악한다. |
| 노트를 주제별로만 잘라 맥락을 잃는다. | 사례의 시간 흐름과 인과 관계를 보존한 뒤 주제를 합성한다. |

## 검증 방법

1. 인터뷰 가이드에서 유도 질문과 제품 중심 질문을 동료가 표시하게 한다.
2. 파일럿에서 참가자가 최근 구체적 사례를 충분히 회상할 수 있는지 확인한다.
3. 합성 결과마다 근거가 된 사례 수와 반례를 추적한다.
4. 연구 참가자가 아니라 팀의 편견이 결론에 들어간 지점을 리플렉시브 메모로 검토한다.

## 인수 기준

- [ ] 연구 목적과 다룰 수 없는 주제, 녹음·기록·데이터 사용, 중단 권리를 사전에 설명하고 동의를 받는다.
- [ ] ‘보통 어떻게 하세요’보다 최근 실제 사례를 시작·중간·결과 순서로 탐색한다.
- [ ] 제품 아이디어에 대한 칭찬이나 미래 사용 의향을 실제 수요의 증거로 사용하지 않는다.
- [ ] 질문자의 가정과 해석을 메모에서 참가자의 관찰·발언과 분리한다.
- [ ] 민감 정보가 화면·문서에 노출될 때 캡처 범위와 보관 정책을 통제한다.
- [ ] 인터뷰 가이드에서 유도 질문과 제품 중심 질문을 동료가 표시하게 한다.
- [ ] 파일럿에서 참가자가 최근 구체적 사례를 충분히 회상할 수 있는지 확인한다.
- [ ] 합성 결과마다 근거가 된 사례 수와 반례를 추적한다.

## 에이전트 적용 규칙

- 인터뷰 질문을 생성할 때 최근 실제 행동, 구체적 사례, 후속 탐색 질문을 우선한다.
- 가상 참가자 인용을 실제 근거처럼 만들지 않는다.
- 인터뷰와 사용성 테스트를 목적과 진행 방식에서 분명히 구분한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
