# 포용적 모집과 접근성 리서치

## 한 문장 원칙

장애·언어·기기·환경·숙련도의 다양성을 표본과 연구 운영에 의도적으로 포함하고 참가에 필요한 조정을 연구 품질의 일부로 본다.

## 적용 상황

평균적인 활성 사용자만 반복 모집되거나 접근성 테스트를 체크리스트로만 수행해 실제 보조기술·상황적 제약을 이해하지 못할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 대표성보다 목적 적합성

모든 집단을 통계적으로 대표하기 어렵더라도 연구 질문과 배제 위험에 직접 관련된 경험을 의도적으로 포함한다.

### 조정의 사전 설계

통역, 캡션, 보조기술, 휴식, 동반인, 대체 입력, 비동기 참여를 참가자 개인의 요청이 아니라 연구 계획으로 준비한다.

### 장애와 환경의 상호작용

문제는 개인의 결함이 아니라 인터페이스, 정책, 환경, 도구와의 부적합에서 발생한다.

### 보조기술 숙련도

한 명의 스크린 리더 사용자가 모든 사용자를 대표하지 않으며 도구·플랫폼·숙련도 차이를 기록한다.

### 존중과 보상

추가 시간·감정 노동·접근 요구를 인정하고 공정한 보상과 안전한 참여 조건을 제공한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 연구 질문과 위험에 따라 포함해야 할 능력·언어·기기·환경·숙련도 기준을 정의한다.
- **MUST:** 모집 과정에서 필요한 조정을 안전하게 묻고 제공 가능 범위와 연락 창구를 안내한다.
- **MUST:** 참가자가 평소 사용하는 기기·보조기술·설정 사용을 기본으로 허용한다.
- **MUST:** 접근성 문제를 참가자의 실수나 낮은 숙련도로 설명하지 않고 인터페이스 조건을 분석한다.
- **MUST:** 개인 건강·장애 정보는 최소 수집하고 식별 가능성이 높은 인용·영상 공유를 통제한다.

### SHOULD

- **SHOULD:** 모집 파트너와 커뮤니티에 일회성 추출이 아닌 장기적 관계와 피드백을 제공한다.
- **SHOULD:** 연구 자료와 동의서 자체를 접근 가능한 형식으로 제공한다.
- **SHOULD:** 장애 사용자 연구를 별도 마지막 단계가 아니라 초기 문제 발견과 반복 검증에 포함한다.
- **SHOULD:** 상황적 제약과 일시적 장애도 시나리오에 포함해 기본 설계의 회복력을 본다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 제품의 핵심 과업과 배제 가능성을 능력·환경·언어·기기 축으로 점검한다.
2. 모집 기준과 조정 예산, 도구, 장소, 시간, 개인정보 절차를 준비한다.
3. 파일럿으로 연구 자료·프로토타입·회의 도구의 접근성을 확인한다.
4. 참가자의 평소 전략과 보조기술을 존중하며 실제 과업을 관찰한다.
5. 장벽을 사용자·인터페이스·정책·환경·기술 의존성으로 분해한다.
6. 발견 사항을 시스템 개선과 개별 결함 수정으로 나누고 재검증한다.

## 예외·극단 상황

- 소수 집단이라 익명성을 보장하기 어려운 조직 내부 연구
- 보조기술이 프로토타입 또는 원격 연구 도구와 호환되지 않는 경우
- 인지·언어 장애로 표준 동의 절차와 긴 세션이 부담되는 경우
- 통역·동반인이 답변에 영향을 줄 수 있는 경우
- 연구자가 해당 커뮤니티의 문화·장애 경험을 충분히 이해하지 못하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 비장애 연구자가 화면을 눈 감고 사용해 접근성을 대체한다. | 실제 장애 사용자와 보조기술 사용 경험을 포함하고 자동·전문 테스트로 보완한다. |
| 접근성 참가자를 한 명만 모집해 대표 사례로 만든다. | 과업 위험과 도구·숙련도 변이를 고려해 반복 패턴과 차이를 기록한다. |
| 연구 도구가 접근 불가능해 참가를 포기하게 한다. | 대체 채널, 접근 가능한 자료, 유연한 세션 방식과 기술 지원을 제공한다. |
| 문제를 보조기술의 한계로만 돌린다. | 의미 구조, 포커스, 상태 알림, 콘텐츠와 상호작용 설계를 먼저 검토한다. |
| 참가자의 장애 정보를 보고서에 과도하게 노출한다. | 결정에 필요한 맥락만 보존하고 재식별 위험을 줄인다. |

## 검증 방법

1. 모집 퍼널에서 초대·스크리닝·예약·참여·중단 단계별 배제율을 검토한다.
2. 연구 자료와 프로토타입을 키보드, 확대, 스크린 리더, 캡션 환경에서 파일럿한다.
3. 발견 사항이 특정 참가자 취향인지 구조적 장벽인지 여러 근거로 검토한다.
4. 수정 후 같은 보조기술·맥락에서 과업 성공과 복구를 재검증한다.

## 인수 기준

- [ ] 연구 질문과 위험에 따라 포함해야 할 능력·언어·기기·환경·숙련도 기준을 정의한다.
- [ ] 모집 과정에서 필요한 조정을 안전하게 묻고 제공 가능 범위와 연락 창구를 안내한다.
- [ ] 참가자가 평소 사용하는 기기·보조기술·설정 사용을 기본으로 허용한다.
- [ ] 접근성 문제를 참가자의 실수나 낮은 숙련도로 설명하지 않고 인터페이스 조건을 분석한다.
- [ ] 개인 건강·장애 정보는 최소 수집하고 식별 가능성이 높은 인용·영상 공유를 통제한다.
- [ ] 모집 퍼널에서 초대·스크리닝·예약·참여·중단 단계별 배제율을 검토한다.
- [ ] 연구 자료와 프로토타입을 키보드, 확대, 스크린 리더, 캡션 환경에서 파일럿한다.
- [ ] 발견 사항이 특정 참가자 취향인지 구조적 장벽인지 여러 근거로 검토한다.

## 에이전트 적용 규칙

- ‘장애인 사용자’ 하나의 세그먼트로 일반화하지 말고 과업 관련 능력·도구·환경을 구체화한다.
- 접근성 준수 체크와 실제 사용자 연구를 서로 대체 가능한 것으로 표현하지 않는다.
- 조정 요청과 민감 정보의 최소 수집 원칙을 연구 계획에 포함한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [wai-accessibility-intro] Introduction to Web Accessibility

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: foundational-guidance
- 적용 범위: 장애, 상황적 제약, 포용성, 조직적 접근성의 기본 개념
- 이 가이드에서의 사용: 접근성을 특정 사용자군의 예외가 아니라 제품 품질로 설명할 때 사용한다.
- 원문: https://www.w3.org/WAI/fundamentals/accessibility-intro/

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [spectrum-inclusive] Inclusive Design

- 발행·관리 주체: Spectrum Design System
- 유형: product-design-system
- 적용 범위: 다양한 능력, 상황, 문화권을 고려한 포용적 설계
- 이 가이드에서의 사용: 평균 사용자 가정을 깨고 배제 위험을 발견할 때 사용한다.
- 원문: https://spectrum.adobe.com/page/inclusive-design/

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

### [nng-research-methods] When to Use Which User-Experience Research Methods

- 발행·관리 주체: Nielsen Norman Group
- 유형: research-guidance
- 적용 범위: 태도·행동, 정성·정량, 맥락·통제 축에 따른 방법 선택
- 이 가이드에서의 사용: 질문에 맞는 연구 방법을 선택하고 방법 간 오용을 방지할 때 사용한다.
- 원문: https://www.nngroup.com/articles/which-ux-research-methods/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
