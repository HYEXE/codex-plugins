# UX 전략과 근거 포트폴리오

## 한 문장 원칙

UX 전략은 하나의 비전 문구가 아니라 우선할 사용자 결과, 경쟁할 경험 원칙, 투자할 역량, 검증할 가정을 연결한 선택의 체계다.

## 적용 상황

프로젝트마다 개별 화면은 개선되지만 제품 전체 경험이 일관되지 않거나, 연구·디자인 시스템·콘텐츠·접근성 투자가 로드맵과 분리되어 있을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 명시적 선택

모든 사용자·채널·문제를 동시에 최적화할 수 없으므로 무엇을 먼저 해결하고 무엇을 하지 않을지 정한다.

### 경험 원칙의 검증 가능성

‘간단하고 직관적’ 같은 일반 문구 대신 구체적 행동과 설계 트레이드오프를 결정할 수 있는 원칙을 만든다.

### 근거 포트폴리오

탐색 연구, 사용성, 분석, 접근성, 지원 데이터, 운영 지표를 서로 다른 질문에 맞게 조합한다.

### 역량과 시스템

지속적인 경험 품질은 한 번의 프로젝트보다 콘텐츠 운영, 디자인 시스템, 연구 리포지터리, 계측, QA 역량에 좌우된다.

### 학습 로드맵

기능 로드맵과 별도로 가장 위험한 가정을 언제 어떤 방법으로 줄일지 계획한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 전략 기간, 우선 사용자·과업, 목표 결과, 비우선 범위, 핵심 제약을 명시한다.
- **MUST:** 각 경험 원칙을 구체적 좋은 예·나쁜 예·트레이드오프 질문과 연결한다.
- **MUST:** 핵심 가정마다 현재 근거 수준, 위험도, 다음 검증 방법을 기록한다.
- **MUST:** 접근성·콘텐츠·성능·신뢰를 별도 후처리가 아니라 전략적 품질 속성으로 포함한다.
- **MUST:** 기능 투자가 공통 역량과 부채에 미치는 영향을 로드맵에서 추적한다.

### SHOULD

- **SHOULD:** 선행 지표, 결과 지표, 부작용 지표를 연결한 측정 지도를 만든다.
- **SHOULD:** 분기별로 근거 포트폴리오의 편향과 비어 있는 사용자군을 검토한다.
- **SHOULD:** 경험 원칙에 예외 승인 절차와 만료 시점을 둔다.
- **SHOULD:** 전략을 디자인 팀 문서가 아니라 제품·기술·운영의 공동 의사결정 문서로 운영한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 제품 목표와 사용자 결과를 분리해 현재 전략의 긴장을 파악한다.
2. 가장 큰 사용자 장벽과 경험 부채를 근거별로 정리한다.
3. 우선할 사용자·과업·품질 속성과 하지 않을 일을 선택한다.
4. 선택을 지지하는 경험 원칙과 운영 역량 투자를 정의한다.
5. 가정·지표·연구 계획을 학습 로드맵으로 연결한다.
6. 정기 검토에서 결과와 새 근거에 따라 원칙·우선순위·투자를 갱신한다.

## 예외·극단 상황

- 서로 다른 제품군이 하나의 브랜드·계정·디자인 시스템을 공유하는 포트폴리오
- 규제·보안·레거시 제약으로 이상적 흐름을 바로 구현할 수 없는 경우
- 성장 지표가 사용자의 자율성·신뢰와 충돌하는 비즈니스 모델
- 조직 개편과 담당자 변경이 잦아 장기 역량이 축적되지 않는 환경
- 국가·언어·접근성 요구가 달라 단일 경험 원칙이 충분하지 않은 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 전략을 슬로건과 무드보드로 끝낸다. | 원칙별 의사결정 규칙, 사례, 지표, 책임자를 연결한다. |
| 연구 건수나 디자인 산출물 수를 성과로 본다. | 불확실성 감소와 사용자 결과 변화로 학습 가치를 평가한다. |
| 기능 로드맵에만 예산을 배분한다. | 공통 컴포넌트, 콘텐츠 운영, 계측, 접근성 QA를 제품 역량으로 투자한다. |
| 모든 원칙을 항상 지켜야 하는 절대 규칙으로 만든다. | 원칙 간 우선순위와 트레이드오프 절차를 정의한다. |
| 과거 데이터가 미래 전략을 자동 결정한다고 본다. | 데이터의 범위와 구조적 편향을 기록하고 전략적 가설을 별도로 검증한다. |

## 검증 방법

1. 실제 로드맵 항목 3개에 전략을 적용해 선택이 달라지는지 검토한다.
2. 제품·기술·운영·지원 담당자가 같은 우선순위와 비우선 범위를 설명하는지 확인한다.
3. 근거 지도에서 특정 방법이나 사용자군에 과도하게 의존하는 영역을 찾는다.
4. 분기 말에 학습된 내용이 원칙·로드맵·시스템에 반영되었는지 추적한다.

## 인수 기준

- [ ] 전략 기간, 우선 사용자·과업, 목표 결과, 비우선 범위, 핵심 제약을 명시한다.
- [ ] 각 경험 원칙을 구체적 좋은 예·나쁜 예·트레이드오프 질문과 연결한다.
- [ ] 핵심 가정마다 현재 근거 수준, 위험도, 다음 검증 방법을 기록한다.
- [ ] 접근성·콘텐츠·성능·신뢰를 별도 후처리가 아니라 전략적 품질 속성으로 포함한다.
- [ ] 기능 투자가 공통 역량과 부채에 미치는 영향을 로드맵에서 추적한다.
- [ ] 실제 로드맵 항목 3개에 전략을 적용해 선택이 달라지는지 검토한다.
- [ ] 제품·기술·운영·지원 담당자가 같은 우선순위와 비우선 범위를 설명하는지 확인한다.
- [ ] 근거 지도에서 특정 방법이나 사용자군에 과도하게 의존하는 영역을 찾는다.

## 에이전트 적용 규칙

- 전략 문서를 요청받으면 비전 문구만 생성하지 말고 선택, 근거, 역량, 학습 로드맵을 포함한다.
- 근거가 약한 영역을 숨기지 말고 가정 레지스터로 제시한다.
- 범용 원칙은 실제 트레이드오프 사례로 구체화한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

### [govuk-design-system] GOV.UK Design System

- 발행·관리 주체: UK Government Digital Service

- 이 가이드에서의 사용: 검증된 패턴을 재사용하고 서비스 전체의 일관성을 판단할 때 사용한다.
- 원문: https://design-system.service.gov.uk/

### [nng-research-methods] When to Use Which User-Experience Research Methods

- 발행·관리 주체: Nielsen Norman Group

- 발행·관리 주체: web.dev

- 이 가이드에서의 사용: 현재 지표명·임계값은 최신 원문을 확인하고, 현장 데이터와 실제 과업 지표를 함께 사용한다.
- 원문: https://web.dev/articles/vitals

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
