# 결과 중심 디자인 의사결정

## 한 문장 원칙

화면이나 기능의 산출물이 아니라 특정 사용자가 특정 맥락에서 달성해야 할 관찰 가능한 결과를 먼저 정의한다.

## 적용 상황

로드맵에 화면·컴포넌트·기능 이름만 있고 무엇이 개선되어야 성공인지 불분명할 때 사용한다. 이해관계자마다 성공의 정의가 다르거나, 전환율 같은 단일 지표가 사용자 결과를 대체하고 있을 때도 적용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 결과와 산출물 분리

산출물은 팀이 만드는 것이고 결과는 사용자의 행동·이해·성공 상태가 달라지는 것이다. 산출물은 가설을 검증하기 위한 수단으로 취급한다.

### 관찰 가능한 성공

‘좋아한다’처럼 추상적인 표현 대신 완료, 오류 감소, 이해도, 재작업 감소, 도움 요청 감소처럼 관찰 가능한 변화를 정의한다.

### 근거 사슬

사용자 필요 → 문제 증거 → 설계 가설 → 구현 결정 → 검증 지표가 연결되어야 한다. 중간 연결이 끊기면 결정은 의견으로 남는다.

### 반증 가능성

성공 조건뿐 아니라 어떤 결과가 가설을 기각하거나 재검토하게 만드는지도 미리 정한다.

### 위해와 장기 효과

단기 클릭·체류·수익이 장기 신뢰, 오류 비용, 이탈, 취약 사용자에게 미치는 영향을 함께 본다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 대상 사용자, 맥락, 핵심 과업, 현재 기준선, 기대 변화, 검증 시점을 한 문단으로 명시한다.
- **MUST:** 성공 지표를 최소 하나의 행동 지표와 하나의 품질·위해 지표로 구성한다.
- **MUST:** 각 주요 화면·기능이 어떤 사용자 결과에 기여하는지 추적 가능하게 연결한다.
- **MUST:** 가설을 지지하지 않는 반증 신호와 중단 기준을 사전에 기록한다.
- **MUST:** 사용자에게 전가되는 시간, 비용, 개인정보, 실수 위험을 성공 정의에 포함한다.

### SHOULD

- **SHOULD:** 대안별 기대 효과, 비용, 불확실성, 되돌리기 가능성을 비교한다.
- **SHOULD:** 제품 지표와 사용성 지표를 분리해 해석하고 인과관계를 단정하지 않는다.
- **SHOULD:** 결정 로그에 근거 날짜, 책임자, 남은 가정, 다음 검증 지점을 기록한다.
- **SHOULD:** 저빈도·고위험 과업은 평균 지표보다 실패 결과와 복구 가능성을 우선한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 요청된 산출물을 사용자 행동과 맥락을 나타내는 결과 문장으로 다시 쓴다.
2. 현재 상태의 정성·정량 근거와 근거가 없는 가정을 분리한다.
3. 개선 가설과 경쟁 가설을 각각 한 문장으로 만든다.
4. 가설마다 최소 구현 대안과 비구현 대안을 포함해 비교한다.
5. 성공·위해·반증 지표와 측정 시점을 정한다.
6. 결정 후 결과를 검토하고 지식베이스와 로드맵을 갱신한다.

## 예외·극단 상황

- 여러 사용자군의 결과가 충돌하는 양면 시장이나 관리자·최종 사용자 구조
- 장기간 후에만 결과가 나타나는 학습·건강·재정 과업
- 성공 사례가 많아도 한 번의 실패 비용이 매우 큰 고위험 서비스
- 규정 준수나 조직 목표가 사용자 목표와 충돌하는 상황
- 측정 가능한 대리 지표가 실제 가치와 쉽게 어긋나는 참여·체류 지표

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| ‘대시보드 제작’처럼 산출물을 목표로 둔다. | 누가 어떤 결정을 더 빠르고 정확하게 내려야 하는지로 목표를 재작성한다. |
| 전환율 하나로 성공을 판단한다. | 완료 품질, 오류, 취소·환불, 지원 요청, 신뢰 지표를 함께 본다. |
| 성공한 데이터만 찾는다. | 반증 기준과 부작용 지표를 실험 전에 고정한다. |
| 모든 사용자에게 같은 결과를 기대한다. | 핵심 세그먼트와 배제 위험이 큰 세그먼트를 별도로 분석한다. |
| 결정 근거가 회의에만 남는다. | 근거·가정·결정·검증 시점을 구조화된 로그로 보존한다. |

## 검증 방법

1. 팀원에게 결과 문장만 보여주고 대상 사용자·행동·성공 기준을 동일하게 설명하는지 확인한다.
2. 현재 데이터로 기준선을 계산할 수 있는지, 계산 불가능하면 어떤 계측이 필요한지 검토한다.
3. 대표 사용자 과업에서 성공뿐 아니라 오류·포기·우회 행동을 관찰한다.
4. 출시 후 예정한 검증 시점에 가설 유지·수정·폐기를 결정한다.

## 인수 기준

- [ ] 대상 사용자, 맥락, 핵심 과업, 현재 기준선, 기대 변화, 검증 시점을 한 문단으로 명시한다.
- [ ] 성공 지표를 최소 하나의 행동 지표와 하나의 품질·위해 지표로 구성한다.
- [ ] 각 주요 화면·기능이 어떤 사용자 결과에 기여하는지 추적 가능하게 연결한다.
- [ ] 가설을 지지하지 않는 반증 신호와 중단 기준을 사전에 기록한다.
- [ ] 사용자에게 전가되는 시간, 비용, 개인정보, 실수 위험을 성공 정의에 포함한다.
- [ ] 팀원에게 결과 문장만 보여주고 대상 사용자·행동·성공 기준을 동일하게 설명하는지 확인한다.
- [ ] 현재 데이터로 기준선을 계산할 수 있는지, 계산 불가능하면 어떤 계측이 필요한지 검토한다.
- [ ] 대표 사용자 과업에서 성공뿐 아니라 오류·포기·우회 행동을 관찰한다.

## 에이전트 적용 규칙

- 요청이 화면 제작으로만 표현되어 있으면 사용자 결과 문장과 가정을 먼저 제시한다.
- 근거가 없는 수치 목표는 사실처럼 만들지 말고 측정 계획으로 전환한다.
- 추천안에는 반드시 반증 기준과 사용자 위해 지표를 포함한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [govuk-design-principles] Government Design Principles

- 발행·관리 주체: UK Government Digital Service
- 유형: public-service-principles
- 적용 범위: 사용자 필요, 데이터, 단순성, 반복, 포용성, 맥락, 일관성, 개방성
- 이 가이드에서의 사용: 전략·문제정의·서비스 수준의 의사결정 원칙을 구성할 때 사용한다.
- 원문: https://www.gov.uk/guidance/government-design-principles

### [govuk-user-needs] Identify User Needs

- 발행·관리 주체: UK Government Digital Service
- 유형: research-guidance
- 적용 범위: 행동과 맥락으로 사용자 필요를 정의하고 기존 근거를 활용하는 방법
- 이 가이드에서의 사용: 화면 요구가 아니라 사용자가 달성할 과업으로 문제를 재정의할 때 사용한다.
- 원문: https://www.gov.uk/guidance/content-design/user-needs

### [uswds-principles] USWDS Design Principles

- 발행·관리 주체: U.S. Web Design System
- 유형: public-service-principles
- 적용 범위: 신뢰, 연속성, 접근성, 실제 사용자 필요와 팀 운영 원칙
- 이 가이드에서의 사용: 공공성과 신뢰가 중요한 서비스의 전략·운영 품질을 평가할 때 사용한다.
- 원문: https://designsystem.digital.gov/design-principles/

### [nng-research-methods] When to Use Which User-Experience Research Methods

- 발행·관리 주체: Nielsen Norman Group
- 유형: research-guidance
- 적용 범위: 태도·행동, 정성·정량, 맥락·통제 축에 따른 방법 선택
- 이 가이드에서의 사용: 질문에 맞는 연구 방법을 선택하고 방법 간 오용을 방지할 때 사용한다.
- 원문: https://www.nngroup.com/articles/which-ux-research-methods/

### [ftc-dark-patterns] Bringing Dark Patterns to Light

- 발행·관리 주체: U.S. Federal Trade Commission
- 유형: regulatory-guidance
- 적용 범위: 선택 왜곡, 중요 정보 은폐, 무단 청구, 개인정보 선택 방해 등 기만적 패턴
- 이 가이드에서의 사용: 법률 자문이 아니라 위해·기만 위험을 식별하는 설계 기준으로 사용한다.
- 원문: https://www.ftc.gov/reports/bringing-dark-patterns-light

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
