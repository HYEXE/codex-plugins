# 인간 중심 문제 정의

## 한 문장 원칙

요청된 해결책을 그대로 받지 말고 사용자의 목표, 현재 행동, 제약, 실패 비용을 확인해 해결해야 할 문제를 재구성한다.

## 적용 상황

‘챗봇을 넣자’, ‘단계를 줄이자’, ‘앱으로 만들자’처럼 해결책이 먼저 제시되었거나 사용자 필요가 직무·인구통계 라벨로만 표현될 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 과업과 동기

사용자는 제품 기능을 사용하려는 것이 아니라 외부 세계의 목적을 달성하려고 한다. 제품 밖의 선행·후속 단계까지 본다.

### 현재 행동의 존중

우회, 수기 기록, 다른 채널 사용은 무지의 증거가 아니라 현재 시스템이 충족하지 못한 필요의 단서다.

### 맥락적 제약

시간 압박, 기기, 연결성, 언어, 능력, 권한, 감정 상태가 같은 과업의 난이도를 바꾼다.

### 문제와 증상 분리

낮은 클릭률이나 이탈은 증상일 수 있다. 원인을 정보 부족, 신뢰, 비용, 권한, 기술 실패 등으로 분해한다.

### 배제 검토

평균적인 사용자를 전제하면 가장 큰 장벽이 사라져 보인다. 극단·취약 상황을 문제 정의에 포함한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 문제 문장에 사용자 집단, 발생 맥락, 달성하려는 과업, 현재 장벽, 장벽의 결과를 포함한다.
- **MUST:** 문제 정의에 사용한 근거와 아직 검증하지 않은 가정을 구분한다.
- **MUST:** 현재 사용자가 취하는 대안·우회 경로와 그것이 유지되는 이유를 기록한다.
- **MUST:** 조직 목표와 사용자 목표가 충돌하는 지점을 명시한다.
- **MUST:** 문제 범위에서 제외하는 대상과 이유를 투명하게 기록하고 후속 검토 시점을 둔다.

### SHOULD

- **SHOULD:** 기능명과 내부 조직 용어를 제거한 상태에서도 이해되는 문제 문장을 만든다.
- **SHOULD:** 문제의 상위 원인과 하위 증상을 원인 지도 또는 가설 트리로 구분한다.
- **SHOULD:** 다양한 능력·언어·기기·연결 상태에서 문제 강도가 어떻게 달라지는지 비교한다.
- **SHOULD:** 문제가 해결되었을 때 사용자와 조직 모두에게 나타날 변화를 기술한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 요청된 해결책에서 기능명·화면명을 제거하고 사용자가 하려는 일을 적는다.
2. 기존 연구, 분석, 지원 문의, 현장 관찰에서 문제 증거를 모은다.
3. 사용자·상황·장벽·영향을 포함한 여러 문제 문장 후보를 만든다.
4. 원인과 증상을 분리하고 경쟁 설명을 나열한다.
5. 영향도, 빈도, 위해, 해결 가능성으로 우선순위를 정한다.
6. 문제 문장을 사용자·현장 담당자·팀과 검토한 뒤 가설로 확정한다.

## 예외·극단 상황

- 사용자가 서비스 이용을 원하지 않지만 법적·행정적으로 강제되는 과업
- 구매자, 관리자, 운영자, 최종 사용자의 목표가 서로 다른 B2B 제품
- 표현하기 어려운 감정·낙인·건강·재정 맥락
- 현재 행동이 비공식적이거나 규정 위반이라 직접 관찰하기 어려운 상황
- 사용자 연구 접근이 제한되어 2차 근거와 가정으로 시작해야 하는 상황

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 인구통계 페르소나를 문제의 원인으로 사용한다. | 행동, 맥락, 장벽, 숙련도와 동기를 중심으로 세분화한다. |
| 이탈을 ‘사용자가 이해하지 못함’으로 단정한다. | 가격, 신뢰, 필요성, 권한, 기술 문제 등 경쟁 원인을 조사한다. |
| 조직의 내부 프로세스를 사용자 과업으로 표현한다. | 사용자 관점의 시작·종료 상태로 과업 경계를 다시 잡는다. |
| 극단 사용자를 예외로 제외한다. | 극단 상황에서 드러난 구조적 장벽을 기본 설계 품질로 반영한다. |
| 문제 정의가 변경되지 않는 문서가 된다. | 새 근거가 들어오면 버전과 변경 이유를 남기며 갱신한다. |

## 검증 방법

1. 문제 문장을 여러 역할의 팀원이 같은 의미로 재진술하는지 확인한다.
2. 문제 문장마다 직접 증거, 간접 증거, 추정의 비율을 표시한다.
3. 사용자에게 해결책을 묻기보다 최근 실제 사례와 행동을 탐색한다.
4. 문제 해결 전후의 관찰 가능한 차이를 정의할 수 있는지 검토한다.

## 인수 기준

- [ ] 문제 문장에 사용자 집단, 발생 맥락, 달성하려는 과업, 현재 장벽, 장벽의 결과를 포함한다.
- [ ] 문제 정의에 사용한 근거와 아직 검증하지 않은 가정을 구분한다.
- [ ] 현재 사용자가 취하는 대안·우회 경로와 그것이 유지되는 이유를 기록한다.
- [ ] 조직 목표와 사용자 목표가 충돌하는 지점을 명시한다.
- [ ] 문제 범위에서 제외하는 대상과 이유를 투명하게 기록하고 후속 검토 시점을 둔다.
- [ ] 문제 문장을 여러 역할의 팀원이 같은 의미로 재진술하는지 확인한다.
- [ ] 문제 문장마다 직접 증거, 간접 증거, 추정의 비율을 표시한다.
- [ ] 사용자에게 해결책을 묻기보다 최근 실제 사례와 행동을 탐색한다.

## 에이전트 적용 규칙

- 해결책 중심 요청을 받으면 바로 화면을 제안하기 전에 재구성된 문제와 최소 가정을 제시한다.
- 페르소나를 임의로 꾸미지 말고 확인된 행동 세그먼트와 미확인 가정을 분리한다.
- 사용자와 조직의 충돌을 숨기지 말고 의사결정 항목으로 올린다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

- 원문: https://www.nngroup.com/articles/user-interviews/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
