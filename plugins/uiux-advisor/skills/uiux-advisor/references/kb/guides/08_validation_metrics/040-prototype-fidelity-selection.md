# 프로토타이핑과 충실도 선택

## 한 문장 원칙

프로토타입의 충실도는 보기 좋은 정도가 아니라 가장 위험한 가정을 가장 적은 비용으로 검증할 수 있는 수준으로 선택한다.

## 적용 상황

아이디어를 바로 고해상도 화면으로 만들거나, 반대로 실제 상호작용·콘텐츠·성능 위험을 종이 스케치만으로 판단하려 할 때 사용한다. 이해관계자가 프로토타입을 완성품으로 오해하거나 검증 질문이 불명확할 때도 적용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 질문 우선

프로토타입은 산출물이 아니라 질문에 답하기 위한 실험 도구다. 무엇을 배우려는지 먼저 정하고 표현 범위를 제한한다.

### 가정별 충실도

정보구조는 카드와 텍스트로, 흐름은 클릭 가능한 와이어프레임으로, 미세 상호작용·접근성·성능은 실제 코드에 가까운 구현으로 검증한다.

### 대표 콘텐츠

가짜 짧은 문구와 이상적인 데이터만 쓰면 레이아웃·이해·오류 문제가 사라진다. 현실적인 길이와 극단값을 포함한다.

### 오해 방지

프로토타입의 작동 범위, 미구현 상태, 데이터의 가상성, 검증하지 않는 항목을 참여자와 이해관계자에게 명시한다.

### 폐기 가능성

프로토타입에 과도한 생산 비용을 투입하면 잘못된 가설도 유지하려는 매몰비용이 생긴다. 학습 후 버리거나 다시 만들 수 있게 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 프로토타입마다 검증 질문, 핵심 가정, 대상 사용자, 성공·실패 신호를 기록한다.
- **MUST:** 검증 질문에 필요하지 않은 시각적·기능적 세부사항은 의도적으로 제외하고 제외 범위를 표시한다.
- **MUST:** 주요 성공 상태뿐 아니라 오류, 빈 상태, 로딩, 취소, 뒤로 가기, 권한 거부 등 질문과 관련된 상태를 포함한다.
- **MUST:** 실제 사용 맥락을 왜곡할 수 있는 더미 콘텐츠와 이상적 데이터의 한계를 기록한다.
- **MUST:** 접근성, 키보드 조작, 반응형 재배치, 지각된 성능을 검증하려면 해당 특성이 작동하는 구현 수준을 사용한다.

### SHOULD

- **SHOULD:** 같은 질문에 여러 대안을 빠르게 비교한 뒤 한 대안만 정교화한다.
- **SHOULD:** 프로토타입 링크나 화면에 범위·버전·소유자·마지막 검증 날짜를 표시한다.
- **SHOULD:** 사용자 테스트 전 내부 파일럿으로 막힌 링크, 잘못된 데이터, 의도치 않은 힌트를 제거한다.
- **SHOULD:** 프로토타입에서 얻은 학습을 최종 요구사항과 인수 기준으로 변환하고 프로토타입 자체를 명세로 간주하지 않는다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 가장 불확실하고 실패 비용이 큰 가정을 한 문장으로 고른다.
2. 가정을 관찰 가능한 사용자 행동 또는 이해 질문으로 변환한다.
3. 구조, 흐름, 콘텐츠, 시각, 상호작용, 기술 위험 중 필요한 충실도 차원을 선택한다.
4. 최소 상태와 현실적인 콘텐츠를 포함해 프로토타입을 만든다.
5. 파일럿을 실행해 프로토타입 결함과 제품 가설 실패를 구분할 수 있게 보정한다.
6. 검증 결과를 결정 로그·요구사항·다음 실험으로 연결하고 불필요한 산출물을 폐기한다.

## 예외·극단 상황

- 음성·제스처·공간 인터페이스처럼 정적 화면으로 핵심 상호작용을 재현하기 어려운 제품
- 실제 개인정보·금융·건강 데이터 없이 신뢰와 위험 인식을 재현하기 어려운 과업
- 네트워크 지연·장치 성능·외부 시스템 실패가 경험을 크게 좌우하는 서비스
- 스크린 리더와 키보드 사용성을 시각적 목업으로 평가하려는 상황
- 생성형 AI처럼 출력이 비결정적이어서 고정된 대화 예시만으로 실패 범위를 숨길 수 있는 기능

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 완성도 높은 화면을 먼저 만들어 문제 정의가 고정된다. | 낮은 비용의 대안 여러 개로 위험한 가정을 비교한 뒤 필요한 부분만 정교화한다. |
| 행복 경로만 연결한다. | 실패·취소·재시도·복구 상태를 검증 질문에 맞춰 포함한다. |
| 프로토타입의 애니메이션을 실제 성능으로 오해한다. | 성능 질문은 실제 코드·데이터·네트워크 조건에서 별도 검증한다. |
| 임시 문구가 최종 콘텐츠로 굳어진다. | 콘텐츠 소유자와 검토 상태를 표시하고 최종 인수 기준으로 다시 작성한다. |
| 참여자가 미구현 영역에서 막힌 것을 사용성 실패로 기록한다. | 파일럿과 범위 안내를 통해 프로토타입 한계와 제품 문제를 구분한다. |

## 검증 방법

1. 검증 질문마다 프로토타입의 요소가 왜 필요한지 설명하고 불필요한 요소를 제거한다.
2. 대표 사용자에게 과업을 수행하게 한 뒤 행동·오류·발화가 가정 판단에 충분한지 확인한다.
3. 서로 다른 콘텐츠 길이, 권한, 오류, 기기 조건에서 프로토타입이 질문을 여전히 검증하는지 점검한다.
4. 검증 후 어떤 결정이 유지·변경·보류되었는지 추적하고 배운 것이 없는 프로토타입은 원인을 분석한다.

## 인수 기준

- [ ] 프로토타입마다 검증 질문, 핵심 가정, 대상 사용자, 성공·실패 신호를 기록한다.
- [ ] 검증 질문에 필요하지 않은 시각적·기능적 세부사항은 의도적으로 제외하고 제외 범위를 표시한다.
- [ ] 주요 성공 상태뿐 아니라 오류, 빈 상태, 로딩, 취소, 뒤로 가기, 권한 거부 등 질문과 관련된 상태를 포함한다.
- [ ] 실제 사용 맥락을 왜곡할 수 있는 더미 콘텐츠와 이상적 데이터의 한계를 기록한다.
- [ ] 접근성, 키보드 조작, 반응형 재배치, 지각된 성능을 검증하려면 해당 특성이 작동하는 구현 수준을 사용한다.
- [ ] 검증 질문마다 프로토타입의 요소가 왜 필요한지 설명하고 불필요한 요소를 제거한다.
- [ ] 대표 사용자에게 과업을 수행하게 한 뒤 행동·오류·발화가 가정 판단에 충분한지 확인한다.

## 에이전트 적용 규칙

- 프로토타입 요청을 받으면 도구나 화면 수준보다 먼저 검증 질문과 위험 가정을 제시한다.
- 시각적 목업만으로 접근성·성능·실제 기술 가능성을 검증했다고 표현하지 않는다.
- 최종 산출물에는 프로토타입 범위, 미검증 영역, 다음 검증 단계를 명시한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
