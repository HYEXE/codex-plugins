# 휴리스틱·표준 기반 리뷰

## 한 문장 원칙

전문가 리뷰는 일반 휴리스틱, 접근성 표준, 도메인 규칙, 제품의 실제 과업을 분리해 적용하고 관찰 증거와 검증 한계를 함께 제시한다.

## 적용 상황

출시 전 빠르게 구조적 문제를 찾거나, 사용자 테스트 전에 명백한 결함을 제거하거나, 기존 제품의 대규모 품질 부채를 분류해야 할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 기준의 출처

‘직관적이지 않다’ 같은 인상 대신 어떤 표준·원칙·컴포넌트 계약을 위반하는지 밝힌다.

### 과업 기반 검토

화면을 고립해서 보지 않고 시작 조건, 상태 전환, 오류, 복구, 종료까지 대표 과업을 따라간다.

### 심각도 캘리브레이션

미관 선호와 과업 차단·접근성 실패·법적 위험을 같은 수준으로 다루지 않는다.

### 보이는 증거와 추론

정적 화면에서는 키보드 순서, 동적 알림, 지연, 실제 문구 변경을 확정할 수 없다. 확인한 것과 추정한 것을 구분한다.

### 대체가 아닌 보완

전문가 리뷰는 사용자의 실제 행동·맥락을 대체하지 않는다. 발견과 미확인 영역을 후속 테스트로 연결한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 리뷰 범위, 플랫폼, 사용자·과업, 상태, 브라우저·기기·보조기술, 검토하지 않은 영역을 명시한다.
- **MUST:** 각 이슈에 관찰 증거, 적용 기준, 사용자 영향, 심각도, 권고 수정, 검증 방법을 기록한다.
- **MUST:** 규범 표준의 요구사항과 제품 디자인 시스템의 권고사항, 리뷰어의 맥락적 판단을 서로 다른 근거 수준으로 표시한다.
- **MUST:** 키보드, 포커스, 접근 가능한 이름·역할·상태, 대비, 확대·재배치, 오류 전달을 실제 동작으로 검사한다.
- **MUST:** 화면만 제공된 경우 보이지 않는 동작을 단정하지 않고 확인 질문 또는 테스트 항목으로 남긴다.

### SHOULD

- **SHOULD:** 서로 다른 전문성을 가진 리뷰어가 독립 검토한 뒤 심각도와 중복 이슈를 합의한다.
- **SHOULD:** 이슈를 개별 화면 수정뿐 아니라 공통 컴포넌트·콘텐츠·프로세스·계측의 시스템 원인으로 분류한다.
- **SHOULD:** 수정 비용보다 사용자 위해와 과업 차단을 우선해 순서를 정한다.
- **SHOULD:** 완료 기준을 스크린샷 변화가 아니라 재현 가능한 테스트 조건으로 작성한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 검토할 사용자군·대표 과업·환경·위험 수준을 정의한다.
2. 적용할 휴리스틱, 접근성 기준, 도메인 규칙, 내부 컴포넌트 계약을 목록화한다.
3. 행복 경로와 오류·취소·복구·권한·빈 데이터 경로를 직접 수행한다.
4. 이슈를 증거와 함께 기록하고 확정·추정·미검증 상태를 붙인다.
5. 사용자 영향과 시스템 범위로 심각도를 캘리브레이션한다.
6. 수정 후 자동·수동·사용자 검증을 조합해 닫힘 조건을 확인한다.

## 예외·극단 상황

- 접근할 수 없는 운영 환경이나 실데이터 없이 정적 산출물만 검토하는 경우
- 플랫폼 네이티브 규칙과 웹 패턴이 충돌하는 멀티플랫폼 제품
- 도메인 규정이 공개 표준보다 더 엄격하거나 다른 용어를 요구하는 서비스
- 사용자별 설정과 권한에 따라 화면·상태가 크게 달라지는 시스템
- AI 생성 결과처럼 동일 과업에서도 매번 다른 콘텐츠와 위험이 나타나는 기능

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 리뷰어 취향을 보편 원칙처럼 쓴다. | 출처가 있는 기준과 맥락적 추천을 분리하고 대안의 트레이드오프를 설명한다. |
| 홈 화면만 보고 전체 경험을 평가한다. | 대표 과업과 상태 전환을 시작부터 복구·완료까지 따라간다. |
| 모든 이슈를 ‘높음’으로 표시한다. | 과업 차단, 위해, 빈도, 범위, 복구 가능성으로 심각도를 캘리브레이션한다. |
| 자동 접근성 검사 통과를 완전한 준수로 본다. | 키보드·스크린 리더·확대·인지적 이해를 수동 및 사용자 검증한다. |
| 문제만 나열하고 재현 조건이 없다. | 환경·경로·현재 결과·기대 결과·검증 절차를 기록한다. |

## 검증 방법

1. 동일한 이슈를 다른 리뷰어가 재현하고 같은 근거 수준과 심각도로 분류할 수 있는지 확인한다.
2. 접근성 이슈는 해당 성공 기준과 테스트 조건을 연결하고 자동 검사만으로 판단하지 않는다.
3. 수정안이 다른 상태·사용자·화면에 새 문제를 만들지 회귀 경로를 테스트한다.
4. 전문가 리뷰로 답할 수 없는 사용자 이해·신뢰·맥락 문제를 사용성 테스트나 현장 연구로 이관한다.

## 인수 기준

- [ ] 리뷰 범위, 플랫폼, 사용자·과업, 상태, 브라우저·기기·보조기술, 검토하지 않은 영역을 명시한다.
- [ ] 각 이슈에 관찰 증거, 적용 기준, 사용자 영향, 심각도, 권고 수정, 검증 방법을 기록한다.
- [ ] 규범 표준의 요구사항과 제품 디자인 시스템의 권고사항, 리뷰어의 맥락적 판단을 서로 다른 근거 수준으로 표시한다.
- [ ] 키보드, 포커스, 접근 가능한 이름·역할·상태, 대비, 확대·재배치, 오류 전달을 실제 동작으로 검사한다.

## 에이전트 적용 규칙

- 리뷰 출력은 심각도, 증거, 기준, 영향, 수정, 검증의 고정 구조를 사용한다.
- 이미지·설명만으로 확인할 수 없는 동작은 ‘미검증’으로 표시한다.
- 표준 위반과 개선 권고를 같은 언어로 단정하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
