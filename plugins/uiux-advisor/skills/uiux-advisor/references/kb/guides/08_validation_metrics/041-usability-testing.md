# 사용성 테스트

## 한 문장 원칙

대표 사용자가 현실적인 과업을 수행하는 행동을 관찰해 문제의 존재·원인·심각도를 확인하고, 의견이나 선호만으로 사용성을 판단하지 않는다.

## 적용 상황

팀 내부 평가가 엇갈리거나, 새 흐름·콘텐츠·컴포넌트가 실제로 이해되고 완료되는지 확인해야 할 때 사용한다. 분석 데이터가 실패 위치는 보여주지만 원인을 설명하지 못할 때도 적용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 행동 관찰

사람이 무엇을 좋아한다고 말하는지보다 무엇을 시도하고 어디에서 멈추며 어떻게 복구하는지 관찰한다.

### 현실적 과업

정답을 암시하는 기능명이나 화면 요소를 과업 문구에 넣지 않고 사용자의 목적과 맥락으로 제시한다.

### 대표성의 명시

소수 테스트는 통계적 모집단 추정이 아니라 반복되는 문제와 원인 탐색에 적합하다. 모집 범위와 한계를 숨기지 않는다.

### 중립적 진행

진행자가 설명·유도·구조를 방어하면 제품의 문제를 가린다. 필요한 경우에만 표준화된 탐침 질문을 사용한다.

### 반복 개선

한 번의 대형 테스트보다 설계 단계마다 작은 테스트와 수정 주기를 반복해 위험을 줄인다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 연구 질문, 대상 사용자, 과업, 성공 기준, 관찰 항목, 분석 방법을 테스트 전에 문서화한다.
- **MUST:** 과업 문구에서 UI 레이블, 정답 경로, 평가 의도를 제거하고 실제 목표와 맥락을 제시한다.
- **MUST:** 참여자의 동의, 개인정보 처리, 녹화·공유 범위, 중단 권리를 명확히 안내한다.
- **MUST:** 관찰 사실, 참여자 해석, 연구자 추론, 권고안을 분리해 기록한다.
- **MUST:** 키보드·스크린 리더·확대·음성 입력 등 실제 보조기술 사용이 중요한 대상은 해당 환경과 숙련 사용자를 포함한다.

### SHOULD

- **SHOULD:** 본 테스트 전에 파일럿을 실행해 과업 난이도와 진행자의 유도 표현을 점검한다.
- **SHOULD:** 완료 여부 외에 시간, 오류, 재탐색, 도움 요청, 자신감, 복구 방식을 함께 기록한다.
- **SHOULD:** 문제 심각도는 빈도뿐 아니라 과업 차단, 위해, 복구 가능성, 영향 사용자 범위로 평가한다.
- **SHOULD:** 세션 후 팀이 원본 관찰을 함께 검토하되 한 참여자의 강한 발언을 전체 사용자로 일반화하지 않는다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 제품 결정과 연결된 연구 질문을 정하고 테스트가 답할 수 없는 질문을 분리한다.
2. 행동·맥락·능력·숙련도 기준으로 모집 조건을 정의한다.
3. 현실적 과업, 중립적 진행 가이드, 관찰 기록 양식을 만든다.
4. 파일럿 후 과업 문구·프로토타입·기술 환경을 수정한다.
5. 세션에서 생각 말하기를 강요하지 않고 행동을 우선 관찰하며 필요 시 사후 탐침한다.
6. 문제를 증거와 함께 합성하고 심각도·원인·수정안·재검증 계획을 연결한다.

## 예외·극단 상황

- 업무상 비밀이나 개인정보 때문에 실제 데이터·환경을 재현하기 어려운 도메인
- 전문가의 숙련 행동이 자동화되어 생각 말하기가 수행을 방해하는 과업
- 응급·고위험 상황처럼 실전 실패를 직접 재현할 수 없는 서비스
- 장기 학습·습관 형성처럼 단일 세션으로 성과를 판단하기 어려운 경험
- 참여자가 진행자에게 만족을 주려는 경향이 강한 문화·권력 관계

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| ‘이 버튼이 마음에 드나요?’처럼 선호만 묻는다. | 목적을 주고 실제 선택·탐색·완료 행동을 관찰한다. |
| 진행자가 막힌 즉시 설명한다. | 자연스러운 탐색과 복구를 관찰한 뒤 사전에 정한 시점에만 도움을 준다. |
| 한 명의 실패를 보편적 결론으로 만든다. | 패턴, 맥락, 심각도와 다른 근거를 함께 해석한다. |
| 문제 목록만 만들고 원인과 수정이 연결되지 않는다. | 관찰 증거 → 가능한 원인 → 수정 가설 → 재검증 기준을 기록한다. |
| 장애 사용자를 마지막 별도 테스트로만 포함한다. | 초기 모집과 반복 주기에 다양한 보조기술·능력 조건을 포함한다. |

## 검증 방법

1. 과업 문구를 제품을 모르는 사람이 읽고 특정 UI 요소 없이 목표를 이해하는지 확인한다.
2. 두 관찰자가 같은 세션을 독립 기록해 사실과 해석의 일관성을 비교한다.
3. 발견 문제마다 원본 증거, 영향 과업, 심각도 근거, 수정 책임자, 재검증 상태가 있는지 검토한다.
4. 수정 후 동일하거나 동등한 과업을 다시 수행해 문제 이동·새 회귀를 확인한다.

## 인수 기준

- [ ] 연구 질문, 대상 사용자, 과업, 성공 기준, 관찰 항목, 분석 방법을 테스트 전에 문서화한다.
- [ ] 과업 문구에서 UI 레이블, 정답 경로, 평가 의도를 제거하고 실제 목표와 맥락을 제시한다.
- [ ] 참여자의 동의, 개인정보 처리, 녹화·공유 범위, 중단 권리를 명확히 안내한다.
- [ ] 관찰 사실, 참여자 해석, 연구자 추론, 권고안을 분리해 기록한다.
- [ ] 키보드·스크린 리더·확대·음성 입력 등 실제 보조기술 사용이 중요한 대상은 해당 환경과 숙련 사용자를 포함한다.
- [ ] 과업 문구를 제품을 모르는 사람이 읽고 특정 UI 요소 없이 목표를 이해하는지 확인한다.
- [ ] 두 관찰자가 같은 세션을 독립 기록해 사실과 해석의 일관성을 비교한다.
- [ ] 발견 문제마다 원본 증거, 영향 과업, 심각도 근거, 수정 책임자, 재검증 상태가 있는지 검토한다.

## 에이전트 적용 규칙

- 사용성 테스트 계획에는 모집 조건, 과업 문구, 관찰 지표, 진행자 중립성, 윤리·개인정보를 포함한다.
- 소수 참여자 결과를 통계적 비율처럼 표현하지 않는다.
- 스크린샷만 보고 실제 사용성 테스트를 수행했다고 주장하지 말고 검증 계획을 제시한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
