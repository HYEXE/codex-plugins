# 접근 가능한 이름·역할·상태와 ARIA

## 한 문장 원칙

보조기술이 각 요소의 이름, 역할, 값, 상태, 관계, 변경을 정확히 이해하도록 네이티브 의미를 우선하고 ARIA는 필요한 만큼만 올바르게 사용한다.

## 적용 상황

아이콘 버튼에 이름이 없거나, 레이블과 접근 가능한 이름이 다르고, 펼침·선택·오류·필수 상태가 시각적으로만 표시되며, ARIA로 잘못된 역할을 덧붙일 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 이름의 출처

시각 레이블과 접근 가능한 이름을 가능한 한 일치시키고 여러 이름 소스의 우선순위와 중복을 이해한다.

### 역할과 동작의 일치

button 역할을 부여했다면 버튼 키보드·상태·행동을 모두 구현해야 한다.

### 상태와 관계

확장, 선택, 누름, 현재, 오류, 필수, 비활성, 소유·설명 관계를 사용자에게 실제로 필요한 시점에 표현한다.

### ARIA는 의미를 바꾸지 기능을 만들지 않음

ARIA 속성만으로 키보드 처리·포커스·시각 상태·비즈니스 동작이 생기지 않는다.

### 발표의 절제

라이브 영역과 상태 변경은 중요한 정보만 적절한 긴급도로 전달한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 모든 인터랙티브 요소에 고유하고 목적을 설명하는 접근 가능한 이름을 제공한다.
- **MUST:** 시각 레이블에 포함된 핵심 단어가 접근 가능한 이름에도 포함되게 한다.
- **MUST:** 역할·상태·값·관계가 실제 동작과 동기화되고 오래된 상태를 남기지 않는다.
- **MUST:** 네이티브 요소로 가능한 경우 불필요한 ARIA 역할과 속성을 추가하지 않는다.
- **MUST:** 커스텀 위젯은 해당 패턴의 키보드 상호작용, 포커스, 상태 발표를 완전하게 구현한다.

### SHOULD

- **SHOULD:** 아이콘·축약 레이블은 화면 문맥과 반복 목록에서 고유한 이름이 되게 한다.
- **SHOULD:** 설명 텍스트와 오류 텍스트가 이름을 과도하게 길게 만들지 않도록 이름·설명 관계를 분리한다.
- **SHOULD:** 동적 카운트·상태를 매 변화마다 읽지 않고 과업에 필요한 요약을 발표한다.
- **SHOULD:** 여러 스크린 리더·브라우저 조합의 차이를 핵심 패턴에서 확인한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 모든 컨트롤의 시각 레이블, 접근 가능한 이름, 역할, 값, 상태, 설명을 표로 만든다.
2. 네이티브 요소 대안을 먼저 선택하고 커스텀 필요성을 검토한다.
3. 상태 전환과 ARIA 속성·시각 표현·키보드 동작의 동기화를 명세한다.
4. 반복 목록·아이콘·동적 콘텐츠·오류·라이브 업데이트를 추가 검토한다.
5. 접근성 트리와 실제 스크린 리더로 핵심 과업을 테스트한다.
6. 컴포넌트 회귀 테스트에 이름·역할·상태와 키보드 동작을 포함한다.

## 예외·극단 상황

- 복합 그래프·캔버스·지도에서 가상 객체를 탐색해야 하는 경우
- 같은 아이콘 행동이 반복 목록마다 다른 대상을 갖는 경우
- 언어 전환 후 접근 가능한 이름과 시각 레이블이 비동기로 갱신되는 경우
- 웹 컴포넌트와 Shadow DOM의 레이블·설명 관계
- 실시간 상태가 매우 자주 바뀌어 발표 피로가 발생하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 아이콘 버튼에 title만 넣고 끝낸다. | 지원 조합을 검토하고 명시적 접근 가능한 이름과 시각적 툴팁을 각각 설계한다. |
| div에 role=button만 추가한다. | 네이티브 버튼을 쓰거나 키보드·포커스·상태·비활성 동작을 모두 구현한다. |
| aria-label이 시각 레이블과 전혀 다르다. | 음성 사용자가 보이는 이름으로 호출할 수 있게 핵심 문구를 일치시킨다. |
| aria-live=assertive를 모든 알림에 사용한다. | 긴급성에 맞는 발표와 지속적 메시지를 선택한다. |
| aria-hidden으로 포커스 가능한 요소를 숨긴다. | 접근성 트리와 포커스 가능성을 일관되게 관리한다. |

## 검증 방법

1. 접근성 트리에서 이름·역할·상태·관계를 시각 화면과 비교한다.
2. 스크린 리더로 반복 버튼, 폼, 탭, 대화상자, 알림의 과업을 수행한다.
3. 상태 변경 후 오래된 ARIA 값과 중복 발표가 남지 않는지 확인한다.
4. 음성 명령에서 시각 레이블로 컨트롤을 호출할 수 있는지 테스트한다.

## 인수 기준

- [ ] 모든 인터랙티브 요소에 고유하고 목적을 설명하는 접근 가능한 이름을 제공한다.
- [ ] 시각 레이블에 포함된 핵심 단어가 접근 가능한 이름에도 포함되게 한다.
- [ ] 역할·상태·값·관계가 실제 동작과 동기화되고 오래된 상태를 남기지 않는다.
- [ ] 네이티브 요소로 가능한 경우 불필요한 ARIA 역할과 속성을 추가하지 않는다.
- [ ] 커스텀 위젯은 해당 패턴의 키보드 상호작용, 포커스, 상태 발표를 완전하게 구현한다.
- [ ] 접근성 트리에서 이름·역할·상태·관계를 시각 화면과 비교한다.
- [ ] 스크린 리더로 반복 버튼, 폼, 탭, 대화상자, 알림의 과업을 수행한다.
- [ ] 상태 변경 후 오래된 ARIA 값과 중복 발표가 남지 않는지 확인한다.

## 에이전트 적용 규칙

- ARIA 속성을 제안할 때 네이티브 요소 대안과 키보드 구현을 함께 설명한다.
- 스크린 리더 호환성을 코드·브라우저 검증 없이 보장하지 않는다.
- 접근 가능한 이름과 설명을 무조건 길게 합치지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [wai-forms] Forms Tutorial

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: 레이블, 그룹화, 지침, 검증, 알림을 포함한 접근 가능한 폼
- 이 가이드에서의 사용: 폼의 의미 구조와 오류 전달을 설계·검토할 때 사용한다.
- 원문: https://www.w3.org/WAI/tutorials/forms/

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

### [uswds-accessibility] USWDS Accessibility

- 발행·관리 주체: U.S. Web Design System
- 유형: implementation-guidance
- 적용 범위: 컴포넌트 접근성, 팀 책임, 테스트와 준수 범위
- 이 가이드에서의 사용: 디자인 시스템이 접근성을 보장하는 범위와 제품 팀의 책임을 구분할 때 사용한다.
- 원문: https://designsystem.digital.gov/documentation/accessibility/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
