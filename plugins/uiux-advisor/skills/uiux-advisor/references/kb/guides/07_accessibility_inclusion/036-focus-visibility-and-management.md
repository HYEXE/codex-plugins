# 포커스 가시성과 관리

## 한 문장 원칙

키보드 포커스는 항상 찾을 수 있고 가려지지 않아야 하며 화면 상태 변화 뒤에는 사용자의 다음 과업에 맞는 논리적 위치로 이동하거나 유지되어야 한다.

## 적용 상황

포커스 링이 제거되거나 고정 헤더에 가리고, 모달·오류·라우팅 후 포커스가 사라지며, 동적 업데이트 때 예고 없이 이동할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 가시성

포커스 표시가 배경·상태·테마에서 충분히 구분되고 요소 전체가 고정 영역에 가려지지 않아야 한다.

### 예측 가능성

사용자 행동 없이 포커스를 이동하지 않고 이동이 필요할 때는 상태 변화와 과업 맥락을 따른다.

### 수명주기

열기·오류·삭제·추가·라우팅·닫기·복구마다 포커스의 출발, 목적, 복귀를 정의한다.

### 시각·프로그램 일치

시각적으로 포커스처럼 보이는 선택 상태와 실제 키보드 포커스를 구분한다.

### 스크롤과 포커스

포커스 이동은 필요한 경우 요소를 보이게 스크롤하되 맥락을 잃는 갑작스러운 이동을 줄인다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 모든 키보드 포커스 가능 요소에 명확하고 일관된 포커스 표시를 제공한다.
- **MUST:** 고정 헤더·배너·오버레이가 포커스 요소 전체를 가리지 않게 한다.
- **MUST:** 모달·메뉴·오류·라우팅·삭제·추가 후 초기·복귀 포커스를 상태별로 정의한다.
- **MUST:** 선택·활성·호버 상태와 포커스 상태를 시각·의미적으로 구분한다.
- **MUST:** 프로그램적 포커스 이동은 사용자 행동과 과업 결과에 근거하고 화면 변화와 함께 검증한다.

### SHOULD

- **SHOULD:** 페이지 수준 오류 후 요약 또는 첫 오류로 이동하고 사용자가 오류 간 이동하게 한다.
- **SHOULD:** 삭제된 요소에 포커스가 있었다면 다음 합리적 항목이나 목록 제목으로 이동한다.
- **SHOULD:** SPA 라우팅에서는 페이지 제목·주요 제목·주요 콘텐츠 중 과업에 맞는 시작점을 선택한다.
- **SHOULD:** 마우스 사용자에게도 포커스가 필요한 상황을 고려해 :focus-visible 같은 정책을 실제 브라우저에서 검증한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 화면 상태 변화와 포커스 가능한 요소를 목록화한다.
2. 각 이벤트의 포커스 유지·이동·복귀·스크롤 정책을 표로 만든다.
3. 모든 테마·상태·배경에서 포커스 표시와 가림을 검증한다.
4. 키보드 연속 조작과 빠른 상태 변화에서 포커스 손실을 테스트한다.
5. 스크린 리더 발표와 시각적 스크롤이 과업 맥락을 유지하는지 확인한다.
6. 회귀 테스트에 핵심 포커스 경로와 고정 요소 조합을 포함한다.

## 예외·극단 상황

- 가상화 목록에서 포커스된 항목이 DOM에서 제거되는 경우
- 실시간 협업으로 현재 요소가 다른 사용자에 의해 삭제되는 경우
- 여러 고정 헤더·배너·하단 바가 동시에 존재하는 작은 화면
- 포커스가 캔버스 내부 가상 객체와 DOM 컨트롤 사이를 이동하는 경우
- 라우팅과 데이터 로딩이 비동기로 완료되는 SPA

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| outline: none만 적용한다. | 브랜드와 테마에서 충분히 구분되는 대체 포커스 표시를 제공한다. |
| 오류 후 페이지 상단으로만 이동한다. | 오류 요약과 필드 연결, 현재 맥락을 제공한다. |
| 모달 닫기 후 포커스가 body로 간다. | 호출 요소 또는 다음 논리적 과업 위치로 복귀한다. |
| 선택된 탭과 포커스된 탭을 같은 표시로 만든다. | 선택 상태와 이동 중 포커스를 별도로 표현한다. |
| 동적 업데이트마다 포커스를 새 콘텐츠로 이동한다. | 사용자 의도에 필요한 경우만 이동하고 그 외에는 상태 알림으로 처리한다. |

## 검증 방법

1. 키보드로 빠르게 모든 화면 상태를 전환하며 포커스 위치와 가시성을 기록한다.
2. 고정 요소와 확대·작은 화면에서 포커스가 일부 또는 전체 가려지는지 확인한다.
3. 모달·메뉴·삭제·추가·오류·라우팅 후 논리적 위치와 스크린 리더 발표를 검증한다.
4. 자동화 가능한 핵심 포커스 경로를 브라우저 회귀 테스트에 포함한다.

## 인수 기준

- [ ] 모든 키보드 포커스 가능 요소에 명확하고 일관된 포커스 표시를 제공한다.
- [ ] 고정 헤더·배너·오버레이가 포커스 요소 전체를 가리지 않게 한다.
- [ ] 모달·메뉴·오류·라우팅·삭제·추가 후 초기·복귀 포커스를 상태별로 정의한다.
- [ ] 선택·활성·호버 상태와 포커스 상태를 시각·의미적으로 구분한다.
- [ ] 프로그램적 포커스 이동은 사용자 행동과 과업 결과에 근거하고 화면 변화와 함께 검증한다.
- [ ] 키보드로 빠르게 모든 화면 상태를 전환하며 포커스 위치와 가시성을 기록한다.
- [ ] 고정 요소와 확대·작은 화면에서 포커스가 일부 또는 전체 가려지는지 확인한다.
- [ ] 모달·메뉴·삭제·추가·오류·라우팅 후 논리적 위치와 스크린 리더 발표를 검증한다.

## 에이전트 적용 규칙

- 포커스 명세에는 시각 스타일뿐 아니라 이벤트별 이동·복귀 위치를 포함한다.
- 스크린샷에서 포커스 구현 여부를 단정하지 않는다.
- 포커스 자동 이동을 접근성 개선으로 무조건 제안하지 말고 과업 근거를 설명한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [govuk-error-summary] Error Summary Component

- 발행·관리 주체: GOV.UK Design System
- 유형: component-guidance
- 적용 범위: 페이지 수준 오류 요약, 오류 필드 연결, 포커스 처리
- 이 가이드에서의 사용: 여러 오류를 한 번에 발견하고 이동할 수 있게 설계할 때 사용한다.
- 원문: https://design-system.service.gov.uk/components/error-summary/

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

### [material-states] Interaction States

- 발행·관리 주체: Material Design
- 유형: product-design-system
- 적용 범위: 호버, 포커스, 누름, 드래그, 선택, 비활성 등 상호작용 상태
- 이 가이드에서의 사용: 컴포넌트 상태 모델과 시각적 피드백을 설계할 때 비교 근거로 사용한다.
- 원문: https://m3.material.io/foundations/interaction/states

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
