# 의미 구조와 키보드 조작

## 한 문장 원칙

시각적 모양과 별개로 랜드마크, 제목, 목록, 표, 폼, 버튼, 링크의 의미를 올바르게 표현하고 모든 핵심 과업을 키보드만으로 수행하게 한다.

## 적용 상황

클릭 가능한 div, 제목처럼 보이는 일반 텍스트, 키보드로 접근할 수 없는 컨트롤, Tab 순서가 레이아웃과 다른 화면을 설계·검토할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 네이티브 의미 우선

HTML과 플랫폼 기본 컨트롤은 이름·역할·상태·키보드·보조기술 호환을 제공하므로 커스텀 역할보다 먼저 사용한다.

### 문서 구조

랜드마크와 제목 계층은 화면을 빠르게 탐색하고 관계를 이해하는 핵심 내비게이션이다.

### 논리적 포커스 순서

포커스 순서는 시각·읽기·과업 순서와 일치하고 양의 tabindex로 임의 재배치하지 않는다.

### 키보드 동등성

포인터로 가능한 모든 핵심 행동과 상태 확인을 키보드로 수행할 수 있어야 한다.

### 우회와 반복 감소

반복 내비게이션을 건너뛰고 주요 영역으로 이동할 수 있게 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 페이지 언어, 제목, 랜드마크, 제목 계층, 목록·표·폼 관계를 의미적으로 표현한다.
- **MUST:** 모든 인터랙티브 요소를 키보드로 도달·조작·종료할 수 있게 하고 키보드 함정을 만들지 않는다.
- **MUST:** 시각적 순서와 DOM·포커스 순서를 일치시키고 양의 tabindex로 순서를 강제하지 않는다.
- **MUST:** 버튼·링크·입력 등 가능한 한 네이티브 요소를 사용하고 커스텀 위젯은 표준 패턴을 구현한다.
- **MUST:** 반복 영역 건너뛰기와 명확한 페이지 제목·주요 콘텐츠 진입 경로를 제공한다.

### SHOULD

- **SHOULD:** 랜드마크가 여러 개면 목적을 구분할 수 있는 이름을 제공한다.
- **SHOULD:** 키보드 단축키는 필수 조작을 대체하지 않고 충돌·발견·비활성화·재매핑을 고려한다.
- **SHOULD:** 동적 콘텐츠 추가·삭제 후 포커스와 읽기 순서를 상태 흐름에 맞게 관리한다.
- **SHOULD:** 코드 린트와 자동 검사 외에 실제 키보드·보조기술 과업 테스트를 수행한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 화면의 콘텐츠 구조와 모든 인터랙티브 요소를 인벤토리한다.
2. 네이티브 요소와 랜드마크·제목·목록·표·폼 관계를 설계한다.
3. Tab·Shift+Tab·Enter·Space·화살표·Escape 조작과 포커스 순서를 명세한다.
4. 동적 상태, 오버레이, 오류, 라우팅, 콘텐츠 업데이트 후 포커스를 정의한다.
5. 키보드만으로 핵심 과업과 우회 탐색을 테스트한다.
6. 스크린 리더와 자동 도구로 이름·역할·구조를 보완 검증한다.

## 예외·극단 상황

- 캔버스·그래프·에디터처럼 네이티브 구조가 충분하지 않은 복합 도구
- 가상 스크롤·동적 목록에서 DOM 항목이 계속 교체되는 경우
- 드래그 앤 드롭이 핵심 과업인 경우
- 여러 언어와 오른쪽에서 왼쪽 방향에서 화살표 의미가 달라지는 경우
- 단일 페이지 앱에서 화면 전환 없이 제목·주요 콘텐츠가 바뀌는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 클릭 이벤트가 있는 div를 버튼으로 사용한다. | 네이티브 버튼을 사용하거나 역할·키보드·상태를 완전히 구현한다. |
| CSS order로 보이는 순서만 바꾼다. | DOM 구조를 실제 읽기·과업 순서에 맞춘다. |
| 키보드 포커스를 없애 디자인을 깔끔하게 한다. | 명확하고 일관된 포커스 표시를 제공한다. |
| 모든 요소에 tabindex=0을 넣는다. | 상호작용 가능한 요소만 자연스러운 순서에 포함한다. |
| 자동 검사 통과를 접근성 완료로 본다. | 실제 키보드와 보조기술 사용자 과업으로 검증한다. |

## 검증 방법

1. 마우스를 치우고 시작부터 완료·오류 복구까지 모든 핵심 과업을 수행한다.
2. 제목·랜드마크·링크·폼 목록으로 화면 구조와 목적을 이해할 수 있는지 확인한다.
3. DOM과 포커스 순서를 시각적 순서와 비교하고 확대·반응형에서도 유지되는지 검증한다.
4. 자동 검사 결과를 수동 테스트와 실제 사용자 문제에 연결한다.

## 인수 기준

- [ ] 페이지 언어, 제목, 랜드마크, 제목 계층, 목록·표·폼 관계를 의미적으로 표현한다.
- [ ] 모든 인터랙티브 요소를 키보드로 도달·조작·종료할 수 있게 하고 키보드 함정을 만들지 않는다.
- [ ] 시각적 순서와 DOM·포커스 순서를 일치시키고 양의 tabindex로 순서를 강제하지 않는다.
- [ ] 버튼·링크·입력 등 가능한 한 네이티브 요소를 사용하고 커스텀 위젯은 표준 패턴을 구현한다.
- [ ] 반복 영역 건너뛰기와 명확한 페이지 제목·주요 콘텐츠 진입 경로를 제공한다.
- [ ] 마우스를 치우고 시작부터 완료·오류 복구까지 모든 핵심 과업을 수행한다.
- [ ] 제목·랜드마크·링크·폼 목록으로 화면 구조와 목적을 이해할 수 있는지 확인한다.
- [ ] DOM과 포커스 순서를 시각적 순서와 비교하고 확대·반응형에서도 유지되는지 검증한다.

## 에이전트 적용 규칙

- 정적 화면만 보고 의미 구조와 키보드 동작이 구현됐다고 단정하지 않는다.
- 커스텀 컴포넌트를 제안할 때 네이티브 대안과 필요한 키보드 모델을 함께 제시한다.
- 접근성 요구는 ‘추가 기능’이 아니라 인수 기준으로 작성한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 근거 출처

### [w3c-wcag22] Web Content Accessibility Guidelines (WCAG) 2.2

- 발행·관리 주체: W3C
- 유형: standard
- 적용 범위: 웹 콘텐츠 접근성의 시험 가능한 성공 기준과 적합성 수준
- 이 가이드에서의 사용: 접근성 요구사항을 규범적으로 제시할 때 최우선 기준으로 사용한다.
- 원문: https://www.w3.org/TR/WCAG22/

### [wai-aria-apg] ARIA Authoring Practices Guide

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: ARIA 위젯 패턴, 키보드 상호작용, 이름·역할·상태 구현
- 이 가이드에서의 사용: 네이티브 HTML로 해결할 수 없는 복합 위젯의 상호작용 모델을 설계할 때 사용한다.
- 원문: https://www.w3.org/WAI/ARIA/apg/

### [wai-forms] Forms Tutorial

- 발행·관리 주체: W3C Web Accessibility Initiative
- 유형: implementation-guidance
- 적용 범위: 레이블, 그룹화, 지침, 검증, 알림을 포함한 접근 가능한 폼
- 이 가이드에서의 사용: 폼의 의미 구조와 오류 전달을 설계·검토할 때 사용한다.
- 원문: https://www.w3.org/WAI/tutorials/forms/

### [fluent-accessibility] Accessibility

- 발행·관리 주체: Fluent 2 Design System
- 유형: product-design-system
- 적용 범위: 포용적 설계, 키보드, 스크린 리더, 색상, 확대와 입력 방식
- 이 가이드에서의 사용: 멀티플랫폼 제품의 접근성 체크와 구현 협업 기준으로 사용한다.
- 원문: https://fluent2.microsoft.design/accessibility

### [uswds-accessibility] USWDS Accessibility

- 발행·관리 주체: U.S. Web Design System
- 유형: implementation-guidance
- 적용 범위: 컴포넌트 접근성, 팀 책임, 테스트와 준수 범위
- 이 가이드에서의 사용: 디자인 시스템이 접근성을 보장하는 범위와 제품 팀의 책임을 구분할 때 사용한다.
- 원문: https://designsystem.digital.gov/documentation/accessibility/

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
