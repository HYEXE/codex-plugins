# 파괴적·고위험 행동

## 한 문장 원칙

행동의 위험과 가역성에 맞춰 예방, 검토, 명시적 확인, 지연, 권한, 실행 취소, 감사 기록을 조합한다.

## 적용 상황

삭제·결제·전송·승인·권한 변경·공개·데이터 덮어쓰기처럼 실수 비용이 크거나 여러 사람과 외부 시스템에 영향을 주는 행동을 설계할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 위험 기반 마찰

모든 행동에 확인을 붙이지 않고 영향 범위, 가역성, 시간 민감성, 빈도, 사용자 숙련도로 마찰 수준을 정한다.

### 결과의 구체성

무엇이 몇 개나 영향을 받고 누구에게 보이며 언제부터 되돌릴 수 없는지 확인 전에 보여준다.

### 안전한 기본값

파괴적 행동을 기본 선택이나 주 행동으로 두지 않고 권한·범위·대상을 최소화한다.

### 가역성 설계

소프트 삭제, 보관, 버전, 지연 전송, 실행 취소, 복원 기간으로 실수를 회복한다.

### 책임과 추적

고위험 행동은 권한, 재인증, 실행자, 시간, 대상, 결과, 복구를 감사 가능하게 기록한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 행동별 영향 대상, 범위, 가역성, 복구 기간, 권한, 승인, 실패 비용을 분류한다.
- **MUST:** 확인 화면에 실제 대상·수량·결과·되돌리기 가능성을 동적 값으로 보여준다.
- **MUST:** 파괴적 행동을 중립적 ‘확인’으로 표현하지 않고 구체적 동사와 대상을 사용한다.
- **MUST:** 중복 실행, 느린 응답, 새로고침, 다중 기기에서 동일 행동이 반복되지 않게 한다.
- **MUST:** 가능한 경우 실행 취소·복원·버전 기록을 제공하고 복구 한계를 명확히 한다.

### SHOULD

- **SHOULD:** 대량·고가·외부 공개·권한 상승 행동은 요약 검토와 추가 권한 또는 재인증을 사용한다.
- **SHOULD:** 확인 문구 입력은 정말 높은 위험에서만 사용하고 정확한 대상 이해를 돕는 방식으로 제한한다.
- **SHOULD:** 반복 업무의 안전성을 해치지 않으면서 실수를 줄이는 미리보기·검증·기본 범위를 제공한다.
- **SHOULD:** 감사 로그와 사용자 알림에서 민감 정보를 최소화하면서 행동 추적을 가능하게 한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 행동 목록을 영향·가역성·빈도·권한·시간 민감성으로 위험 등급화한다.
2. 각 등급에 예방, 미리보기, 확인, 재인증, 승인, 지연, 실행 취소 정책을 매핑한다.
3. 대상·수량·동적 범위·부분 실패·중복 요청 상태를 명세한다.
4. 복구 기간, 데이터 보존, 알림, 감사 로그, 지원 절차를 설계한다.
5. 대표·극단·의도적 실수 시나리오로 이해와 복구를 테스트한다.
6. 실수·복원·취소·지원·권한 오용 데이터를 바탕으로 마찰 수준을 조정한다.

## 예외·극단 상황

- 한 번의 행동이 수천 개 대상 또는 조직 전체에 영향을 주는 대량 작업
- 예약 전송·게시처럼 실행 전 지연 구간이 있는 행동
- 복원할 수 있지만 법적 보존·개인정보 삭제 요구와 충돌하는 경우
- 승인자와 실행자가 다르고 책임이 분산된 워크플로
- 외부 시스템에 전달된 후 제품에서 직접 취소할 수 없는 행동

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 모든 삭제에 같은 확인 대화상자를 사용한다. | 영향·가역성·빈도에 따라 실행 취소, 소프트 삭제, 동적 검토, 재인증을 조합한다. |
| ‘계속하시겠습니까?’만 묻는다. | 대상, 수량, 결과, 복구 가능성을 구체적으로 보여준다. |
| 파괴적 버튼이 기본 포커스다. | 안전한 선택을 기본으로 두고 키보드 오작동을 줄인다. |
| 성공 응답이 늦어 재실행된다. | 접수·처리 상태, 멱등성, 작업 ID와 결과 조회를 제공한다. |
| 실행 취소가 가능해 보이지만 일부만 복구된다. | 복구 범위·기간·예외를 사전에 설명하고 결과를 확인하게 한다. |

## 검증 방법

1. 사용자에게 확인 화면만 보여주고 영향 범위와 복구 가능성을 설명하게 한다.
2. 키보드·터치·느린 네트워크에서 우발 실행과 중복 실행을 테스트한다.
3. 복원·실행 취소·승인 취소가 실제 데이터와 외부 시스템까지 일관되게 적용되는지 검증한다.
4. 감사 로그가 누가 무엇을 언제 왜 했는지 지원과 보안 조사에 충분한지 확인한다.

## 인수 기준

- [ ] 행동별 영향 대상, 범위, 가역성, 복구 기간, 권한, 승인, 실패 비용을 분류한다.
- [ ] 확인 화면에 실제 대상·수량·결과·되돌리기 가능성을 동적 값으로 보여준다.
- [ ] 파괴적 행동을 중립적 ‘확인’으로 표현하지 않고 구체적 동사와 대상을 사용한다.
- [ ] 중복 실행, 느린 응답, 새로고침, 다중 기기에서 동일 행동이 반복되지 않게 한다.
- [ ] 가능한 경우 실행 취소·복원·버전 기록을 제공하고 복구 한계를 명확히 한다.
- [ ] 사용자에게 확인 화면만 보여주고 영향 범위와 복구 가능성을 설명하게 한다.
- [ ] 키보드·터치·느린 네트워크에서 우발 실행과 중복 실행을 테스트한다.
- [ ] 복원·실행 취소·승인 취소가 실제 데이터와 외부 시스템까지 일관되게 적용되는지 검증한다.

## 에이전트 적용 규칙

- 고위험 행동 명세에는 확인 대화상자만 제안하지 말고 예방·가역성·권한·감사를 함께 설계한다.
- 복구 가능 여부와 기간을 확인하지 않은 채 약속하지 않는다.
- 실제 대상과 수량을 동적 자리표시자로 명시한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
