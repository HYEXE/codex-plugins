# 권한·동의·개인정보 선택

## 한 문장 원칙

필요한 순간에 필요한 범위만 요청하고 목적·결과·대안을 설명하며 사용자가 이후에도 선택을 확인하고 변경·철회할 수 있게 한다.

## 적용 상황

앱 시작과 동시에 여러 권한을 요청하거나, 선택 동의와 필수 처리가 섞이고, 거부하면 기능 전체가 막히며, 설정에서 데이터 사용을 찾기 어려울 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 맥락적 요청

사용자가 기능의 가치를 이해하고 권한이 필요한 행동을 시작한 시점에 요청한다.

### 최소 범위

한 번에 광범위한 권한보다 과업에 필요한 데이터·기간·대상만 요청한다.

### 명확한 선택 결과

허용·거부·나중에 선택했을 때 무엇이 가능하고 어떤 대안이 있는지 설명한다.

### 철회 가능성

선택은 지속적으로 확인·변경할 수 있어야 하며 철회 후 데이터와 기능에 미치는 영향을 알려준다.

### 플랫폼과 서비스 구분

운영체제 권한, 계정 권한, 조직 관리자 정책, 법적 동의는 서로 다른 주체와 복구 경로를 가진다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 권한·동의별 목적, 필수 여부, 데이터 범위, 보존·공유, 거부 결과, 변경 경로를 정의한다.
- **MUST:** 선택 동의를 서비스 핵심 이용의 필수 조건처럼 위장하거나 시각적으로 거부를 숨기지 않는다.
- **MUST:** 운영체제 권한을 요청하기 전에 제품 내 설명으로 필요성과 대안을 제공한다.
- **MUST:** 거부 후에도 가능한 수동·제한 기능을 제공하거나 불가능한 이유를 구체적으로 설명한다.
- **MUST:** 설정에서 현재 선택, 적용 범위, 변경·철회 결과와 필요한 후속 조치를 확인할 수 있게 한다.

### SHOULD

- **SHOULD:** 일괄 동의보다 목적별 세분화와 합리적인 기본값을 제공한다.
- **SHOULD:** 권한이 장기간 사용되지 않거나 목적이 바뀌면 재검토·재동의를 고려한다.
- **SHOULD:** 개인정보 선택 화면을 법무 문구만으로 구성하지 않고 평이한 요약과 상세 근거를 계층화한다.
- **SHOULD:** 조직 관리자가 결정한 정책과 사용자가 변경할 수 있는 범위를 명확히 구분한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 기능별 필요한 데이터·권한·법적 근거·대안을 인벤토리한다.
2. 권한 요청 시점, 사전 설명, 플랫폼 대화상자, 결과 상태를 설계한다.
3. 허용·거부·부분 허용·만료·철회·관리자 제한 상태를 명세한다.
4. 설정, 데이터 내보내기·삭제, 지원과 정책 변경 흐름을 연결한다.
5. 이해도·자율성·접근성·기만 위험을 사용자와 전문가가 검토한다.
6. 동의율뿐 아니라 철회, 권한 오류, 기능 실패, 불만, 데이터 요청을 모니터링한다.

## 예외·극단 상황

- 조직 관리자가 최종 사용자 대신 권한을 설정하는 업무 제품
- 보호자·대리인·미성년자 관계가 있는 계정
- 위치·연락처·건강·생체·사진처럼 민감도가 높은 데이터
- 운영체제에서 ‘이번 한 번’, ‘사용 중’, ‘정확한 위치’ 등 부분 권한을 제공하는 경우
- 법적 근거가 동의가 아니지만 투명성과 사용자 제어가 필요한 처리

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 앱 시작 시 모든 권한을 연속 요청한다. | 관련 기능 사용 직전에 가치·범위·대안을 설명하고 필요한 권한만 요청한다. |
| 거부하면 같은 요청을 반복한다. | 거부를 존중하고 기능 맥락에서만 다시 설명하며 설정 경로를 제공한다. |
| ‘개인화 향상’처럼 목적을 포괄적으로 쓴다. | 어떤 데이터가 어떤 기능과 결과에 쓰이는지 구체적으로 설명한다. |
| 철회 경로를 계정 삭제와 묶는다. | 목적별 설정과 데이터 처리 결과를 별도로 제공한다. |
| 동의율을 성공 지표로만 본다. | 이해도, 후회, 철회, 기능 성공, 불만과 위해를 함께 본다. |

## 검증 방법

1. 사용자가 허용·거부 결과와 데이터 사용을 자신의 말로 설명하는지 확인한다.
2. 각 권한 상태와 운영체제 설정 변경 후 제품 상태가 정확히 갱신되는지 테스트한다.
3. 키보드·스크린 리더·확대 환경에서 동의와 거부가 동등하게 발견 가능한지 검증한다.
4. 가입·허용과 철회·삭제에 필요한 단계와 시간을 비교한다.

## 인수 기준

- [ ] 권한·동의별 목적, 필수 여부, 데이터 범위, 보존·공유, 거부 결과, 변경 경로를 정의한다.
- [ ] 선택 동의를 서비스 핵심 이용의 필수 조건처럼 위장하거나 시각적으로 거부를 숨기지 않는다.
- [ ] 운영체제 권한을 요청하기 전에 제품 내 설명으로 필요성과 대안을 제공한다.
- [ ] 거부 후에도 가능한 수동·제한 기능을 제공하거나 불가능한 이유를 구체적으로 설명한다.
- [ ] 설정에서 현재 선택, 적용 범위, 변경·철회 결과와 필요한 후속 조치를 확인할 수 있게 한다.
- [ ] 사용자가 허용·거부 결과와 데이터 사용을 자신의 말로 설명하는지 확인한다.
- [ ] 각 권한 상태와 운영체제 설정 변경 후 제품 상태가 정확히 갱신되는지 테스트한다.
- [ ] 키보드·스크린 리더·확대 환경에서 동의와 거부가 동등하게 발견 가능한지 검증한다.

## 에이전트 적용 규칙

- 개인정보·동의 요청에서는 법적 적합성을 보장하지 말고 검토 필요 항목을 명시한다.
- 거부 경로와 제한 기능을 정상 설계로 포함한다.
- 동의율을 높이는 기만적 문구나 비대칭 위계를 제안하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
