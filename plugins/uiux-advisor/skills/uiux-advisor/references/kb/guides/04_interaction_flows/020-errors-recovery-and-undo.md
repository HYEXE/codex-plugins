# 오류·복구·실행 취소

## 한 문장 원칙

오류를 예방하되 발생하면 원인과 영향을 구분하고 사용자의 작업을 보존하며 가장 안전하고 구체적인 복구 경로를 제공한다.

## 적용 상황

오류 코드나 ‘문제가 발생했습니다’만 보이거나, 재시도해도 되는지·데이터가 저장됐는지 알 수 없고, 실수 복구보다 확인 대화상자만 남용할 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 오류 유형 분리

입력 오류, 권한, 충돌, 네트워크, 서비스, 데이터 무결성, 외부 의존성은 사용자가 할 수 있는 행동과 책임이 다르다.

### 작업 보존

오류가 발생해도 가능한 한 입력·선택·위치·업로드·진행을 보존한다.

### 구체적 복구

문제가 무엇인지, 무엇이 영향을 받았는지, 무엇이 보존됐는지, 다음에 무엇을 할지 알려준다.

### 가역성 우선

되돌릴 수 있는 행동은 반복 확인보다 실행 취소와 버전 기록이 더 낮은 마찰로 실수를 회복하게 한다.

### 지원 가능한 진단

사용자에게 내부 세부를 노출하지 않으면서 참조 ID, 시간, 상태, 재현 정보를 지원 채널과 연결한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 오류 상태마다 원인 범주, 사용자 영향, 보존된 데이터, 가능한 행동, 재시도 안전성을 정의한다.
- **MUST:** 사용자 입력·작업을 불필요하게 삭제하지 않고 손실이 불가피하면 사전에 경고한다.
- **MUST:** 오류 메시지를 문제 위치 또는 관련 작업 가까이에 표시하고 페이지 수준 요약과 연결한다.
- **MUST:** 실행 취소·복원·버전 기록이 가능한 행동은 파괴 전 확인만으로 대체하지 않는다.
- **MUST:** 재시도·지원 문의가 중복 결제·중복 생성·상태 불일치를 만들지 않게 설계한다.

### SHOULD

- **SHOULD:** 오류 코드 대신 사용자 언어를 사용하되 지원용 참조 정보는 별도로 제공한다.
- **SHOULD:** 자동 재시도는 데이터 안전성과 횟수·간격을 통제하고 사용자에게 상태를 숨기지 않는다.
- **SHOULD:** 여러 하위 작업 중 일부만 실패하면 성공·실패 항목을 분리해 재처리하게 한다.
- **SHOULD:** 오류 빈도뿐 아니라 복구 성공률, 반복 오류, 작업 손실, 지원 전환을 측정한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 핵심 과업의 오류 분류와 실패 비용·가역성을 작성한다.
2. 오류 전 예방, 오류 시 보존, 사용자 메시지, 복구 행동, 지원 진단을 설계한다.
3. 재시도·취소·실행 취소·복원·수동 대체의 상태 전이를 명세한다.
4. 부분 성공, 중복 요청, 동시 편집, 세션 만료, 외부 실패를 추가한다.
5. 오류를 의도적으로 발생시켜 실제 과업과 보조기술에서 복구를 테스트한다.
6. 운영 로그와 지원 사례를 오류 분류와 연결해 우선순위를 갱신한다.

## 예외·극단 상황

- 결제는 성공했지만 화면 응답이 끊긴 불확실 상태
- 다른 사용자가 동시에 수정해 충돌이 발생한 협업 작업
- 삭제·전송·승인처럼 외부 세계에 이미 영향이 발생한 행동
- 일부 파일만 업로드되거나 일부 대상에게만 전송된 부분 성공
- 보안상 상세 원인을 공개하면 계정·데이터 존재를 노출하는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 모든 오류를 ‘다시 시도하세요’로 처리한다. | 재시도 가능한지, 무엇이 보존됐는지, 대체 행동과 지원 경로를 구체화한다. |
| 확인 대화상자를 모든 위험 행동에 사용한다. | 기본값, 제약, 미리보기, 실행 취소, 버전 복원으로 오류를 구조적으로 줄인다. |
| 오류 시 입력을 초기화한다. | 유효한 입력을 보존하고 민감 정보 예외를 설명한다. |
| 부분 성공을 전체 실패처럼 보인다. | 성공 항목과 실패 항목, 영향, 재처리 범위를 분리한다. |
| 내부 오류 코드를 그대로 노출한다. | 사용자에게 의미 있는 설명과 지원용 참조 ID를 분리한다. |

## 검증 방법

1. 오류 주입 테스트로 입력·네트워크·권한·충돌·외부 장애·타임아웃을 재현한다.
2. 사용자가 오류 원인과 보존 상태, 다음 행동을 정확히 설명하는지 확인한다.
3. 실행 취소·복원 기간, 다중 기기, 동시 편집, 재시도 멱등성을 검증한다.
4. 오류 메시지와 상태 변화가 키보드·스크린 리더에서 발견되고 복구 가능한지 테스트한다.

## 인수 기준

- [ ] 오류 상태마다 원인 범주, 사용자 영향, 보존된 데이터, 가능한 행동, 재시도 안전성을 정의한다.
- [ ] 사용자 입력·작업을 불필요하게 삭제하지 않고 손실이 불가피하면 사전에 경고한다.
- [ ] 오류 메시지를 문제 위치 또는 관련 작업 가까이에 표시하고 페이지 수준 요약과 연결한다.
- [ ] 실행 취소·복원·버전 기록이 가능한 행동은 파괴 전 확인만으로 대체하지 않는다.
- [ ] 재시도·지원 문의가 중복 결제·중복 생성·상태 불일치를 만들지 않게 설계한다.
- [ ] 오류 주입 테스트로 입력·네트워크·권한·충돌·외부 장애·타임아웃을 재현한다.
- [ ] 사용자가 오류 원인과 보존 상태, 다음 행동을 정확히 설명하는지 확인한다.
- [ ] 실행 취소·복원 기간, 다중 기기, 동시 편집, 재시도 멱등성을 검증한다.

## 에이전트 적용 규칙

- 오류 문구를 작성할 때 원인, 영향, 보존, 행동, 지원을 모두 고려하되 공개하면 안 되는 보안 정보는 분리한다.
- 재시도가 안전한지 모르면 자동으로 권하지 말고 확인 필요 항목으로 남긴다.
- 실행 취소 가능성을 확인 없이 약속하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
