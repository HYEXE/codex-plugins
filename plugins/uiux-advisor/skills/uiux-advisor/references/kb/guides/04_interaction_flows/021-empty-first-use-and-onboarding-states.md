# 빈 상태·첫 사용·온보딩

## 한 문장 원칙

빈 화면을 하나의 상태로 뭉뚱그리지 말고 왜 비어 있는지, 사용자에게 가능한 다음 행동이 무엇인지, 예시·권한·데이터가 필요한지를 상태별로 설명한다.

## 적용 상황

첫 로그인 화면이 텅 비어 있거나 검색 0건, 필터 결과 없음, 권한 없음, 삭제 후 비어 있음, 서비스 오류가 모두 같은 일러스트와 CTA를 사용할 때 적용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 원인별 구분

처음 데이터가 없음, 사용자가 모두 완료함, 검색·필터로 없음, 권한 없음, 오류로 불러오지 못함은 의미와 다음 행동이 다르다.

### 가치의 맥락

기능 설명보다 사용자가 첫 가치를 얻기 위해 필요한 최소 행동과 결과를 보여준다.

### 점진적 온보딩

사용 전에 모든 기능을 설명하기보다 과업 시점에 필요한 도움과 안전한 샘플을 제공한다.

### 현실적인 예시

샘플 데이터는 실제 구조·길이·제약을 보여주되 실제 데이터로 오인되지 않게 한다.

### 건너뛰기와 재접근

튜토리얼은 강제하지 않고 나중에 다시 찾을 수 있으며 실제 작업을 방해하지 않아야 한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 빈 상태의 원인과 사용자에게 가능한 행동을 상태 모델에서 구분한다.
- **MUST:** 첫 가치 달성에 필요한 가장 작은 다음 행동을 명확한 CTA와 함께 제공한다.
- **MUST:** 오류·권한·검색 결과 없음 상태를 정상적인 초기 빈 상태처럼 표현하지 않는다.
- **MUST:** 강제 투어·팝업이 핵심 과업과 접근성 탐색을 가로막지 않게 하고 건너뛰기·재접근을 제공한다.
- **MUST:** 샘플·데모 데이터는 실제 데이터와 시각·텍스트로 구분하고 삭제·교체 방법을 제공한다.

### SHOULD

- **SHOULD:** 온보딩을 사용자 역할·목표·숙련도에 맞게 조정하되 과도한 초기 질문을 줄인다.
- **SHOULD:** 첫 성공 후 다음 고급 행동을 단계적으로 제안하고 반복 사용자에게는 숨긴다.
- **SHOULD:** 데이터 가져오기, 템플릿, 샘플, 수동 생성 등 여러 시작 경로를 과업에 맞게 제공한다.
- **SHOULD:** 온보딩 완료율보다 첫 가치 시간, 실제 과업 성공, 도움 재방문을 측정한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 빈 상태가 발생하는 원인과 사용자 권한·데이터·과업 단계별 상태를 분류한다.
2. 각 상태에 필요한 설명, CTA, 보조 경로, 예시, 지원을 정의한다.
3. 첫 가치까지 필요한 최소 흐름과 선택적 고급 도움을 설계한다.
4. 강제·건너뛰기·복귀·재방문·다중 역할 시나리오를 명세한다.
5. 신규·복귀·전문 사용자와 보조기술 환경에서 과업을 테스트한다.
6. 첫 가치 시간과 실패 상태 데이터를 사용해 온보딩을 줄이고 개선한다.

## 예외·극단 상황

- 관리자가 먼저 설정해야 최종 사용자가 시작할 수 있는 제품
- 데이터 가져오기가 오래 걸리거나 일부만 성공하는 경우
- 초기 화면에 민감한 샘플 데이터를 보여주면 안 되는 경우
- 사용자가 여러 역할·워크스페이스를 오가며 빈 상태 의미가 달라지는 경우
- 기능이 계절·프로젝트 주기에 따라 일시적으로 비어 있는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 모든 빈 상태에 ‘새로 만들기’를 표시한다. | 검색·필터·권한·오류·완료 상태에 맞는 복구와 설명을 제공한다. |
| 긴 제품 투어를 먼저 강제한다. | 첫 과업과 연결된 짧은 도움을 제공하고 건너뛰기·재접근을 허용한다. |
| 일러스트만 있고 다음 행동이 없다. | 원인, 가치, 구체적 CTA, 대체 경로를 함께 제공한다. |
| 샘플을 실제 데이터로 오인하게 한다. | 명시적 샘플 표시와 삭제·교체 경로를 제공한다. |
| 온보딩 완료율만 최적화한다. | 첫 가치, 오류, 이탈, 지원, 장기 과업 성공을 함께 본다. |

## 검증 방법

1. 각 빈 상태를 원인만 바꿔 제시하고 사용자가 상황과 다음 행동을 정확히 이해하는지 확인한다.
2. 신규 사용자가 설명 없이 첫 가치를 얻는 데 필요한 단계와 시간을 관찰한다.
3. 강제 투어를 건너뛴 사용자와 보조기술 사용자가 동일한 기능을 찾을 수 있는지 검증한다.
4. 검색·필터·권한·오류 데이터를 빈 상태 유형별로 분리해 모니터링한다.

## 인수 기준

- [ ] 빈 상태의 원인과 사용자에게 가능한 행동을 상태 모델에서 구분한다.
- [ ] 첫 가치 달성에 필요한 가장 작은 다음 행동을 명확한 CTA와 함께 제공한다.
- [ ] 오류·권한·검색 결과 없음 상태를 정상적인 초기 빈 상태처럼 표현하지 않는다.
- [ ] 강제 투어·팝업이 핵심 과업과 접근성 탐색을 가로막지 않게 하고 건너뛰기·재접근을 제공한다.
- [ ] 샘플·데모 데이터는 실제 데이터와 시각·텍스트로 구분하고 삭제·교체 방법을 제공한다.
- [ ] 각 빈 상태를 원인만 바꿔 제시하고 사용자가 상황과 다음 행동을 정확히 이해하는지 확인한다.
- [ ] 신규 사용자가 설명 없이 첫 가치를 얻는 데 필요한 단계와 시간을 관찰한다.
- [ ] 강제 투어를 건너뛴 사용자와 보조기술 사용자가 동일한 기능을 찾을 수 있는지 검증한다.

## 에이전트 적용 규칙

- 빈 상태를 요청받으면 원인 유형을 먼저 분류하고 상태별 문구와 행동을 제안한다.
- 가상의 제품 가치나 샘플 데이터를 사실처럼 만들지 말고 자리표시자로 표현한다.
- 온보딩은 기능 설명 목록이 아니라 첫 가치 흐름으로 구성한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
