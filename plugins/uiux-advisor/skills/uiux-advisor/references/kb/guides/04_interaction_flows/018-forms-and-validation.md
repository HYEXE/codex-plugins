# 폼과 검증

## 한 문장 원칙

필요한 정보만 사용자가 이해하는 방식으로 묻고, 입력 전 요구사항·입력 중 지원·제출 후 오류 복구를 하나의 폼 경험으로 설계한다.

## 적용 상황

필드가 많고 왜 필요한지 불분명하거나, 브라우저 자동완성·복사·붙여넣기를 막고, 오류가 제출 후 상단에만 표시되거나 입력값이 사라질 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 최소 정보

각 필드는 사용자 결과와 운영 필요에 직접 연결되어야 하며 나중에 추론·가져오기·선택적으로 받을 수 있는 정보는 제거한다.

### 자연스러운 질문

필드 구조보다 사용자가 아는 질문과 답변 단위를 우선하고 관련 항목은 의미 구조로 그룹화한다.

### 입력 자유와 관용

붙여넣기, 자동완성, 비표준 이름·주소·전화, 공백·구분자 등 합리적인 입력 변이를 허용한다.

### 검증의 목적

검증은 사용자를 통제하기보다 잘못된 제출을 방지하고 정확히 복구하도록 돕는 수단이다.

### 데이터 보존

오류가 발생해도 유효한 입력과 사용자의 작업을 보존하고 민감 데이터는 보안 요구와 균형을 맞춘다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 각 필드의 필요성, 사용 목적, 필수·선택 여부, 데이터 보존과 공개 범위를 정의한다.
- **MUST:** 레이블, 그룹 제목, 형식·단위·예시, 오류 메시지를 의미적으로 연결한다.
- **MUST:** 클라이언트 검증에만 의존하지 않고 서버 검증 결과를 같은 오류 모델로 전달한다.
- **MUST:** 오류 시 입력값을 보존하고 페이지 수준 요약과 해당 필드 오류를 함께 제공한다.
- **MUST:** 키보드, 자동완성, 붙여넣기, 비밀번호 관리자, 확대, 스크린 리더 사용을 방해하지 않는다.

### SHOULD

- **SHOULD:** 질문을 논리적 순서로 배치하고 조건부 필드는 관련 답변 후에만 노출한다.
- **SHOULD:** 입력 마스크는 편의를 제공하되 원시 입력·붙여넣기·수정과 보조기술을 방해하지 않게 한다.
- **SHOULD:** 실시간 검증은 사용자가 필드를 떠났거나 의미 있는 입력이 끝난 뒤, 오탐을 줄이는 경우에 사용한다.
- **SHOULD:** 긴 폼은 저장·복귀, 검토 단계, 변경 링크와 제출 전 요약을 제공한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 과업 완료에 필수인 데이터와 법·운영·분석 목적의 추가 데이터를 분리한다.
2. 사용자 질문 단위와 데이터 모델의 차이를 매핑한다.
3. 필드별 정상·빈 값·형식 오류·범위 오류·중복·서비스 오류 상태를 정의한다.
4. 레이블·도움말·자동완성·키보드·개인정보·보존 정책을 명세한다.
5. 대표·극단 입력과 오류 복구를 실제 기기·보조기술에서 테스트한다.
6. 오류율, 반복 제출, 중단, 지원 문의로 필드 필요성과 문구를 지속 개선한다.

## 예외·극단 상황

- 국가별로 이름·주소·신분 번호 구조가 다른 경우
- 한 입력값이 여러 필드와 외부 기록의 일치 여부에 영향을 주는 경우
- 금융·의료·법률 데이터처럼 입력 실수 비용과 보안 요구가 큰 경우
- 사용자가 문서를 준비하거나 다른 사람에게 확인해야 하는 긴 폼
- 오프라인 저장 또는 다중 기기 복귀가 필요한 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 플레이스홀더와 별표만으로 질문과 필수 여부를 표시한다. | 영구 레이블, 명시적 선택 표기, 관련 도움말을 제공한다. |
| 입력 즉시 빨간 오류를 띄운다. | 사용자가 답할 시간을 주고 의미 있는 시점에 구체적으로 검증한다. |
| 오류 후 모든 필드를 초기화한다. | 유효 입력을 보존하고 민감 필드의 재입력 이유를 설명한다. |
| 붙여넣기와 비밀번호 관리자를 막는다. | 보안 효과를 검증하고 대체로 자동완성·붙여넣기를 허용한다. |
| 서비스 장애를 ‘입력 오류’로 보여준다. | 사용자 수정 가능 오류와 시스템 오류를 구분하고 재시도·보존 상태를 설명한다. |

## 검증 방법

1. 필드별 대표·최소·최대·빈 값·특수문자·다국어·붙여넣기 입력을 테스트한다.
2. 오류를 여러 개 만든 뒤 요약, 포커스, 해당 필드 이동, 수정, 재제출을 검증한다.
3. 키보드와 스크린 리더로 레이블·설명·오류·그룹 관계를 확인한다.
4. 실제 사용자에게 필요한 정보 준비와 중단·복귀를 포함한 전체 과업을 관찰한다.

## 인수 기준

- [ ] 각 필드의 필요성, 사용 목적, 필수·선택 여부, 데이터 보존과 공개 범위를 정의한다.
- [ ] 레이블, 그룹 제목, 형식·단위·예시, 오류 메시지를 의미적으로 연결한다.
- [ ] 클라이언트 검증에만 의존하지 않고 서버 검증 결과를 같은 오류 모델로 전달한다.
- [ ] 오류 시 입력값을 보존하고 페이지 수준 요약과 해당 필드 오류를 함께 제공한다.
- [ ] 키보드, 자동완성, 붙여넣기, 비밀번호 관리자, 확대, 스크린 리더 사용을 방해하지 않는다.
- [ ] 필드별 대표·최소·최대·빈 값·특수문자·다국어·붙여넣기 입력을 테스트한다.
- [ ] 오류를 여러 개 만든 뒤 요약, 포커스, 해당 필드 이동, 수정, 재제출을 검증한다.
- [ ] 키보드와 스크린 리더로 레이블·설명·오류·그룹 관계를 확인한다.

## 에이전트 적용 규칙

- 폼 명세를 작성할 때 필드 목록뿐 아니라 필요성, 데이터 사용, 자동완성, 검증 시점, 오류와 보존을 포함한다.
- 국가별 식별자·주소 형식을 임의로 표준화하지 않는다.
- 보안 이유를 가정해 붙여넣기나 비밀번호 관리자를 금지하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
