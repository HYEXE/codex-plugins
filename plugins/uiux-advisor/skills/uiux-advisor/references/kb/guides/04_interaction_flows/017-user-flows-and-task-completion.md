# 사용자 흐름과 과업 완료

## 한 문장 원칙

행복 경로만 연결하지 말고 시작 조건, 분기, 중단, 저장, 복귀, 권한, 오류, 복구, 완료 후 결과까지 하나의 상태 흐름으로 설계한다.

## 적용 상황

와이어플로가 화면 순서만 보여주고 사용자가 중간에 멈추거나 다른 채널로 이동했을 때, 권한·데이터·네트워크 상태가 달라졌을 때의 동작이 정의되지 않았을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 과업 경계

흐름은 화면 진입부터가 아니라 사용자가 필요한 정보와 권한을 준비하는 시점부터 결과를 확인하고 다음 행동을 하는 시점까지 본다.

### 상태 기반 모델

화면 목록보다 사용자·데이터·시스템의 상태와 이벤트, 전환, 가드 조건을 명시해야 누락을 줄일 수 있다.

### 진행과 통제

사용자는 현재 위치, 남은 작업, 저장 여부, 취소·뒤로 가기의 결과를 이해해야 한다.

### 중단과 복귀

실제 과업은 알림, 승인 대기, 문서 준비, 기기 변경으로 중단된다. 복귀 지점과 만료를 설계한다.

### 완료의 증거

완료 화면은 성공 메시지만이 아니라 제출 내용, 결과 상태, 다음 단계, 영수증·기록·지원 경로를 제공한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 흐름의 시작 상태, 종료 상태, 성공 정의, 취소·포기·실패 상태를 명시한다.
- **MUST:** 각 단계의 입력, 전제 조건, 시스템 검증, 상태 변경, 사용자에게 보이는 피드백을 정의한다.
- **MUST:** 뒤로 가기, 새로고침, 중복 제출, 세션 만료, 기기 변경에서 데이터 보존과 결과를 명세한다.
- **MUST:** 권한 없음, 데이터 없음, 서비스 지연, 외부 시스템 실패에서 안전한 대체 경로를 제공한다.
- **MUST:** 완료 후 사용자가 결과를 확인·저장·수정·취소·문의할 수 있는 범위를 설명한다.

### SHOULD

- **SHOULD:** 사용자에게 필요한 단계만 보이고 내부 처리 단계는 상태 피드백으로 추상화한다.
- **SHOULD:** 긴 흐름은 의미 있는 단계와 저장 지점을 제공하되 불필요한 단계 표시로 부담을 늘리지 않는다.
- **SHOULD:** 분기 조건과 사용자에게 묻는 질문의 필요성을 제거 가능성부터 검토한다.
- **SHOULD:** 다채널 전환 시 동일한 상태와 기록을 유지하거나 차이를 명확히 설명한다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 사용자 목표, 시작·완료 조건, 외부 의존성과 위험을 정의한다.
2. 정상 사례를 상태·이벤트·전환 표로 작성한다.
3. 분기, 중단, 뒤로 가기, 만료, 오류, 권한, 중복 행동을 추가한다.
4. 각 상태의 콘텐츠, 행동, 포커스, 저장·복구 동작을 명세한다.
5. 프로토타입으로 대표·극단 과업과 복귀 시나리오를 테스트한다.
6. 구현 이벤트와 분석을 상태 모델에 맞춰 계측하고 실제 실패 경로를 개선한다.

## 예외·극단 상황

- 다른 사람의 승인·서명·결제를 기다리는 비동기 흐름
- 한 과업을 여러 사용자가 공동 편집하거나 소유권을 넘기는 경우
- 오프라인 또는 불안정한 네트워크에서 진행해야 하는 경우
- 법적 제출처럼 완료 후 수정·취소가 제한되는 경우
- 외부 인증·결제·정부 서비스로 이동했다 돌아오는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 화면 간 화살표만 그려 상태를 설명한다. | 각 전환의 이벤트, 조건, 데이터 변경, 피드백, 실패를 표로 정의한다. |
| 뒤로 가면 입력을 모두 잃는다. | 보존 범위와 민감 정보 예외를 정의하고 손실 전 경고한다. |
| 완료 후 ‘성공’만 보여준다. | 제출 내용, 참조 번호, 다음 단계, 예상 시간, 수정·지원 경로를 제공한다. |
| 외부 시스템 실패를 사용자 입력 오류로 표시한다. | 사용자 행동으로 해결 가능한 문제와 서비스 문제를 구분한다. |
| 세션 만료가 갑자기 발생한다. | 사전 경고, 연장, 임시 저장, 안전한 재인증·복귀를 제공한다. |

## 검증 방법

1. 상태 전이 표에서 모든 이벤트가 하나 이상의 결과와 사용자 피드백을 갖는지 확인한다.
2. 사용성 테스트에서 중단·복귀·뒤로 가기·중복 클릭·외부 이동을 의도적으로 유발한다.
3. 실제 구현에서 분석 이벤트가 화면 조회가 아니라 과업 상태를 정확히 나타내는지 검증한다.
4. 지원·오류 로그로 설계하지 않은 우회와 막힌 상태를 찾는다.

## 인수 기준

- [ ] 흐름의 시작 상태, 종료 상태, 성공 정의, 취소·포기·실패 상태를 명시한다.
- [ ] 각 단계의 입력, 전제 조건, 시스템 검증, 상태 변경, 사용자에게 보이는 피드백을 정의한다.
- [ ] 뒤로 가기, 새로고침, 중복 제출, 세션 만료, 기기 변경에서 데이터 보존과 결과를 명세한다.
- [ ] 권한 없음, 데이터 없음, 서비스 지연, 외부 시스템 실패에서 안전한 대체 경로를 제공한다.

- [ ] 상태 전이 표에서 모든 이벤트가 하나 이상의 결과와 사용자 피드백을 갖는지 확인한다.

## 에이전트 적용 규칙

- 흐름 명세에는 정상 경로 외에 상태 전이와 실패·복귀를 반드시 포함한다.
- 백엔드 동작을 모르면 가정으로 표시하고 확인 질문 또는 인수 기준으로 남긴다.
- 완료 상태의 법적·운영적 의미를 임의로 단정하지 않는다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.
