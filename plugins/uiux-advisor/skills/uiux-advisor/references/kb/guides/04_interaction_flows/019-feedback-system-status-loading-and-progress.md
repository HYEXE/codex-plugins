# 피드백·시스템 상태·로딩·진행

## 한 문장 원칙

사용자 행동이 접수되었는지, 시스템이 무엇을 하는지, 결과가 언제·어떻게 나타나는지, 사용자가 기다리거나 다른 일을 해도 되는지를 지속적으로 알려준다.

## 적용 상황

클릭 후 반응이 없어 중복 제출이 발생하거나, 스피너만 오래 돌고, 진행률이 부정확하며, 백그라운드 작업이 끝났는지 알 수 없을 때 사용한다.

## 이 가이드가 답하는 결정

1. 이 문제에서 반드시 지켜야 할 사용자 결과와 품질 경계는 무엇인가?
2. 어떤 상태·맥락·사용자 조건을 포함해야 설계가 실제 환경에서 무너지지 않는가?
3. 어떤 증거와 검증 방법으로 이 결정을 승인·수정·폐기할 것인가?

## 핵심 원리

### 즉각적 접수

시스템 응답이 늦어도 사용자의 입력이 접수되었음을 즉시 보여 중복 행동과 불안을 줄인다.

### 범위에 맞는 피드백

버튼 하나의 작업인지 페이지·전체 앱 작업인지에 따라 로딩 표시의 위치와 차단 범위를 맞춘다.

### 결정 가능한 정보

남은 시간, 단계, 취소 가능성, 백그라운드 처리, 데이터 안전 여부처럼 사용자가 다음 행동을 정하는 데 필요한 정보를 제공한다.

### 안정성과 연속성

콘텐츠가 로딩되며 레이아웃이 크게 움직이거나 포커스·스크롤이 사라지지 않게 한다.

### 완료와 실패의 폐쇄

작업이 성공·부분 성공·실패·취소 중 무엇으로 끝났는지 명확히 하고 결과와 다음 행동을 연결한다.

## 규범적 요구사항

> **MUST**는 위반 시 사용자 과업·안전·접근성·신뢰 또는 검증 가능성이 실질적으로 훼손되는 요구사항이다.  
> **SHOULD**는 특별한 맥락과 근거가 있을 때만 예외를 허용하는 강한 권고다.  
> **MAY**는 선택 가능한 구현 방식이며, 대안의 사용자 결과와 위험을 기록해야 한다.

### MUST

- **MUST:** 사용자 행동 직후 접수 상태를 보여주고 중복 실행 가능성과 버튼 상태를 정의한다.
- **MUST:** 로딩·대기·처리 중·백그라운드·완료·부분 성공·오류·취소 상태를 구분한다.
- **MUST:** 결정적 진행률만 숫자로 표시하고 알 수 없는 진행을 허위 퍼센트로 표현하지 않는다.
- **MUST:** 상태 변화와 중요한 결과를 시각 외 채널로도 알리고 포커스를 불필요하게 이동하지 않는다.
- **MUST:** 장시간 작업에서 이탈·새로고침·기기 변경 후 결과 확인과 재시도·취소 방법을 제공한다.

### SHOULD

- **SHOULD:** 예상 지연이 짧으면 불필요한 깜빡임을 피하고, 길어지면 단계·예상·대안을 점진적으로 제공한다.
- **SHOULD:** 스켈레톤은 최종 구조를 정확히 예고할 때만 사용하고 의미 없는 장식 애니메이션을 피한다.
- **SHOULD:** 사용자가 기다리는 동안 안전하게 수행할 수 있는 다른 행동과 작업 보존 상태를 설명한다.
- **SHOULD:** 성공 메시지는 자동 사라짐만으로 두지 않고 중요한 결과는 지속 가능한 기록으로 남긴다.

### MAY

- **MAY:** 프로젝트의 플랫폼·도메인·조직 제약이 정당화하면 다른 패턴을 선택할 수 있다. 단, 사용자 결과, 접근성, 위해, 되돌리기 가능성, 검증 계획을 결정 로그에 남긴다.
- **MAY:** 검증 비용을 줄이기 위해 충실도와 방법을 조정할 수 있다. 단, 조정으로 답할 수 없게 된 질문과 미검증 영역을 명시한다.

## 설계·실행 절차

1. 각 작업의 기대 시간, 범위, 가역성, 네트워크·외부 의존성을 분류한다.
2. 접수부터 종료까지 상태와 전환·타임아웃·중복 행동 규칙을 정의한다.
3. 상태별 시각·텍스트·보조기술 피드백과 차단 범위를 설계한다.
4. 느림, 오프라인, 부분 성공, 재접속, 백그라운드 완료 시나리오를 추가한다.
5. 실제 지연 분포와 사용자 과업으로 인지·통제·중복 행동을 테스트한다.
6. 성능·오류·중복 제출·취소 데이터를 상태 설계와 함께 개선한다.

## 예외·극단 상황

- 여러 하위 작업이 서로 다른 시간에 성공·실패하는 일괄 처리
- 완료까지 수분·시간이 걸리고 이메일·알림으로 결과를 전달하는 작업
- 사용자가 같은 객체를 여러 탭이나 기기에서 변경하는 경우
- 오프라인 큐에 저장했다가 나중에 동기화하는 작업
- 사용자 행동이 외부 결제·서명·검토 시스템에 전달되는 경우

## 실패 패턴과 교정

| 실패 패턴 | 교정 방법 |
|---|---|
| 버튼을 눌러도 시각 변화가 없어 다시 누른다. | 즉시 처리 중 상태와 중복 실행 규칙을 표시한다. |
| 정확하지 않은 99%에서 오래 멈춘다. | 알 수 없는 진행과 단계 기반 진행을 구분하고 지연 이유·대안을 제공한다. |
| 전체 페이지를 막는 스피너를 남용한다. | 작업 범위에 맞는 부분 로딩과 기존 콘텐츠 유지, 독립 행동을 제공한다. |
| 토스트가 사라지면 완료 기록이 없다. | 중요 결과는 페이지 상태·작업 기록·영수증에 지속적으로 남긴다. |
| 재시도 시 중복 처리가 발생한다. | 멱등성·작업 식별자·현재 상태 조회를 설계하고 사용자에게 결과를 설명한다. |

## 검증 방법

1. 실제 또는 인위적 네트워크 지연에서 사용자가 작업 접수와 현재 상태를 이해하는지 관찰한다.
2. 중복 클릭, 새로고침, 뒤로 가기, 오프라인 전환, 재로그인에서 결과 일관성을 확인한다.
3. 스크린 리더로 상태 갱신이 과도하지 않고 필요한 정보가 전달되는지 검증한다.
4. 현장 성능 데이터와 중복 실행·포기·지원 문의를 함께 분석한다.

## 인수 기준

- [ ] 사용자 행동 직후 접수 상태를 보여주고 중복 실행 가능성과 버튼 상태를 정의한다.
- [ ] 로딩·대기·처리 중·백그라운드·완료·부분 성공·오류·취소 상태를 구분한다.
- [ ] 결정적 진행률만 숫자로 표시하고 알 수 없는 진행을 허위 퍼센트로 표현하지 않는다.
- [ ] 상태 변화와 중요한 결과를 시각 외 채널로도 알리고 포커스를 불필요하게 이동하지 않는다.
- [ ] 장시간 작업에서 이탈·새로고침·기기 변경 후 결과 확인과 재시도·취소 방법을 제공한다.
- [ ] 실제 또는 인위적 네트워크 지연에서 사용자가 작업 접수와 현재 상태를 이해하는지 관찰한다.
- [ ] 중복 클릭, 새로고침, 뒤로 가기, 오프라인 전환, 재로그인에서 결과 일관성을 확인한다.

## 에이전트 적용 규칙

- 로딩 명세에는 표시 모양보다 상태 모델, 범위, 중복 실행, 취소, 완료 기록을 우선한다.
- 실제 처리 시간을 모르면 허위 예상 시간이나 퍼센트를 만들지 않는다.
- 알림이 자동 사라지는 경우 중요 정보의 지속 경로를 제안한다.
- 입력에 근거가 없으면 사실을 보충하지 말고 가정, 확인 질문 또는 검증 과제로 표시한다.
- 정적 이미지·텍스트만 제공된 경우 키보드, 포커스, 보조기술, 성능, 동적 상태를 통과했다고 단정하지 않는다.
- 권고를 제시할 때 사용자 영향, 트레이드오프, 검증 방법을 함께 적는다.

## 범위와 근거 수준

이 문서는 공개 표준, 공공 서비스 가이드, 제품 디자인 시스템, UX 연구 자료를 교차해 재구성한 독립적인 한국어 실무 가이드다. 특정 출처의 원문을 대체하거나 특정 조직의 승인·제휴를 의미하지 않는다.

규범 표준에 직접 근거한 요구사항과 여러 출처를 종합한 실무 권고를 구분해 사용한다. 법률·규제 준수, 현재 제품 기능, 최신 브라우저·보조기술 지원, 성능 지표와 임계값처럼 변할 수 있는 사항은 적용 시점의 공식 자료와 실제 구현으로 다시 확인한다.

> **최신성 주의:** 이 가이드는 시간에 따라 정의·도구·권고가 바뀔 수 있는 내용을 포함한다. 현재 공식 문서와 운영 데이터를 확인하지 않은 수치·기능·임계값은 미검증으로 표시한다.
