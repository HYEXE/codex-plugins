# 장면 recipe

필요한 장면 section만 읽고 적용한다. 장면 이름이 아니라 설명 목표와 fallback을 먼저 결정한다.

## timeline

사용 조건:

- 사건·릴리스·실험 결과의 순서가 결론에 중요하다.
- 각 시점에 서로 다른 근거 상태나 변화가 있다.

계약:

- `events`는 실제 시간 순서를 보존한다.
- `date`, `title`, `detail`을 text로 제공하고 색만으로 tone을 구분하지 않는다.
- demo에서는 ready → running → complete 순서로 자동 강조한다.
- experience에서는 각 event를 button으로 직접 선택한다.
- fallback은 날짜순 사건 목록이다.

피해야 할 사용:

- 순서가 중요하지 않은 기능 목록
- 근거가 없는 정확한 날짜 보간
- 사건 수가 많아 발표자가 읽기 어려운 축소형 연표

## diagram

사용 조건:

- 구성 요소의 역할과 연결 관계가 핵심이다.
- 노드를 선택해 세부 설명을 확인하는 것이 정적 문단보다 명확하다.

계약:

- 모든 node는 고유 `id`, 짧은 `label`, 독립적인 `detail`을 가진다.
- 모든 link의 `from`과 `to`는 존재하는 node를 참조한다.
- node를 keyboard로 선택할 수 있고 현재 선택을 `aria-pressed`로 알린다.
- link는 시각 선뿐 아니라 `A → B: 관계` 형식의 텍스트 목록으로 제공한다.
- fallback은 node 역할 목록과 link 관계 목록이다.

피해야 할 사용:

- 자유 배치가 의미를 만들지만 좌표와 responsive 규칙이 없는 복잡한 네트워크
- 방향·관계를 색 또는 선 모양만으로 구분하는 도식

## code-walkthrough

사용 조건:

- 특정 코드 줄과 설명의 순서를 동기화해야 한다.
- 전체 코드 실행보다 제어 흐름·상태 변화 설명이 목적이다.

계약:

- code는 textContent로 렌더링하고 실행하지 않는다.
- 각 항목은 한 줄 또는 짧은 논리 블록과 하나의 explanation을 가진다.
- demo에서는 자동 강조하고 replay·skip·cancel을 제공한다.
- experience에서는 코드 줄 button으로 직접 이동한다.
- fallback은 줄 번호가 있는 코드 블록과 번호별 해설 목록이다.

피해야 할 사용:

- 실제 실행 결과가 핵심인데 sandbox와 오류 경로가 없는 경우
- 화면에 맞지 않는 전체 파일 또는 가로 스크롤이 긴 코드
- 구문 강조를 위해 코드 의미보다 많은 색을 사용하는 경우

## before-after

사용 조건:

- 같은 대상의 변화가 핵심이고 전후 기준이 동일하다.
- 두 상태를 번갈아 보는 것이 나란히 놓는 것보다 차이를 쉽게 만든다.

계약:

- before와 after에 같은 비교 항목과 단위를 사용한다.
- 전환 button과 `aria-pressed`로 현재 상태를 알린다.
- 상태가 바뀌어도 layout이 크게 이동하지 않게 한다.
- fallback은 같은 기준의 두 열 comparison이다.

피해야 할 사용:

- 서로 다른 대상이나 단위를 억지로 전후로 묶는 경우
- after를 과장하기 위해 scale, crop 또는 기준선을 다르게 쓰는 경우
